# Duty-HGS 北京独立子问题单轮教育耗时诊断

## 结论

本包只测一次初始完整邻域扫描，不实际接受动作、不进入下一轮，也不形成算法成绩或算例选择。北京 37 客户子问题共生成 2132 个动作，扫描耗时 16.620887 秒。纯油车动作 1564 个，合计 1.018019 秒；涉及电动车动作 568 个，合计 15.578491 秒。

初次汇总按未加罚的成本找到了一个便宜 5.540786% 的候选；事后完整真值复核确认它带 1 条违规，不能据此判断算法会接受。按算法实际使用的初始罚值重新排列全部 197 个已评价候选后，真正的最佳候选是一次完整整日车型—任务交换：完整可行、0 违规，罚后成本改善 1.984679%，增量评价与完整重算逐项相等。按现有 best-improvement 写法，这个候选会被接受，随后重新生成并扫描下一轮完整邻域。

这直接支持“涉及电动车的候选修复是单轮主要耗时来源”，也证明当前初始解至少需要再扫一轮；完整局部最优究竟需要多少轮、总耗时怎样随规模增长，本包没有测。更正和逐候选罚后结果分别保存在 `penalized_recheck.json` 与 `penalized_recheck.csv`。

## 交付前九条自检

1. 每个事实是否有出处？——逐动作状态与耗时在同包 raw_runs.csv，来源、版本和哈希在 metadata.json，汇总在 decision.json。
2. 有没有把建议或担忧写成已决或状态？——没有；这里只登记技术诊断。
3. 改动范围有没有超出任务文本？——没有；只做用户批准的问题定位。
4. 有没有碰受保护文件？——未碰，运行前后哈希一致，见 metadata.json。
5. 待决事项是否转成候选并写清代价？——本包不新增用户待决事项。
6. 有没有用自造词或内部任务号跟用户说话？——没有。
7. 失败、跳过、超时、异常结果有没有如实保留？——每个被拒动作及错误类型均逐行保留。
8. 四件套齐了吗？——metadata.json、raw_runs.csv、decision.json、artifact_hashes.json、report.md 齐全。
9. HANDOFF 和 memory 是否同步？——本轮审查闭合后统一同步。
