# E6-RAO-GAP-01：Rao 2019 实体调货与现有 E6 的缺口

文献核对源：饶卫振等（2019），Zotero 条目 `MTCWTY8Q`，本地 PDF `Zotero/storage/W96R3AUG/饶卫振 等 _ 2019 _ 一种求解协作配送成本分摊问题核仁解的近似迭代算法.pdf`，逐页核对第 1520—1522 页。

## 结论

**FACT：Rao 2019 确实提供了“不先决定谁付钱”的系统总成本思路。** 第 1520 页先求各联盟的协作配送成本，再在优化完成后分摊成本；第 1521 页式（1）把客户配送路线与车场间调货路线同时放进联盟目标。因此，系统层可以先只算“整个联盟一共花多少钱”，不需要收入，也不需要预先指定哪个承包商最终承担调货费。

**FACT：但 Rao 2019 印出的式（1）—（15）不能按原样得到有效的实体调货方案。** 论文定义了车场间货量 \(Q_{ij}\) 和调货弧变量 \(y_{ijk}\)，却没有约束要求正的 \(Q_{ij}\) 必须由某辆车承运。令所有 \(y_{ijk}=0\)，式（5）、式（8）和变量域式（14）仍然成立，而且式（1）的调货项最小。因此“逐式照抄”会得到零调货路线、零调货代价，与论文文字表达的实体调货意图相反。

**FACT：Rao 原式也没有给出大宗货物拆成多趟的方法。** 式（8）把完整的 \(Q_{ij}\) 乘到单车弧变量上；若 \(Q_{ij}>Q\)，任何单车取该弧都会违反容量。当前 pilot07 的 11 个有货方向中，7 个方向超过单车容量；最大方向为 6390 kg，而现有柴油车和电动车载重分别为 1735 kg、1700 kg。因此，现有数据不能直接套用该式。

**判定：当前不能靠一个隔离的薄包装“精确复现 Rao 的实体调货”。** 要实现论文文字想表达的模型，至少要补“每公斤货由哪一趟车承运、货量如何拆趟、调货车和末端配送车如何共同占用现有车队上限”三部分。它们不是现成公式的机械翻译，而是模型补全。此轮没有擅自补公式，也没有运行 seed 1 小试。

## Rao 2019 实际给出的语义

| 文献位置 | 已确认内容 | 对本项目的含义 |
|---|---|---|
| 第 1520 页 | 先优化各子联盟配送成本，再做合作博弈成本分摊 | 可以先求系统总账；“谁付钱”留到事后分摊 |
| 第 1520—1521 页 | 每家企业有一个车场和自己的车辆集合 \(K_i\)，车辆同型号 | 车辆有物理归属，但论文没有混合车队 |
| 第 1521 页 | \(Q_{ij}\) 是从车场 \(i\) 调到车场 \(j\) 的货量；\(y_{ijk}\) 表示车辆走车场—车场弧 | 原客户被别家车场配送时，货物应先发生实体移动 |
| 第 1521 页式（1） | 联盟目标同时计客户配送弧和车场间调货弧 | 调货不能只在求解后写一张里程表，应该影响路线选择 |
| 第 1521 页假设 2、第 1522 页式（5） | 车辆起终点为同一车场；调货弧满足流量平衡 | pilot07 的单向里程不是可执行路线 |
| 第 1522 页式（7） | \(Q_{ij}\) 由“原属 \(i\) 的客户改由 \(j\) 配送”的需求量汇总 | 当前 owner→serving 的货量方向与原文一致 |
| 第 1522 页式（8） | 调货车辆受容量约束 | 原文缺少承运覆盖和多趟拆分，无法直接用于当前大货量 |

补充事实：式（1）对客户配送弧使用 \(c_{ij}\)，对车场调货弧印为 \(d_{ij}\)；第 1521 页把前者定义为配送成本、后者定义为距离。论文没有给出柴油、电力、碳、固定出车费和充电的混合车队调货计价办法。

## 现有 E6 已经有的东西

1. **客户原属车场和实际配送车场。** `customer_home_depot` 保存原属车场，路线的 `home_depot_id` 给出实际配送车场；现有代码能够据此得到 owner→serving 货量（`run_pilot07_physical_transfer_ledger.py:65-77`）。

2. **四家联盟与各自车队上限。** 子联盟保留成员车场、成员客户、每个车场的柴油车/电动车上限以及道路矩阵（`e6_methods.py:34-92`）。路线重组也分别限制各车场、各车型的数量（`e6_methods.py:176-191`）。

3. **末端配送路线的完整成本。** 现有路线能够按车型、载重、道路剖面计算里程、柴油或电耗，并进入总成本（`solver/src/setp_solver/cost.py:282-335`）。

4. **联盟成本和事后分摊。** 15 个联盟、Shapley 和核检查已经存在（`e6_methods.py:25-147`）。这与 Rao 第 1520 页“先优化、后分摊”的顺序一致。

5. **直接送货场景的承包商账本。** 当前利润账把客户收入记给实际配送车场，把路线成本记给该路线的出发车场（`solver/src/setp_solver/profit.py:64-117`）。这是本项目已有业务规则，不是 Rao 2019 提供的规则。

## 现有 E6 缺少的东西

1. **解的数据结构没有调货任务。** `Solution` 只有配送 `Route`、充电动作和跨场客户标记；没有 \(Q_{ij}\)、调货趟次、每趟承运量或调货路线类别（`solver/src/setp_solver/solution.py:28-87`）。

2. **合法性检查明确禁止经过另一个车场。** 静态路线中间出现车场会被判错（`solver/src/setp_solver/check.py:551-587`），所以 `[广州车场, 深圳车场, 广州车场]` 不能作为现有合法路线。

3. **载重算法只会处理“从出发车场装好、沿客户顺序逐渐卸货”。** 它只把客户需求倒序累加，无法表达在车场装货、在另一车场卸货，也无法表达多批调货（`solver/src/setp_solver/cost.py:848-858`；`solver/src/setp_solver/check.py:590-627`）。如果把车场往返硬塞进普通 `Route`，能源计算会把车辆当空车。

4. **路线池只有带客户的末端配送路线。** 没有客户的路线会被丢弃（`route_pool_sp.py:441-479`）；E6 的整数规划只覆盖客户并计算已存在路线的成本（`e6_methods.py:168-206`），没有 Rao 的 \(Q\)、\(y\) 或货运守恒。

5. **当前 `cross_site_cost` 不是实体调货费。** 它只是“每个跨场客户一次固定金额”，总成本按跨场客户数量相乘（`solver/src/setp_solver/cost.py:192-206`），与货量、距离、趟次和车型都无关。

6. **配送车与调货车没有共享同一套车辆占用。** 若新增调货趟次，必须与末端配送路线共同占用现有各车场、各车型上限；pilot07 没有做这件事。

## pilot07 与 Rao 原模型的差别

pilot07 的 owner→serving 货量方向是对的，但它只是读取一个已经优化完的末端配送方案，再做物理账本，不会让调货代价反过来改变客户分配或配送路线。

| pilot07 做法 | 与 Rao 的差别 |
|---|---|
| 每个有货方向分别算 `ceil(货量/载重)` | 自行补了 Rao 缺失的多趟拆分，但没有形成车辆路线和承运量变量 |
| 同一批货分别计算“全柴油车”和“全电动车” | 这是两套边界账，不是算法在现有混合车队上选择车型；两者不能相加 |
| 报单向里程 | 违反 Rao 的车辆回到原车场要求，只能视为几何下限 |
| 报逐对闭环往返里程 | 强制每个方向单独往返，不能合并多个车场；且未检验车队数量、日程和续航，因此还不是经认证的可行上界 |
| 只计非能源里程费 | 没计固定出车费、柴油/电费、碳、充电、时间与车队占用，不是系统总成本 |
| 先固定配送方案再算账 | Rao 的式（1）意图是让配送与调货共同进入优化目标 |

当前账本的已核数字为：11 个有货方向、108 个跨场客户、28614 kg；柴油车和电动车口径都至少需要 22 趟。单向/闭环车公里为 1612.350/3224.775；只含非能源里程费时，柴油车为 1257.630/2515.325 元，电动车为 1080.270/2160.599 元。这些数字能说明调货不是零，但不能当作 Rao 联合模型的结果。

## “谁出车”和“谁付钱”要分开

**FACT：物理上哪辆车执行调货不能省略。** Rao 第 1521 页把车辆放在各企业的集合 \(K_i\) 中，并要求车辆回到同一车场。对本项目而言，调货车的出发车场、车型和数量可以由算法在现有上限内选择，不需要人为规定一个车型比例；这属于路线决策。

**FACT：会计上谁承担调货费可以暂时不决定。** 先把所有末端配送成本和调货成本加成联盟总成本，再求 15 个联盟成本并做 Shapley/核分摊，正是 Rao 第 1520 页的顺序。这个版本不需要收入，也不需要把某趟调货费先记到某家承包商头上。

**边界：这个系统总成本版本只能回答“合作总共省多少、事后怎样分摊成本”。** 如果还要回答“合作但不结算时哪家承包商亏了”，就必须把调货成本和收入落到具体承包商。Rao 2019 第 1520—1522 页没有规定：由原客户所属车场承担、由实际配送车场承担，还是由实际派车车场承担。三者是不同经营故事，不能由代码暗中替用户选。

## 真正需要审批的模型补全

在继续实体调货试算前，需要形成一份明确施工设计并由用户审批以下内容：

1. **承运覆盖和拆趟规则。** 每个 \(Q_{ij}\) 必须被调货趟次完整承运，并允许拆到多辆车或多趟；这是修复 Rao 式（5）、（8）之间的缺口。Rao 第 1521—1522 页只有 \(Q_{ij}\)、\(y_{ijk}\) 和单车容量，没有给出该规则。

2. **混合车队扩展。** 不设人为车型比例；算法在现有每车场柴油车/电动车上限内选择调货车，并与末端配送共用车队。Rao 第 1520—1521 页只写“同型号车辆”，所以车型、能源和充电是 China81 扩展，不是原文复现。

3. **调货路线形状。** “每个方向单独闭环往返”容易实现但会预先绑定出车车场，也不能合并多个车场；“允许一趟串联多个车场”更接近 Rao 的车场弧变量，但需要显式的逐弧装卸货量。二者会产生不同成本，不能偷偷二选一。

4. **只有在研究自然利润时才需要费用归属。** 可选语义为实际派车车场承担、原客户所属车场承担、实际配送车场承担。Rao 第 1520 页只提供系统成本后分摊，没有支持其中任何一种自然归属；不得为了制造亏损者选择。

## 本轮停止点

本轮完成 FACT 级缺口审计，没有修改求解器、检查器、成本器、算例或参数，没有运行新实验，也没有更新 `HANDOFF.md`。继续工作的正确下一步不是把 pilot07 的闭环里程塞进现有总成本，而是先把上述补全写成可逐条核验的实体调货数学模型；否则会得到形式上有数字、实际上没有承运约束的假结果。
