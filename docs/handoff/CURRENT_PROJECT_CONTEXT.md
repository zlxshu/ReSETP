### 算法

- 冻结的 PyVRP 0.12.2 HGS 只作对手，自研算法运行时、文件和控制流程与它分离，不替它优化，也不在运行时调用它。

- 公开与私有算例使用同一套串行控制流程。公开用普通路线适配器，私有用完整实体车整日任务适配器；不再维护几套互相割裂的外层循环。
- 不采用多视角、双分支、并行算法或多算法竞赛。活动算法只允许一条能解释、能画流程图、能逐项消融的串行改进链。
- v2 同款 28 个公开算例上，自研算法与冻结 HGS 使用相同 20 分钟上限、相同评价口径并完成全部客户与需求，目标是整体超过冻结 HGS。
- 私有算例中，能源、时变碳、车型、车场、实体车多趟、充电、动态状态、协同和公平必须真正进入同一套搜索、入群、生存和父代选择，而不是只在求解结束后补一次。
- 自研部件必须用消融证明有稳定增量。最终要稳定输出节点顺序、路线、车型、车场、充电安排，以及成本和排放分解。
- 半成品先用单个最小算例快速否决；只有核心机制站住，才逐步扩大到多种子、28 例和 20 分钟。不得让半吊子算法反复跑全量。

### 算例

- China81 是如实披露的构造仿真算例，不追求完整复刻现实，但可信度要达到目标期刊同类论文水平。
- 尽量选择或构造一个统一代表算例贯穿主要实验和机制分析；只有证明数学或物理上无法统一时才拆分。
- 统一算例首先要给三条主实验留下真实作用空间：
  - 时变碳强度能通过充电择时降低间接排放；
  - 混合车队能通过电动车替代燃油车，明显降低直接排放和总排放；
  - 动态需求能体现订单逐步到来、滚动重算相对机械静态配送的优势。
- 多车场、多趟、非线性充电、协同配送和公平分配要正确、合理、不拖后腿，并尽量产生容易解释的辅助效果。
- 算例允许调整，但必须先证明弱效应确实来自作用空间不足，并排除算法、模型、实现、评价和人为限制。调整依据与方案先交用户批准，再改生成器或参数。
- 所有构造依据、参数来源、失败和反例如实保留，不事后挑种子、挑参数或隐藏失败。

## 论文真正讲什么

`USER DECISION`：主线是时变电网碳强度、混合车队和动态需求。多车场、多趟、非线性充电、协同配送和公平分配是把问题做正确、做完整并支撑三条主线的结构，不自动升级成五个额外贡献。

算法和算例承担不同责任：公开性能不佳首先查算法；私有效应不佳要分别排查算法、算例作用空间、模型语义、实现接线、评价记账和人为限制。不能把所有失败都归到代码，也不能用算例或机制成绩替算法过关。

## 已经走过的路

1. 早期英国算例和 ALNS 路线已经退役。它们留下的方法、失败和数据只能作历史材料，旧预算、旧门槛和旧结论不得迁入当前 China81 主线。
2. China81 的 MV-HGS-SP 路线曾跑过大量技术与形式实验，但后来发现解的完成链存在根本缺陷：2520 次尝试没有产生真实完成，实际回退到初始解。相关结果不能证明当前算法或论文主张。
3. DCREX 有文献依据，也完成过实现和试跑；但它耗时高、稳定增量不足。用户已定为源码和证据保留、最终默认路径关闭。
4. 项目随后复制并剥离了成熟 HGS 底座，使新包不导入 PyVRP；等价核对表明复制底座能复现母体。它解决了独立运行问题，但本身不是创新，也不会自然超过母体。

7. 最终复盘确认：这些工作形成了“统一、可运行、可核账的底座”，但没有形成论文需要的核心算法突破。用户要求本轮写入交接、停止试错并告一段落。
