# 4. 逐案施工可行性攻击

不过，三案都不能按当前文字直接施工；方案一和方案三少写了物化契约，方案二低估了解码器。

方案一：风险比文档写的“大不了 30 秒停”更大。当前充电失败在 `charging.py:209–264、625–630` 和 `education.py:214–245` 已经是拒绝；调度物化还可能在 `search/multitrip_schedule.py:2473–2493` 因无可行充电窗口直接抛错。要让候选带着缺口进入惩罚池，至少要明确：如何生成一个可序列化的 best-effort `Solution`，缺失的充电窗口如何进入证书/旁路字段，`FullEvaluation` 如何计算缺口量，什么情况下只进入不可行池，什么情况下才允许成为可行最优。单独说“改非受保护的装配层”和“让 `check.py` 记违约”不够；`check.py` 本身不会把尚未物化的充电动作凭空变成可检查对象。另需补上 `multitrip_schedule.py` 和所有调用方的实际改动面。

方案一的“最快拿到效应”也没有证据。A2 现有两循环成本变化为 0、EV 使用为 0；新的 best-effort 适配可能增加序列化和完整评价时间。若惩罚流接受数为 0，不能自动跳到方案三，必须把升级作为用户可选的后续合同。

方案二：两篇论文支持的是 giant tour、Split/labeling 和多趟分隔的表示思想，不是本项目五项约束的现成解码器。HeuristicLab 官方教程也明确把 MultiTripEncoding 建在 CVRP、最大距离和兼容算子之上；它存的是车辆分配和趟次分隔，并不替本项目处理双仓、实体车辆身份、跨趟 SOC、充电窗口和项目的 ≤3 趟约束。

现有 `PhysicalVehicleDuty` 和 `from_solution` 只能在输入已经带有实体车辆/趟次/仓库/车型且连续性正确时恢复结构；giant tour + Split 的输出并不天然带这些字段。方案二施工前必须写死中间表示：客户顺序、趟次分隔、实体车辆绑定、归属仓库、车型、跨趟 SOC、充电动作重建和旧充电账本清理。尤其 ≤3 趟目前不是代码现成上限，必须由解码器显式限制。

方案二还把每个后代都交给解码、充电修复和完整评价。现有路径在 `integrated_private.py:493–566` 仍是修复失败即拒绝；方案二又把惩罚流关闭，等于要求解码器把每个进入评价的后代都修到可修复状态。A2 约 175 秒/循环、A1 超过 600 秒未返回，已经说明吞吐不是小风险；30 秒只能做早停检查，不能证明正式解码可行。文档还同时写“主表示”和“备份表示”，没有说明选择失败后是否自动切换；这也是施工合同未收口。

方案三：归因结构是三案中最清楚的——第一段检验“后代能否被接住”，第二段检验“交叉能否产生值得接住的后代”。但它继承方案一的 best-effort 物化未知，又叠加方案二的解码未知，因此“两个阶段各有完整退路”目前只能理解为诊断退路，不是已经证明的工程退路。第一段的固定“两循环/三种子”闸门要删；第一段是否继续、第二段是否开始，都应由证据和用户决定，不能自动升级。

# 5. 各案风险清单漏项

不过，三案现有风险清单都漏了同一组会直接改变结论的运行风险；必须逐案补上，不能只在方案三补。

共同漏项：

- 外置盘噪声：P43-K 已测得小文件写入外置盘约为内置盘 8.3 倍，UVFS/fskitd 还会占用 90%–150% CPU；不同批次墙钟不可比，正式比较要同批、同盘状态、无无关重负载。
- M1 内存：8 GB 机器在既有批次只剩约 57–67 MB 空闲；“8 路×3 种子×120 秒”曾静默被杀。三案都必须写低并发、单批探针和进程退出识别，不能把并发探测当默认加速。
- 175 秒/循环：A2 约两主循环用 349.747 秒，即约 175 秒/循环；120 秒方向探针可能连一个完整循环都没有，不能据此判定“死亡”或“有效”。A1 超过 600 秒未返回也要保留为风险。
- 正式种子数未定：P06 仍开放，所有“3 种子”“精确 p 值”和“配对确认”都只能是候选设计，不是已决门槛。
- 28 题多种子机时：在用户给定每题每臂 20 分钟上限下，单臂为 28×S×20 分钟；S=3 时约 28 小时，成对比较至少约 56 小时，还没算三个公共方法、写盘和重跑。这是资源估算，不是正式结果，但必须让用户在选案时看见。

方案一还缺：best-effort 对象的内存/序列化成本、缺口证书在人口清理和惩罚更新中的生命周期、`multitrip_schedule.py` 的异常路径、零接受数时是否停、以及企业归属映射是否真正进入路线和评价。

方案二还缺：解码器的最坏候选吞吐、失败后是否能安全回到 B0、实体车辆和趟次编码的唯一性、旧充电账本删除后的成本一致性、≤3 趟约束、双仓归属转换、表示主备切换的公平预算，以及解码器是否会把公共侧和私有侧算法偷偷变成不同预算。

方案三还缺：阶段间是否复用同一批输入/种子/预算、第一段输出是否成为第二段的先验、阶段增量的独立分母、第一段结束后的用户确认点、两阶段累计墙钟、以及第一段已经改变评价链后第二段还能否和 B0 公平配对。

动态部分还缺一项合同：P41 允许外包并计入服务账，但外包价格来源、单位、最低收费、里程/重量规则和排放口径仍未定；方案中写“outsource cost”不能代替这些输入。动态事件流也仍是设计合同，不是已冻结的数据产物。

# 6. 对“推荐方案三”的反向攻击

改

方案三可以作为“归因最清楚”的候选，但“三个死点是三种病，因此最不容易失败”目前站不住。证据只支持三个失败位置，不支持三种相互独立的病因：

- 62.3% 预筛拒绝说明候选生成/体积与班次过滤有一个瓶颈。
- 63/63 交叉后 `NO_FEASIBLE_WINDOW` 说明交叉子代经过现有修复链时全部在充电窗口处死亡。
- 这两项来自同一套表示、同一套修复和同一套评价链；没有因子化实验把“候选本身坏”“修复把候选丢掉”“充电账本/时窗检查错误”彼此分开。因此不能把“交叉制造坏孩子”和“修复丢孩子”直接宣布为两种独立疾病。

更准确的标题应是“三个可观测失败位置”或“至少三个候选瓶颈”。方案三的真正强点是阶段化归因：先固定第一段，再把第二段的增量单独测出来。它的弱点是总工程量最大，且第一段适配层和第二段解码器都未证明可行；“第一段最快得到效应”“最不容易失败”都应降级为代理推断。

当前没有证据足以把方案一或方案二改成更强的总推荐：方案一实现面较小但不能证明最快，方案二故事最强但解码风险最高，方案三归因最好但总工期最长。因此可以保留方案三作为代理建议，但推荐理由必须改成“最利于把两个改动的增量分开归因”，不能写成“三种病已经被证明”。最终三选一仍是用户决定。
