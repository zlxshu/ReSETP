## 二、我的病灶判断（`INFERENCE`，读码得出，请打）

### 判断 1：标签淘汰被按"最后一刀切在哪"分了组，组间永不淘汰

`FACT`（代码）：`hybrid_decoder.py:688-722` 的 `_prune_split_labels`：

```python
by_last_start.setdefault(int(label.last_segment_start), []).append(label)
for group in by_last_start.values():
    ...  # 只在组内做 (last_return_second, total_drive_energy_kwh) 二维帕累托淘汰
```

`FACT`（代码注释给的动机）：「不同的最后一段起点是不同的路线边界，不能被另一边界的标签
时间支配，否则等于**偷偷替你选了分隔点**，而不是让可行性自己去选。」
`INFERENCE`（我）：动机对（它落实 P67-3「切点归 Split 一个负责人」），
但代价是——**块长 L 就有最多 L 个组，每组各留一条前沿**，标签总数下界约 O(L × 前沿宽度)。

### 判断 2：淘汰本身是平方级

`FACT`（代码）：`:707` 的 `dominated = any(... for existing in local)`——
每个候选对已留集合做线性扫描，故单组淘汰是 O(k²)。
`INFERENCE`：**标签数增长 × 淘汰平方**＝双重复利，与实测 347 倍量级相容。

### 判断 3：算法层面已经没有任何枚举边界

`FACT`（`:400-406` 文档注释原文）：
「The only finite enumeration boundary is that every extension consumes at least one customer
and the customer permutation is finite. Labels are removed only by time/energy dominance
at the same permutation position. No label is removed because a vehicle has accumulated
a particular number of trips.」
`INFERENCE`：唯一的界是"客户数有限"。而"不按趟数删标签"来自 **P69（用户决定，禁止任何趟数计数上限）**
——那条**建模上是对的**，但它顺手拆掉了算法里的另一个界。

### 判断 4：为什么"越往后越贵"

`INFERENCE`（我最不确定的一条，最需要你用数据裁）：搜索早期解松散，
时间和电量都离上限远，一个标签容易支配掉一片；搜索后期解被压得紧，
时间与电量互相权衡（省时费电／费时省电），**帕累托前沿上的标签互不支配**，前沿变宽 → 爆炸。
若成立，则爆炸是**"解变好"的副产品**，越接近收敛越严重——这对我们是最坏的形态。

## 三、我倾向的方向（`DECISION`，非用户决定，请打）

**修法不该动模型**：趟数上限该不设还是不设（P69 是用户决定，且建模上正确）。
要加的是**算法层面的界**。候选（我想到的，你必然有我没想到的）：

1. **把"切点"纳入统一淘汰**：不再按 `last_segment_start` 分组，而是把它当成标签的一个维度，
   用文献的标准做法处理。**风险**：可能真的会"替 Split 选切点"，违反 P67-3 分工——**这条请你重点判**。

3. **把破坏支配性质的约束移出 Split**，切完再修（充电与 SOC 本来就归后续重建管）。
4. **按 P82 让它在该休眠时休眠**：公开侧自研件本就该冻结；长跑取收敛曲线时是否也该关，
   属实验设计问题。**这条是"更高维度"的最省解，但它回避而非根除问题。**
