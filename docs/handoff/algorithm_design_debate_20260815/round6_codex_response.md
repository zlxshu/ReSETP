# 第六轮：发动机调校联合设计

## 0. 本轮边界

**USER DECISION（2026-08-16）**：C9 从“被动等瓶颈”改为“主动调校”。私有赛道固定、公开赛道按题族公开披露；本轮是平级联合设计，不是执行派工。

**DECISION（Codex 建议）**：本轮只冻结调校设计，不冻结任何新参数值，不改代码、不改算例、不跑求解器，不使用旧的 `china81_finite_fleet_authority`。正在运行的收敛探针仍是独占现场；它的中途读数不在本轮当作正式结果。

当前工作树在本轮开始前已有其他未提交改动。本轮只新增本文件；其余改动均保留，不把它们当作本轮成果。

## 1. 先给结论

Claude 的五项候选中，前四项不能原样平推：

1. **罚分窗口：保留，而且列为第一优先级；但按“每类罚分登记次数”调，不按循环次数调。** 当前 `solutions_between_updates=50` 的确可能在短探针内只记录几次、一次更新都没有；这证明“当前窗口在当前运行长度下不可观察”，还没有证明“50 一定错误”或“罚分是全部病因”。
2. **邻域粒度：保留，但拆成两个不同参数。** 路径搜索的 `num_neighbours`/旧称 `nb_granular` 是邻域宽度；种群的 `num_close=5` 是多样性距离参数，不能混调、不能互相代称。
3. **种群规模 μ/λ：保留，按成对规模调。** `25/40` 是 HGS 家族的复制起点，不是本项目已经证明的最优值。
4. **“停滞重启”：暂不作为当前调校项。** 当前私有 runner 没有配置重启；`stagnation_patience=500` 是无改进停止耐心，不是重启周期。把它叫“重启节奏”会改变问题含义。
5. **OFAT 与小型阵列：不选极端。** Codex 建议“先做小型筛选阵列，再对入选因素做少量逐个确认”；不要直接做全因子，也不要把所有东西排成长长的单因素队列。

**DECISION（Codex 建议）**：第一阶段只把四个主要因素放进小型筛选：罚分窗口 `U`、路径邻域宽度、成对种群规模、`num_close`。罚分响应参数、`num_elite` 放第二阶段确认；停止策略不进入同预算质量筛选。

## 2. 逐条裁断 Claude 清单，并补充候选

### 2.1 罚分自适应窗口：接受问题，修正单位和判读

**FACT**：`AdaptivePenaltyManager.register()` 每次接收一个评价结果，按违反类型分别把可行/不可行状态放进长度为 `solutions_between_updates` 的窗口；窗口满后才计算可行比例、调整罚分并清空历史（`solver/src/setp_solver/algorithms/problem_hgs/population.py:139-184`）。

**FACT**：当前复制值是 `solutions_between_updates=50`；round2 的诊断记录了 3 次登记、0 次更新，最终时间窗罚分仍为 100（`docs/handoff/algorithm_design_debate_20260815/round2_codex_response.md:52-58`；`solver/reports/diag_violation_types_20260816/metadata.json:189-198`、`best_solution.json:811-815`）。round6 交底记录的另一轮是 4 次登记、0 次更新（`docs/handoff/algorithm_design_debate_20260815/round6_claude_position.md:14-17`；当前事实源 C9）。

**裁断**：Claude 的“窗口与实际注册节奏匹配”是正确方向，但“每循环 3–4 个解”只能作为观测，不应直接换算成窗口值。真正的调节单位是**某一罚分类型收到的登记次数**；不同类型可能登记频率不同，不能用总循环数替代。

**新增候选**：窗口之外，把 `target_feasible`、`feasibility_tolerance` 和增减乘数视为一个“罚分响应束”做后续确认。否则只改窗口，可能把“更新得更勤”误判成“罚分方向更正确”。第一轮仍固定复制的响应束，只筛窗口；这样能保留归因。

**候选档位（DECISION，非冻结值）**：以当前 50 为中心，可先讨论 `U∈{20,50,100}`。这三个数只是小型设计的候选水平，不是合格线；最终档位应由收敛探针能覆盖的登记量和预算决定。若某档在预算内根本没有更新，结果应保留为“未观察到更新”，不能事后删掉。

### 2.2 邻域粒度：接受，但必须拆开

**FACT**：官方 PyVRP 0.12 系列的搜索邻域有 `num_neighbours=40`；官方旧版文档把同一概念称为 `nb_granular`，定义为每个客户保留的邻居数。当前项目私有提案引擎在构造时创建默认 `SolveParams()`，然后计算邻域；现有入口没有把该参数作为私有调校接口公开（`solver/src/setp_solver/algorithms/problem_hgs/kernel_proposals.py:131-140`）。

**FACT**：本地 `PopulationParameters.num_close=5` 只用于种群中“最近解”的距离/多样性计算（`solver/src/setp_solver/algorithms/problem_hgs/population.py:326-350`、`402-434`），不是路径搜索的客户邻域宽度。

**裁断**：保留“邻域粒度”这个研究问题，名称改为两行：

- **路径邻域宽度**：`num_neighbours`/`nb_granular`；需要先确认私有 kernel 入口是否已经可配置。当前它是设计候选，不是现成可直接填写的参数。
- **种群近邻数**：`num_close`；这是多样性参数，当前值 5，可单独调。

**新增观测**：每次搜索要记录“理论邻居数、经过班次/重建过滤后的有效邻居数、实际评价数、被接受的移动数、按班次的拒绝原因”。否则只看最终成本，不知道调窄后是减少了无效搜索，还是误删了有效跨班次移动。

**候选档位（DECISION，非冻结值）**：路径邻域可讨论 `20/40/60`，`num_close` 可讨论 `3/5/8`。这只是低/当前/高的候选中心，不能在没有接线验证前写成正式参数。

### 2.3 种群规模 μ/λ：接受成对调，不拆成两个孤立旋钮

**FACT**：本地 `copied_hgs_defaults()` 复制的是 μ=`min_pop_size=25`、λ=`generation_size=40`、`num_elite=4`、`num_close=5`，多样性界限为 0.1/0.5（`solver/src/setp_solver/algorithms/problem_hgs/population.py:35-71`）。PyVRP 0.12.0 官方文档给出同一组 PopulationParams 默认结构；Vidal HGS-CVRP 官方仓库也列出 μ=25、λ=40，但其 `nbElite`/`nbClose` 版本值不同，不能把不同实现的整组默认值混成一套。

**裁断**：μ、λ 先按成对规模调，保留大致相同的 λ/μ 比例；不要只增大 λ 再宣称“种群更强”。

**候选档位（DECISION，非冻结值）**：可以讨论 `(15,24)/(25,40)/(35,56)` 这类低/当前/高成对档位。这里的数是围绕复制值的设计示例，最终是否采用、是否按本机预算缩放，仍需用户批准及本地探针依据。

**必须测的不是“代数”**：同一墙钟预算下的产生子代数、评价数、登记数、可行池比例、种群多样性、最佳可行目标、每代耗时和最终服务客户/需求量。只报“跑了多少代”会把不同规模的每代成本藏起来。

### 2.4 停滞重启：否决原命名，保留一个较窄的审计问题

**FACT**：当前 runner 在无改进超过 `stagnation_patience` 时终止，终止状态为 `CONVERGED_NO_IMPROVEMENT`；传给 `HGSControl` 的 `restart_after_iterations_without_improvement=None`，当前适配器没有打开重启（`solver/src/setp_solver/algorithms/problem_hgs/runner.py:707-720`）。

**裁断**：本轮不把它写成“重启节奏调校”。如果把停止耐心改成质量调校，实际是在改变停止策略和有效预算；如果新增重启，则是搜索架构变化，不是普通参数调校。两者都不应混进第一阶段阵列。

**可保留的窄问题**：记录当前无改进停止是否在统一墙钟预算之前触发，以及停止时是否仍有真实搜索进展。这个记录用于解释异常，不作为“重启效果”结论。若以后要研究真正重启，需另开一个用户批准的算法设计问题。

### 2.5 Claude 的 OFAT/阵列问题：接受混合路线

**裁断**：纯 OFAT 能看清单因素，但在本题中会漏掉 `U×登记速率`、`邻域宽度×种群规模` 等交互；全因子又把成本推高。建议采用“L8 式小型筛选阵列 + 关键因素确认”，而不是在本轮替用户冻结一个完整试验矩阵。

### 2.6 新增候选清单

**候选 A：罚分响应束。** 在窗口筛选后，单独确认目标可行比例、容差、增罚/减罚乘数；原因是窗口解决“何时调”，响应束决定“调多大”。

**候选 B：有效邻域而非名义邻域。** 把 `num_neighbours` 与过滤后有效邻居数同时报告；原因是本题存在班次/重建过滤，名义 40 不等于实际 40。

**候选 C：`num_elite`。** 作为种群规模筛选后的低优先级确认因素。金东遥 2024 的体裁记录显示，参数敏感性可以单独考察 `nElite`、`nClosest`，但这属于参数敏感性，不是组件消融；当前 `num_elite=4` 是复制值，不是本项目的科学结论。

**候选 D：不把初始解组件、复合移动、算子组合塞进 C9。** 它们会改变算法组件或问题机制的归因，应留在各自的独立消融臂；不能用发动机参数调校替它们过门。

## 3. “逐个调”与“小型标定阵列”怎么选

| 方案 | 怎么做 | 好处 | 代价与盲点 | 本轮判断 |
|---|---|---|---|---|
| 逐个调（OFAT） | 复制基线固定，其余因素不动，每次只改一个因素的低/当前/高档 | 归因直观，容易画敏感性曲线；适合确认单个因素 | 忽略交互；四个主因素做三档至少要 1+2×4=9 个配置，还要补交互确认；容易把窗口效果和登记速率混淆 | 适合作为第二阶段确认，不适合作为唯一首轮 |
| 小型二水平阵列 | 四个主因素各取低/当前附近和高/当前附近，做 8 个预先写定的组合 | 比全因子省配置数；可以同时看主要方向和一部分交互线索 | 交互会混杂；不能把 8 个结果写成完整参数定理；每个配置仍须同预算、同种子对照 | 第一阶段建议采用 |
| 全因子 | 4 因素×2 水平为 16 个，4 因素×3 水平为 81 个 | 交互最完整 | 时间、算力和当前探针现场都不允许；容易把设计阶段膨胀成另一轮大实验 | 本轮不采用 |

**DECISION（Codex 建议的两阶段设计）**：

1. **阶段一：小型筛选。** 只放 `U`、路径邻域宽度、成对 μ/λ、`num_close` 四个因素；先用 8 个预注册组合看主要方向、登记/更新是否可观察、有效邻域和每墙钟产出。`num_elite`、罚分响应束、停止策略固定不动。
2. **阶段二：确认。** 对阶段一留下的少量候选，逐个确认 `U`、`num_elite`、罚分响应束和最重要的邻域/种群交互。确认时仍保留复制默认对照和全部失败/超时记录。
3. **共同预算。** 所有配置使用同一输入、同一硬件、同一墙钟/评价预算、同一初始解合同和同一随机种子配对；预算数值由本算法、本算例、本机收敛资料另行标定，本文件不替它设定。
4. **选型规则。** 事先写清主目标、次目标、可行性和服务量的报告顺序；不以单个最好种子、不以单个案例、不以少服务客户换来的成本下降选配置。没有用户批准，不新增硬阈值或“必须改善多少”的门槛。

**代价判断（INFERENCE）**：小型阵列的直接成本未必比 OFAT 低很多，因为每个配置仍要完整跑同预算；它真正节省的是避免先做一长串单因素、最后才发现交互改变排序。代价是解释力下降，因此必须安排第二阶段确认，且不能把筛选阵列当成正式最终结果。

| 调什么 | 依据 | 怎么测 | 验收对照 | 风险 |
|---|---|---|---|---|

| 无改进停止耐心 `stagnation_patience` | 当前它触发停止，不是重启；`restart_after...=None` | 仅记录何时停止、停止前后真实评价进展和剩余墙钟；不作为第一阶段质量因素 | 同一硬墙钟/评价预算下作为解释变量报告；如改变它，必须说明有效预算是否变化 | 把停止提前会制造假收敛；新增真正重启会改变算法架构和归因，本轮不做 |
| 公开赛道题族 profile | C9 要求按族调校、整族披露，不许一题一参数；公开题族 A/B 的定义需在结果前冻结 | 先冻结族定义、候选档、选择规则和 profile ID；每族得到一组参数，所有该族实例/种子复用；记录全配置结果 | 与本方法复制默认 profile、以及基线各自公开/复现设置对照；同时报客户数、需求量、超时/失败和硬件版本 | 用最终成绩反复挑族定义会造成泄漏；族内异质性会让一组参数掩盖子族差异；调过的赛道不能写成盲测泛化 |

## 5. 公开赛道按族调校：建议的披露格式

### 5.1 先定“调过什么”，再定“调出了什么”

**DECISION（Codex 建议）**：公开赛道至少保留两层记录。

**主文一行一族：**

| 字段 | 内容 |
|---|---|
| `family_id` | A/B 或经过用户批准的族名；定义在看到最终成绩前冻结 |
| `family_definition` | 只写输入特征和范围，例如时间窗紧度、班次结构、客户规模；不按结果倒推族 |
| `n_instances` | 族内题数；不隐藏少数题族 |
| `profile_id` | 该族唯一参数配置编号；同族不允许一题一参数 |
| `parameter_vector` | `U`、邻域宽度、μ/λ、`num_close`、`num_elite`、罚分响应束和停止策略；区分复制值与调校值 |
| `selection_protocol` | 候选档位、种子、预算、主/次比较口径、是否使用留出题 |
| `tuning_scope` | `family-calibrated`、`all-family-adapted` 或其他经批准口径；明确是否用过最终评价题 |
| `final_protocol` | 最终运行的统一时间/评价预算、种子、机器、代码版本和保护文件哈希 |
| `service_completeness` | 完成客户数/总客户数、完成需求量/总需求量；成本下降不能来自少服务 |
| `comparison_summary` | 同预算下相对复制 profile 和各基线的均值/中位数、离散度、胜/平/负和失败/超时 |

### 5.2 补充材料必须留全试过的配置

**FACT**：金东遥 2024 的体裁记录显示，参数集中说明复制值，并把 `nElite`、`nClosest` 单独做敏感性曲线；实验部分区分参数敏感性与组件贡献，报告重复运行的统计量（`docs/handoff/algorithm_chapter_genre_standard_20260816.md:162-172`；其记录的原文页码为算法 pp.2535、敏感性 pp.2539）。

因此建议补充材料或结果包再加一张“配置长表”：

`family_id, profile_id, candidate_level, full_parameter_vector, seed, budget, best_feasible_F, Phi, feasible_share, penalty_updates_by_type, effective_neighbours, population_stats, customers_served, demand_served, timeout/failure, artifact_hash`。

主文可以只放族级汇总；补充材料不能只放选中的最好配置。敏感性曲线用于说明“参数怎么影响结果”，不能被写成“该参数本身是算法组件贡献”。

### 5.3 族级调校的两种公开口径

这是需要用户在正式实验合同中选择的口径，不在本轮替用户拍板：

| 口径 | 做法 | 优点 | 代价 |
|---|---|---|---|
| `family-calibrated + holdout` | 每族先按预先规则分校准题/留出题；profile 只由校准题确定，再在留出题报告 | 对“族级可迁移”更有说服力 | 每族可用题数变少，调校效应和统计稳定性下降 |
| `all-family-adapted benchmark` | 固定题族上的全部题都参与调校和最终报告 | 充分利用固定公开赛道，适合明确宣称“针对该赛道适配” | 不能把同一批题上的优势写成未见题泛化；必须完整披露调校范围 |

无论选哪种，不能出现“先看每题结果、再给每题单独参数”的隐性口径。若族内题数太少，结论标为 `UNKNOWN` 或探索性记录，不用另一族结果补齐。
