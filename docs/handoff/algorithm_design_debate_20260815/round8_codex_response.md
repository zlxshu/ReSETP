**Codex 平级答复｜2026-08-16**

## 先给裁断

我的结论不是在甲和“前 k 名乙”之间二选一，而是把乙的名字先说准确：

1. **甲“安全缓存”是值得先做的安全层，但它不是目的本身。** 它有机会把同一搜索状态下的重复充电候选、择时和评分复用掉，并保持终解逐位一致；但目前的 `20–50 s` 是热子树预算，不是已经测得的端到端收益，`2–3 倍圈数`也还是估计。只凭圈数，不能说公开表会赢。
2. **乙若等于“便宜排序后只精确修前 k 名”，我不建议做。** 这会丢候选，改变搜索语义；而且当前 `charging_prescreen` 不是成本下界，不能直接升级成这样的排序器。它最多是“近似截断评价”，不是“惰性精确修复”。
3. **乙若改成“可证明的乐观下界 + 不能被下界淘汰的候选全部精确评价”，在原理上可行。** 这才是文献意义上的惰性精确评价。不过当前代码没有现成的候选下界接口，必须把候选描述、下界、当前最好值和精确兜底接起来；这已经是语义敏感的算法施工，不是甲的机械缓存。
4. **我的第三条路（代理建议）是：甲先落地，再做带自动回退的下界分支定界。** 缓存负责消除重复工作；下界只负责安全剪枝；界不成立或算不出来，就退回原来的全候选精确评价。这样把“速度收益”和“候选不漏”分开验证。

最直白的一句话：**只做甲，可能足以让动态滚动开始有动作，但还不能证明公开表有竞争力；做前 k 名乙，风险不值得；真正值得研究的是“精确缓存 + 证明下界”，而不是“精确修前 k 名”。**

## 甲：安全缓存——我同意先做，但不把它说成最终答案

## 乙问题一：当前结构能不能直接做“惰性精确修复”？

### 对“前 k 名乙”的回答：可以施工，但不叫精确，也不值得现在施工

若做法是：用一个便宜近似分数排序，只对前 `k` 个候选做 `_repair_one_ev_duty` 和整日评价，其余候选永远不精确评价，那么：

- 它确实能把每轮充电修复从约数百次降到个位数；
- 它也确实会改变候选入围顺序和最终接受路径；
- 它可能把一个近似分数偏低、但精确充电后很好的候选截掉。

因此这是**候选截断算法**，不是惰性精确算法。没有额外证据时，不能把“前 k 名后的最好解”写成“不劣”。

### 对“有证明下界的乙”的回答：原理上可行，但当前没有现成接口

严格的惰性精确评价需要一个候选级下界 `L(c)`，满足最小化问题的：

```text
对每个候选 c，L(c) <= 精确目标 F(c)
```

当前最好精确值记为 `B`。只有当 `L(c)` 已经证明候选不可能击败 `B` 时，才允许跳过精确评价；否则必须进入原精确修复。并列情况还要保留原来的候选索引和裁决顺序，不能把“等于当前最好”随意剪掉。

在当前代码里，这个接口还不存在，原因有三层：

1. 候选是在 `repair_route_charging_candidates` 内部逐个生成并精确修复的，外部拿不到一个“候选描述 + 未闭合状态”的对象；
2. `route_model_cost_delta` 是对已修复候选的精确路线评分，不是 bound；
3. `_rebuild_ev_duty` 之后才做车场锚定、择时和整日账本复核，单段路线的乐观值不能自动成为整日目标的乐观值。

因此对问题①的明确回答是：**乙在架构上可行，但不能把当前预筛器直接升级为可用乐观界；需要新增候选描述和 bound 计算层，再由 incumbent-aware 的精确评价循环兜底。** 这只是设计判断，不是本轮施工授权。

## 乙问题二：乐观界怎么定，才不会系统性漏好候选？

### 文献里标准的安全做法

`FACT`：Visser 和 Spliet 对时间依赖 VRP 的加速总结，把快速预检查、预计算、成本下界和延迟更新放在同一个“减少不必要精确评价”的框架里。其核心不是“只看前 k 个”，而是：先用容量、非时间依赖的时间窗条件和成本下界筛掉已不可能改善当前最好值的动作；只有通过这些检查的动作才做精确可行性和成本计算。见作者 PDF **pp.2, 12, 15–16**，尤其 p.15 的 cost lower bound 和 p.16 对 bound 强弱与精确评价次数的关系。原文与期刊 DOI 见文末参考文献 [1]。

`FACT`：Froger 等人的电动车路径研究给了更接近本项目的例子：其 SMD 邻域为动作保存成本标签，并在有可用下界时先用下界；当路线能量超出容量时加入充电绕行/充电时长的下界；近似标签不能证明安全时，仍要做精确第二步。作者稿 **pp.25–27，Algorithm 6** 体现的就是“下界排队 + 必要时精确评价”，而不是固定前 k 截断。最终期刊版本为 *Transportation Science* 56(2):460–482。见文末参考文献 [2]。

`FACT`：Vidal 的 HGS-SWAP* 工作也把“避免重复 move evaluation”的数据结构和几何剪枝作为速度来源，但速度收益建立在候选信息可复用、剪枝条件有依据的前提上，不是把结果好的候选数人为缩成 k 个。见作者 PDF **pp.1–2**，文末参考文献 [3]。

### 应用到本项目，界只能从“放松”得到

`DECISION`：如果继续研究下界，我建议按以下形式审计，而不是现在拍一个公式：

1. 对每个候选路线，先计算一个忽略部分约束的最小可能行驶/能耗成本；忽略的绕行、等待、充电占用和时间耦合只能让这个值更低，不能让它更高。
2. 对充电，允许在放松空间中使用理论上最便宜、最早或最有利的充电位置和时间；但必须明确哪些省掉的费用/排放/等待项本来非负，哪些目标项可能为负或受全局配额影响。
3. 对整日 Duty，界必须覆盖车场锚定、跨趟连续时间、锁定充电会话和最终账本；如果只算单趟路线，不足以作为整日目标的安全下界。
4. 任何不能证明 `L(c) <= F(c)` 的部分都不能放进“安全剪枝”；它最多只能作为候选处理顺序。顺序可以加速，但不能据此丢掉后面的候选。
5. bound 计算失败、输入类型未知、动态状态存在或精度边界不清时，自动回到原来的精确评价，而不是猜一个界继续剪枝。

当前可以看出一个可用的研究方向，但还不能声称已经有了可用界：`repair_scoring.py:41-69` 的 route-level 评分明确使用了 quota-neutral 的评价上下文，而最终 search 评价在受保护的 `cost.py`/`check.py` 路径上完成（`solver/src/setp_solver/search/evaluation.py:1-6,87-120`）。这意味着“把未充电路线成本当作整个最终目标的下界”至少还缺全局目标和罚分项审计，不能在本轮凭直觉定成安全公式。

### 我否定一个很诱人的捷径

`HALT`：不能用“候选精确分数的历史均值/最近一次分数/route-only 分数”直接做系统性剪枝。理由不是它可能不够漂亮，而是它没有给出上界或下界关系；只要存在一个充电择时、整日锚定或碳价项使近似排序反转，前 k 就会漏好候选。

## 乙问题三：怎样验收“解质量不劣”？

这里必须把两种目标分开：**缓存要验语义等价；下界惰性要验不漏候选；公开表还要验有限墙钟下的解质量。** 一套指标不能包办三件事。

### 第一层：精确缓存的逐位复现

`DECISION`：甲先做如下固定状态回放，不能一上来跑公开全表：

- 同一实例、同一输入个体、同一 seed、同一 proposal stream；
- 原路径与 cache 路径都完成同一轮 `evaluate_move`；
- 比较候选列表及其顺序、每个候选的接受/拒绝状态、异常类型和消息、完整 repaired Duty、择时结果、`penalized_cost`、被选 action id 和最终 individual/evaluation fingerprint；
- 同时核对客户数、需求量、可行性和违规数。

只要 cache 版本改变候选顺序、拒绝原因或最终 fingerprint，就不能把它称作纯提速。P76-1 已把“终解逐位一致”列为提速铁条：`docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:1157-1176`。

### 第二层：下界版本的“不漏”证明

对每个候选保存：

```text
candidate_index
lower_bound
incumbent_before_exact_eval
pruned_or_exact
exact_value（若做了精确评价）
prune_reason
```

验收要回答四个问题：

1. 所有被剪掉的候选是否满足下界安全关系；
2. 所有没有被下界证明淘汰的候选是否都精确评价；
3. 采用原 tie-break 后，每个 `evaluate_move` 选出的候选是否与原路径一致；
4. 若任何候选的 bound 计算失败，是否真的走了精确回退。

若这四条成立，固定 proposal state 下应当得到与原路径相同的候选选择；若没有相同，就说明它不是纯提速，必须按新语义算法做第三层质量实验。

### 第三层：公开质量和动态效应

`DECISION`：正式质量对照应采用两步：

1. **同 seed、同实例、同墙钟的配对多次对照**：这是回答“速度改变了有限预算下的搜索结果”所必需的主口径。现行项目决定是净 M1、同墙钟，并保留时间列，固定循环数口径已经废除；见 `docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:219-228`；预算由收敛曲线决定，见同文件 `:249-257`。
2. **固定圈数只作辅助诊断**：它能回答“每一圈的语义是否一致、每圈耗时省了多少”，但不能代替同墙钟质量比较，因为提速的目的正是让同一墙钟里完成更多圈。

“多次”所需的 seed 数量按项目已有正式协议冻结，不能在这一轮新造一个数字。单 seed 不能支撑“不劣”：P73 已记录同一配置 seed 11 到 seed 3 的波动约 `8.8%`，大于若干配置差异（`docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:1037-1060`）。

`FACT`：公开正式主表的对手口径是已发表方法，不是把冻结开源 HGS 放进正式表；现行登记见 `docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:230-233`。所以公开验收至少要保持同一实例、同一评价器、同一墙钟、完整服务量和需求量，并同时报告成本、碳排和必要分项，不能只比较最好成本。

## 目的性裁断：提速到底服务哪张表？

### 公开对比表：甲是必要准备，不是“够赢”的证据

`FACT`：当前八行图表中，公开对比表是直接消费算法相对强度的一行；其他机制行已有可产出数据，但其正式多种子、同预算和作用条件仍需按各自合同复核。P76-1 也明确指出速度异常同时卡住公开对比和动态预算；准确证据入口是 `docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:1157-1176`、`docs/handoff/CURRENT_PROJECT_CONTEXT.md:226-250` 和 `docs/handoff/CURRENT_PROJECT_CONTEXT.md:1178-1200`。

`INFERENCE`：如果目的只是“让公开表有机会赢”，甲够不够，当前答案是：**不够知道，更不能提前说够。** 甲的价值在于先消除一个审稿人一眼能抓到的重复计算病灶；但公开表最后看的是固定墙钟、多 seed、同一比较对象下的解质量，不是圈数。

`DECISION`：乙的语义风险是否值得冒，分两种：

| 乙的具体形态 | 对公开表的判断 |
|---|---|
| 近似分数 + 固定前 k 个精确 | 不值得。它可能直接丢掉公开表需要的好解，而且没有安全证明。 |
| admissible lower bound + 未被证明淘汰者全部精确 + 失败回退 | 值得作为甲之后的研究方向；若固定状态能逐位等价，风险可控；若不能，则按新算法做正式对照。 |

### 动态实验：甲有条件地能让滚动臂“转起来”，但要看端到端收益

`FACT`：现有 900 秒记录是每圈约 `90–150 s`（6–10 圈）；项目当前也已经记录“小决策预算可能只做 0–1 圈”的风险，见 `docs/paper_gci_dmm_vrp_20260804/pending_decisions.md:1151-1155`。

按这个区间做纯算术：

| 单决策预算 | 当前 90–150 s/圈 | 若端到端 2 倍提速（45–75 s/圈） | 若端到端 3 倍提速（30–50 s/圈） |
|---:|---:|---:|---:|
| 120 s | 0.8–1.3 圈 | 1.6–2.7 圈 | 2.4–4.0 圈 |
| 180 s | 1.2–2.0 圈 | 2.4–4.0 圈 | 3.6–6.0 圈 |

`INFERENCE`：如果动态触发窗口只有 120–180 秒，甲达到真正的 2–3 倍端到端提速，滚动臂就从“最多一圈”进入“有两圈上下完整重优化”的区间，确实可能改变效应是否可见。若甲只节省热子树而没有达到端到端 2 倍，不能把上表的条件数字当成结果。

`UNKNOWN`：甲是否能达到 2 倍、3 倍，当前没有证据。`20–50 s` 的热子树预算不能直接换算成端到端倍数；还要扣除候选生成之外的教育、完整评价、路线层解码和其他固定成本。故动态实验可以把甲列为高价值准备，但不能先把触发预算定死成某个数字；预算仍应按 M1 的实际收敛/圈数曲线标定，P47 已明确预算不能拍脑袋。

这也回答了“提速到底为哪张表服务”：**第一消费者是公开对比表的有限墙钟搜索强度，第二消费者是动态实验每个决策点是否有足够重优化；不是为了把 profile 表上的百分比做得好看。**

## 丙：我自己的第三条路

### “精确缓存 + 可证下界分支定界 + 不确定时回退全精确”

这是我的 `DECISION` 建议，不是用户决定，也不是本轮施工授权。

它的逻辑是：

1. **先做甲**：把路线候选列表、择时上下文和完全相同输入的精确结果缓存起来；固定状态逐位一致后，才进入下一层。
2. **每个候选先拿便宜下界**：下界只允许来自放松约束，不能使用未经证明的经验分数。
3. **按下界处理，但不截断**：先精确评价一个 incumbent；随后只要候选的下界仍有机会打败 incumbent，就精确评价它。不能证明的候选也精确评价。
4. **只有安全剪枝才跳过**：若下界已证明候选不可能改变当前最优，并且 tie-break 也不会选它，才跳过。
5. **任何疑问自动回退**：动态状态、锁定会话、整日账本、全局目标或浮点边界无法证明时，回到原始全候选精确修复。
6. **保留原候选索引和裁决**：即使精确评价顺序变了，也不能改变同值候选的原有选择；否则最后的 HGS 接受路径可能变化。

这条路的好处是把风险切成两块：

- 甲的风险是缓存键遗漏字段，靠逐位回放查；
- 下界的风险是剪枝不安全，靠候选级证据和自动回退查。

它的代价也要说清：这不是一个“小改 prescreen”任务，而是候选 API、下界证明、日志和 A/B 验收的组合工作。若界很弱，程序会自动接近原始全精确评价，收益可能不大；但它不会为了追求圈数而系统性漏候选。

### 我不建议的两个看似折中方案

`HALT`：下面两个方案都不应在没有用户再次授权和证据合同的情况下施工：

- “固定 k=3/5/10”：这是新门槛和新语义，k 不是从当前代码或文献自动得到的科学量；
- “先用近似分数取前 k，再用正式表结果反向调 k”：这是按结果救故事，不能接受。

如果用户最终明确要探索近似 top-k，它应当作为一个单独的算法臂，事前冻结 k、预算、seed、服务量和证伪标准；不能伪装成安全提速。

## 本轮建议的先后顺序（不是开工授权）

`DECISION`：如果用户下一轮批准施工，我建议只按这个顺序走：

1. 先在隔离副本做甲的 exact-cache A/B，验证候选顺序、异常、整日 Duty、acceptance path 和 fingerprint 逐位一致；
2. 若甲通过，再测端到端墙钟、每圈耗时、缓存命中率和能释放出的决策点预算；
3. 再决定是否为一个最小候选集合设计并审计 admissible lower bound；
4. bound 先做固定状态“不漏”验证，再做同墙钟、多 seed 的公开质量对照；
5. 动态预算最后用 M1 实测圈数和收敛曲线标定，不用本轮的估计值替代。

这一顺序保护的目的只有两个：公开表得到真实搜索强度，动态滚动得到真实重优化次数。若某一步只增加缓存命中数、profile 百分比或内部计数，却没有增加这两个消费者的可复核字段，就只能记为诊断，不应当写成论文进展。
