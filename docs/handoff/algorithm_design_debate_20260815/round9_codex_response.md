## 2.2 后续排序

### 第一位：冻结“保留哪些算法语义”，不先跑数

`DECISION`：先做一次零算力的组件语义归并，把每个施工件分成“已经完成”“被后续实现吸收”“仍有明确功能缺口”“只是候选增强”四类。理由是：不知道最终算法包含什么，任何收敛曲线都会测到一个还在变化的对象。

`DECISION`：归并时只问三件事：它解决哪一个已证实缺口；现有代码是否已经完成同一职责；砍掉后论文或算法链是否真的缺一环。不能因为施工书有编号就默认必须施工，也不能因为已经写了代码就默认必须保留。（依据：`algorithm_design_charter_20260815.md:33-44,59-70`；`AGENTS.md:51-74`）

### 第二位：只补最终主链的语义缺口

`DECISION`：对于归并后仍属主链必需的缺口，按依赖顺序补：候选表示与失败类型 → 完整评价 → 种群准入/教育 → 记录消费者。一次只补一个能被独立观察的语义，不把多个新机制捆成一个黑盒。

`DECISION`：SC3 的候选级 `CHARGING_GAP`、SC5 的跨企业边际代价偏置、SC6 的车辆平衡偏置目前不能凭施工书名字直接宣布“都必须做”。应先核它们是否分别解决一个尚未由 SC8 解码、现有跨场算子和现有车型算子覆盖的缺口；若没有独立缺口，就降为候选增强，不进入定稿关键链。（证据入口：`algorithm_build_spec_20260816.md:208-425`；当前代码中 SC8 的 typed gap 见 `solver/src/setp_solver/algorithms/problem_hgs/hybrid_decoder.py:25-119,287-387`）

### 第三位：完成不改变语义的提速，再采收敛形态

`DECISION`：只有算法语义冻结后，才评估精确缓存类提速。提速件必须使用完全相同的工作量口径验收，并证明评价、可行性、服务量、动作计数和解指纹保持；若缓存改变语义，立即回退，不把“更快”当补偿。（依据：SC-V2 已有同类成功证据，`solver/reports/scv12_speedup_20260816/report.md:31-53`）

`DECISION`：提速是否保留，先看它能否在固定工作量下减少时间，而不是看固定墙钟下终解是否更好。后者同时混入“速度变化”和“多做了多少搜索”，不能单独归因。

### 第四位：重新采收敛形态并冻结正式预算

`DECISION`：在仓库内建立可续跑、可识别成功/失败的产物目录后，从一个种子的小档开始逐档增加工作量，观察改善点之间是否仍有实质下降；只有仍在下降才加档。这里不预写多少秒、多少循环、多少次停滞合格。（依据：P79、P80，`pending_decisions.md:1294-1355`）

`DECISION`：1–3 个探索种子只用于判曲线形态、暴露种子差异和检查记录链；它们不承担算法胜负或论文效应。曲线形态与资源代价清楚后，再由同一口径冻结正式预算。

### 第五位：参数、组件价值和正式实验依次进行

`DECISION`：预算冻结后，先做算法内部参数与组件的配对检查，再做 10 种子正式比较，最后才做公平、动态、时变碳等论文机制实验。每一步只使用上一步冻结的算法和评价器，避免一边看结果一边改算法。

`DECISION`：C7 的正式单干基准和动态公平闭环放在算法结构稳定之后，但其字段消费者可以提前做零求解器核查；“消费者能读字段”与“论文公平结果成立”分开验收。（依据：`c7_fairness_ledger_20260816/report.md:80-112`；`main3b_backend_20260816/report.md:17-37`）

## 2.3 验收框架：验收主张，不验收愿望

### A. 每项工作先写一张四格合同

`DECISION`：每一项只写四格，不再增加统一门槛：

1. **它声称改变什么**：例如减少初始化饥饿、让企业归属进入搜索、降低同一工作量的耗时。
2. **它必须保住什么**：例如完整服务、可行性、完整评价器口径、受保护文件哈希；是否要求解指纹不变由第 1 格决定。
3. **用什么已有事实判**：代码调用链、保存的计数/轨迹、逐位输出或配对产物。
4. **若没通过走哪条路**：修接线、回退、缩小主张、补一个最小辨别动作，或把真实研究取舍交给用户。

`INFERENCE`：这四格能避免 SC1 式自埋坑。企业归属是搜索语义输入，所以解指纹变化是预期现象；把“指纹不变”列为它的合格线，会同时要求它生效又不许它影响搜索，合同内部矛盾。（证据：`CURRENT_PROJECT_CONTEXT.md:485-490`；`sc1_ownership_wiring_20260816/report.md:7-18,78-92`）

### B. 三层验收，三种判定者

| 层次 | 验收问题 | 合理证据 | 谁判 | 没通过怎么办 |
|---|---|---|---|---|
| 技术正确 | 接口、语义和不变量是否符合该件自己的合同 | 代码行、类型、回归、哈希、全评价、服务量 | Codex/Claude 可据事实判 | 修接线或完整回退；不进入下一层 |
| 行为闭环 | 组件是否在正确位置被触发，并改变了它声称改变的中间量 | 调用/命中/接受计数，阶段轨迹，前后状态 | Codex/Claude 可据产物判 | 若未触发，先查作用条件与实现；不靠加预算冒充触发 |
| 研究价值 | 在公平口径下，它是否值得保留并承担论文主张 | 同批配对、多种子分布、服务量、成本/排放和机制字段 | 数据提供事实；用户决定保留、降级或删除 | 负结果如实保留；先分原因，再把真实选项交用户 |

`DECISION`：文献负责确定比较协议和报告内容；项目自己的收敛数据负责确定预算；代理负责核事实；用户负责研究取舍。任何一方都不越位替另一方判。

### C. 不同改动采用不同“是否相同”口径

- `DECISION`：纯提速、重构、缓存和默认关闭的开关，采用同工作量逐位等价验收；它们声称不改算法语义，所以指纹与完整评价不同就是失败。
- `DECISION`：企业归属、交叉、邻域、解码器等本来要改变搜索的件，不要求终解相同；要求的是输入来源正确、组件被触发、产物通过同一完整评价、服务量不下降、失败路径可见。
- `DECISION`：随机算法效果不以单个种子“赢”作为合格线，也不预设改善百分比。保存配对分布和不确定性，真实效果小也照报。

### D. 失败路由

1. `DECISION`：**技术合同失败** → 修复或回退；这是普通实现决定，不升级成研究结论。
2. `DECISION`：**没有激活** → 查实例是否存在作用条件、触发器是否接线、候选是否在进入种群前被挡住；不先改参数救结果。
3. `DECISION`：**已激活但无改善** → 依次区分机制效应小、场景无空间、搜索没找到、评价/记账错误；只设计能区分这些解释的最便宜动作。
4. `DECISION`：**证据丢失或批次不可比** → 结论回到 `UNKNOWN`，不从报告文字、屏幕或残留数字补齐。
5. `DECISION`：**可信负结果** → 保留负结果，由用户在“删除、降为工程件、改论文定位”中选择；代理不得调参或换口径挽救。

## 2.4 我对“算法定稿”的定义

`DECISION`：本项目的“算法定稿”应定义为**算法对象已经固定并可被公平测量**，而不是“已经得到喜欢的效果”。同时满足以下事实条件时，才可称结构定稿：

1. 保留的组件清单、各自职责、调用顺序、默认开关和失败语义已经唯一；不存在两个互斥实现同时冒充主算法。
2. 每个保留组件已通过自己的技术正确层； intended-to-change 的组件还有至少一条行为激活证据。
3. 候选从生成、完整评价、教育/修复、种群准入到最终 best 的链可追踪；服务客户数、需求量、可行性和完整成本口径贯通。

`INFERENCE`：按这个定义，“结构定稿”可以先于正式实验，而“论文证明算法有效”必然晚于正式实验。若把二者都叫“算法定稿”，P79 会形成循环：不跑实验不能证明有效，不定稿又不许跑实验。因此后续文档应把这两个状态分开叫“结构冻结”和“效果闭合”，但名称和是否采纳仍由用户决定。

## 3.7 Q1–Q8 逐题回答

### Q1｜当前到底怎么停；固定迭代验收是否成立

`FACT`：现有技术入口有三个相关参数，但在当前 live integrated 路径中只有两个是终止条件：

1. `--iterations`，默认 1，在 `run_problem_hgs_private_technical.py:2773-2778` 声明，`:2937-2938` 校验；
2. `--max-runtime-seconds`，默认 1200 秒，在同处声明，`:2945-2946` 校验；
3. `--stagnation-patience`，默认 500，**不是当前终止条件**，而是无改进多少轮后重启种群的间隔。

`FACT`：实际 stop 回调是 `state.iterations >= args.iterations OR state.elapsed_seconds >= args.max_runtime_seconds`（`run_problem_hgs_private_technical.py:3365-3384`）。所以现成迭代封顶开关明确存在。

`FACT`：live 入口调用 `run_integrated_problem_hgs`（脚本 `:3403-3428`）。该 runner 把 caller stop 传给 integrated 算法（`runner.py:303-326,431-460,495-523`）；`stagnation_patience` 被写入 `GeneticAlgorithmParams.num_iters_no_improvement`（`integrated_private.py:1107-1122`），在 `IntegratedGeneticAlgorithm.py:136-145` 和 `HGSControl.py:75-101` 的语义是**重启**，不是退出。`runner.py:551-567,718-725` 的旧 retired 路径才把停滞当终止；它不是当前技术入口。

`DECISION`：Claude 的核心判断“提速甲用固定迭代而非固定墙钟做逐位验收”成立，但应写成：固定迭代是**必要的共同工作量口径**，墙钟硬顶设为不触发的安全边界；同时核终解、轨迹、候选/评价/接受计数和异常路径。若墙钟先触发，该配对无效。正式算法竞争仍遵 P45 的同批等墙钟，不能把技术等价口径搬成正式性能口径。（P43-K/P45：`pending_decisions.md:193-205,219-233`）

### Q2｜提速甲最便宜的收益预估

`FACT`：现存 cProfile 只有函数调用次数和累计时间，不保存 route/policy/context 的参数值，不能离线恢复“精确键会重复多少次”。该 profile 单圈总计 157.631 秒；热路径 48,760 次路线评分、67,580 次择时，但可省量仍 `UNKNOWN`（`speed_diag_20260816/report.md:31-42,88-110`）。

`DECISION`：最便宜的有效动作是**一轮影子键计数**：在拟缓存边界只计算完整 key、统计重复 key、累计各 key 的原函数耗时和返回值哈希，绝不复用结果。它回答“有多少完全相同输入”和“理论可省的已观测耗时”，不改变搜索。

`INFERENCE`：按已存单圈 124–158 秒的量级，单次影子运行约 3 分钟；若加一条无埋点固定迭代对照核无扰动，总机器时间约 5–6 分钟。这里只是基于 `scv12` 的 124.17 秒/圈和 cProfile 的 157.63 秒估计，不是承诺。（证据：`scv12_speedup_20260816/report.md:31-53`；`speed_diag_20260816/report.md:31-35`）

`DECISION`：不值得把它另立成完整施工项目。若用户选“先估收益”，把影子计数作为提速甲的第 0 步：重复 key 接近零就停止；有明确复用再接缓存。若用户直接批准提速甲，影子计数仍可先记录再在同一改动中转为真正缓存，避免两次搭架子。

## 4.2 主链

```text
组件语义归并
  → 用户一次选择最终算法范围
  → 只补被选中的主链语义缺口
  → 当前复制内核等价极短复验
  → 精确缓存提速（若批准）
  → 仓库内可续跑的收敛观察
  → 用户确认曲线形态，算法定稿
  → P70/公平基准等实验校准
  → 每算例 10 种子的正式实验与图表
```

### 第一步：组件语义归并

`DECISION`：把 SC0–SC11 按 Q5 结果重写成一份“保留、吸收、实验后置、删除”清单。产物不是新总计划，而是双方案的修订表；每个保留件写清改变什么、保住什么、证据和失败路。

`验收`：所有“必须”都能指到用户决定或一个当前未闭合的语义；所有“完成”都能指到当前代码/产物；P80 纠正全部覆盖旧数。

`失败路`：凡仍存在两个会改变算法含义的解释，集中放进 4.5 的选择题，不由代理默认。

### 第二步：只补被选中的语义缺口

`DECISION`：推荐的中间范围是：保留 SC0、SC1、SC2、SC8、SC-V2；补 SC3 的透明充电缺口，因为它决定近可行候选是否能进入 A2；SC4 只保留可读字段与消费者接口，正式 `c({i})` 和规则选择后置；SC5/SC6 暂缓；SC7 关闭；SC9 并入产物 schema。

`验收`：技术不变量＋行为激活，不看改善百分比。SC3 若保留，至少要分别复算能量缺口和窗口缺口，并证明 BEST_EFFORT 不会冒充可行解；若用户选择硬拒绝，就从设计主张中删除 SC3，而不是留一个永远过不了的施工件。

`失败路`：技术错误修或回退；已激活但没有效果不在此步裁，它留到公平数据中判。

### 第三步：当前复制内核等价复验

`DECISION`：复用历史 100 轮双环境入口，预计低于 2 分钟；这是技术身份核验，不是性能实验。

`验收`：两边完整服务、需求、成本、路线序列和 best SHA 相同，且源码/二进制哈希、互不导入事实写入仓库包。若不等价，先定位当前 copied kernel 漂移，公开性能工作暂停；不能拿私有机制成绩补位。

### 第四步：精确缓存提速

`DECISION`：若用户批准 P78 甲，先做一轮影子 key 计数；重复输入存在再开启 exact cache。只缓存完全相同输入，保留候选顺序、异常和并列裁决。

`验收`：同初始种群、同种子、同固定迭代，墙钟硬顶不触发；终解、完整评价、关键轨迹、候选/接受/拒绝计数逐项相同。另报时间差，但不设“必须快 x%”。

`失败路`：任何语义差异立即删除缓存接线；重复 key 近零则停止，不因为已经施工就扩张到高风险 key 规范化。P78 丙下界剪枝仍是另一项用户决定。

### 第五步：收敛观察

`DECISION`：使用最终结构和已通过的安全提速，从一条种子开始，产物直接落仓库；曲线仍明显下降就从同一现场续跑，不预写总墙钟、总迭代或停滞数字。必要时再用另 1–2 个探索种子看形态是否只属于单一种子。

`验收`：保存每次 best 改进的迭代和墙钟、完整配置/哈希、服务量、完成/失败信号与续跑位置。用户看图判断是否形成经典形态；代理只描述曲线，不代设“几个点算收敛”。

`失败路`：

- 若只是安全硬顶先到而曲线仍下降，续跑同一现场；
- 若记录链断，先修记录，不推算法结论；
- 若算法已做很多工作却无可行 best，查候选→种群→best；
- 若速度仍使有效观察不可承受，再把 P78 丙作为选择题报用户，不自动开工。

### 第六步：算法定稿

`DECISION`：按 P79 的字面顺序，算法定稿时应满足：组件与语义唯一；保留件技术正确且 intended-to-change 件有激活证据；复制内核当前等价；完整服务/评价/种群链贯通；安全提速未改语义；版本与产物可复建；用户认可收敛曲线形态。

`DECISION`：P70 参数阵列、P28 单干基准、完整公平规则选择、动态公平和情景扫描不列为定稿前条件。它们是定稿后的校准/实验。若用户希望把 P70 也定义为“算法定稿的一部分”，须明确修改 P79；代理不能暗改词义。

### 第七步：实验校准与正式图表

`DECISION`：算法定稿后按 P70 已批的形态开展参数校准；多种子协议、同批同墙钟、服务量、完整评价和报告字段事前冻结。首个合法 10 种子同配置批次同时产出搜索波动分布，之后再由用户冻结 P63-2 的公平退回阈值。
