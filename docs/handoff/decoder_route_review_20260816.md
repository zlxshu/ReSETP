# “翻译器”两条造法评审

日期：2026-08-16  
范围：只读代码、只读算例资料、联网核文献；不运行求解器，不修改代码和算例数据。

## 先说结论

FACT：当前项目的完整解不是“一串客户顺序”，而是一组实体车的整日任务。每辆车必须带有实体车 ID、车型、所属车场、连续趟号、充电记录和完整时间安排。这个合同写在整车设计书第四章 §4.2 以及 model.py 的 PhysicalVehicleDuty / ScheduledDuty 结构中（algorithm_full_design_20260816.md:131-152；model.py:271-303、328-400）。

FACT：甲和乙引用的原始参考都没有直接覆盖本项目的五条硬要求。甲的论文方法主要解决“客户顺序如何切成若干趟，并分配给车辆”；乙的官方示例主要解决“车辆分配和趟次分隔符怎样随路线一起保存”。二者都没有现成的实体车 ID、两车场企业归属、跨趟 SOC 连续、充电窗重走这条完整链。

FACT：这不是小缺口。当前整任务层交叉探针中，63 个捕获到的充电候选全部因 NO_FEASIBLE_WINDOW 失败；原始条件、放宽时间窗重放、FRVCPY 重放仍然是 63/63（design_probe_death_survey2_20260815/report.md:47-54）。所以，路线顺序能拼出来，不等于项目完整解能落地。

DECISION：我的推荐是“有边界的混合造法”：

1. 借甲的论文思路，让客户顺序和“怎样切成若干趟”由 Split / labeling 这一个地方负责；
2. 借乙的开源思路，保留明确的车辆分配槽位，但把它升级成项目真实的实体车登记表：实体车 ID、车型、home depot、可用班次、趟数上限；
3. 充电不由甲或乙的路线表示顺手猜出来，而是在改动车辆后丢弃未锁充电账，重新做本项目已有的充电补全；
4. 只有重新组装成 PhysicalVehicleDuty，并通过完整检查，才算一个可接受的孩子。

这套混合只有在“每个决定只有一个负责人”时成立。若 Split 和趟分隔符同时各自决定切点，或者把乙的分隔符位置盲目复制到已经改变的客户顺序上，就会变成不伦不类；具体判别见第七节。

用户尚未在甲、乙、混合三者中作最终选择。上面的推荐是 DECISION，不是 USER DECISION。

## 一、评分口径

本评审中的三个词按下面的意思使用：

- 天然满足：引用的原始方法，在不改变其表示含义的情况下就保证该要求。
- 需额外工程：可以把要求接上去，但引用方法或当前项目没有现成接口；需要明确的新环节。
- 做不到：按引用的原生表示直接使用时不能承载该要求。这里的“做不到”不是说数学上永远不能扩展，而是说不能把原参考直接当成项目现成答案。

因此，表中出现“做不到（原生参考）”时，不应理解为路线被永远关闭；它表示必须先改变表示或补一层工程，不能直接照搬。

## 二、当前项目真正要还原的东西

FACT：PhysicalVehicleDuty 要求：

- 实体车 ID 的前缀和车型一致，EV_ 对应电车、CV_ 对应燃油车；ID 不能把趟号误当成实体车；
- home depot 非空，并且所有趟的首尾都回到同一个 home depot；
- 趟号严格是 1、2、3……，不能跳号；
- 充电事件的相邻 SOC 必须连续，容差为 1e-7；
- to_solution 会把一辆实体车的第 k 趟写成同一个实体车基名加 #Tk；from_solution 会按实体车基名重新分组，再检查车型和车场一致（model.py:328-400、492-620；solution.py:8-25）。

FACT：本项目的客户企业归属在 enterprise_assignment.csv 中，C001–C025 属于 ENT_A，C026–C050 属于 ENT_B（enterprise_assignment.csv:1-51）。当前 china81.py 的读取路径主要从订单或城市车场映射构造 customer_home_depot，并没有直接把这个新增 CSV 接入完整解装配（china81.py:578-617）。整车设计书已经把“way ID 转 node ID，再接入 bundle.customer_home_depot”列为前置接线（algorithm_full_design_20260816.md:208-211）。

FACT：当前实例观察到的“单车最多 3 趟”不是合同；设计书明确写的是实例给出趟数上限，构造器使用 max_reloads=len(customers)-1（algorithm_full_design_20260816.md:24-35、C5 相关说明）。所以任何路线都不能把 3 写死。

## 四、三条路线各要补什么

下面的“工程量”是相对估计，不是运行时间承诺，也不是用户批准的新增合同。按接口块估计，是为了避免虚构人日。

### 甲：巨型路线＋Split

**估计：大。至少要补六个接口块。**

1. 客户顺序检查：客户一次且只出现一次，顺序合法，企业归属可追溯。
2. Split / labeling 扩展：把单车场、同质车辆的论文前提，扩成两车场、车型、容量、班次、时间窗和实例趟数上限。
3. 车辆物化：把 labeling 的抽象车辆转换成真实的 EV_/CV_ 实体车槽位，并保证同一实体车的所有趟使用同一个车型和 home depot。
4. 趟号物化：按每辆实体车重新生成连续的 #T1、#T2……，并按实例上限截断或判不可行。
5. 充电重建：改动车辆时清掉未锁充电账，按新路线重新生成充电会话、SOC 前后值和充电窗占用。
6. 完整验收：先构造 PhysicalVehicleDuty，再走 to_solution / from_solution 和完整检查；失败要返回 typed gap，而不是把半成品当最好解。

**最难的一环：** Split 得到的是客户段和抽象车辆，项目需要的是实体车整日任务；这中间既要满足车场和车型归属，又要让连续趟的时间、SOC、充电窗一起成立。论文的 labeling 只能提供“如何把段落放到车辆上”的思路，不能直接提供本项目的物化规则。

**没有现成单一参考的部分：** “两车场企业归属＋实体车 ID＋跨趟 SOC＋充电窗＋typed gap”这一整段没有在已核参考中找到现成实现。当前设计书也把它列为本项目需要自建、而现有参考只支持表示家族的部分（algorithm_full_design_20260816.md:151-152）。因此这部分是 UNKNOWN，不能写成“已有论文实现”。

### 乙：车辆分配＋趟分隔符

**估计：大。至少要补七个接口块。**

1. 车辆登记：把官方的 VehicleAssignment 从抽象车辆位置扩成实体车 ID、车型、home depot、班次和可用趟数。
2. 分隔符同步：每次路线替换、交叉或删除客户后，重新确认分隔符仍然落在合法客户边界。
3. 可行创建器：官方教程明确说明随机插入分隔符容易产生不可行解，因此不能直接拿随机分隔符创建器承担本项目任务（官方文档网页行405-445）。
4. 双车场和企业归属：分隔符只能表达回场，不表达客户属于哪一个企业或车辆属于哪一个 home depot；这要另接 CSV 和车场规则。
5. 趟号与实例上限：从分隔符推导连续趟号，并按实例上限检查，不能把 3 固定为硬编码。
6. 充电账重建：分隔符改变后，原充电账的车辆、时刻和 SOC 可能都失效，必须重新做充电补全。
7. 完整验收：把结果转换为本项目的 PhysicalVehicleDuty，并验证首尾同场、SOC 连续和充电窗。

**最难的一环：** 分隔符是路线位置的附属信息。官方文档说明，普通 Potvin 交叉把整条 tour 当作整体处理并忽略分隔符；MultiTripRBX 再把父代相应 tour 的分隔符复制到子代。如果客户已经换了，原位置的“回场”是否仍然可行就必须重新证明，而不是靠位置相同来假定。

**没有现成单一参考的部分：** 官方示例没有把分隔符、异构车队、两车场、充电站占用、SOC 连续和本项目 typed gap 合到一起。这个完整接口同样是 UNKNOWN。

### 混合：论文 Split＋实体车分配

**估计：大，但主线更清楚。至少要补七个接口块；它不是零工程量路线。**

1. 保留甲的客户顺序和 Split / labeling 作为唯一的切趟负责人。
2. 借乙的 VehicleAssignment 思路，但把它改成“实体车槽位”，不是简单整数索引。
3. 车槽位绑定实体车 ID、车型、home depot、企业服务范围、班次和实例趟数上限。
4. Split 的客户段交给车槽位后，统一物化为连续 #T1、#T2……。
5. 如果保留分隔符，它只能是 Split 结果的派生记录或缓存；它不能再反过来修改 Split 的切点。
6. 改动车辆后按本项目规则重建充电账和 SOC。
7. 通过 PhysicalVehicleDuty、to_solution / from_solution 和完整检查后，才将孩子交给评价器。

**最难的一环：** 定义并守住“切趟”和“实体车落位”的边界。如果这两个模块互相改对方的结果，错误会被藏在表示里；如果一方只输出客户段，另一方只负责合法实体车和全日状态，问题会更容易定位。

**没有现成单一参考的部分：** 混合后的 materializer、充电重建和 typed gap 仍未在现成参考中找到。混合的价值是把已有参考放在各自擅长的层，而不是声称已有一份代码已经完成全部工作。

## 五、最可能的失败位置

### 甲最可能的失败

第一处是“Split 有结果，但没有可用的实体车整日任务”：客户段可能被分给错误的车型或 home depot，或者趟号和实例上限不合法。

第二处是“路线切好了，但充电时间窗无法落地”。这正对应当前 63/63 的教训：只要客户顺序改变，原充电账就不能默认有效；即使尝试放宽时间窗，现有重放仍全部 NO_FEASIBLE_WINDOW（design_probe_death_survey2_20260815/report.md:47-54）。

第三处是“为了保留较好的客户顺序，偷偷保留旧充电账”。这会把表面路线和实际车辆状态拆开，最终在 SOC 或充电窗处失败。正确处理是把失败作为有类型的不可行孩子记录，不把半成品交给最好解。

### 乙最可能的失败

第一处是“分隔符跟着位置走，但客户已经变了”。一个原来合理的回场位置，换了客户后可能变成超时、超载、车场不对或充电窗不可用。

第二处是“车辆分配看起来保留了，实际没有保留实体车语义”。当前项目的 route ID 是趟标签，不能单独当成权威的实体车分配；最终仍要按物理车基名分组并检查车型、home depot 和连续趟号（model.py:528-620；solution.py:8-25）。官方文档还明确提醒，普通交叉把 tour 当整体处理并忽略分隔符，需要专门处理才能保住趟结构（官方文档网页行567-568）。

第三处是“随机分隔符制造大量不可行候选”。官方教程本身就说明默认创建器不主动随机插入分隔符，因为很容易不可行。对本项目再叠加班次和充电窗，这个风险只会更高。

### 混合最可能的失败

混合不会自动解决充电窗问题。它最可能在两种情况下失败：

- 把乙的分隔符当成第二套切趟决定，和甲的 Split 产生不同答案；
- Split 重新切趟后仍沿用旧的充电账或旧的分隔符位置。

这两种失败都属于接线错误，不应被包装成“混合方法本身证明无效”。应先检查每个决定的唯一负责人，再检查充电重建是否真的被调用。

## 六、混合造法是否“不伦不类”

### 成立的版本

混合成立的必要条件不是“两个参考都露个名字”，而是下面五个决定各自只有一个负责人：

| 决定 | 唯一负责人 | 另一部分能做什么 |
|---|---|---|
| 客户的相对顺序 | 路线层交叉 | 不修改客户顺序 |
| 趟从哪里切开 | Split / labeling | 不再用独立分隔符反向改切点 |
| 用哪辆实体车承接这些趟 | 实体车槽位表，吸收乙的 VehicleAssignment 思路 | 不把抽象车辆编号当实体车 ID |
| 充电和 SOC | 本项目充电重建 | 不从客户顺序或分隔符猜充电 |
| 是否接受孩子 | PhysicalVehicleDuty＋完整检查 | 不以“客户顺序完整”代替完整可行 |

这个版本取的是“甲的论文层次”和“乙的车辆归属保存方式”，没有把两个方法的同一职责叠两遍，所以是相容的。

### 不成立的版本

下面三种做法都属于不伦不类：

1. 先让 Split 自己决定切点，又把乙的旧分隔符复制过来，最后不说明谁拥有最终切点；
2. 把 MultiTripRBX 的分隔符位置直接套到换过客户的子代上，再假定时间和充电仍然成立；
3. 让 labeling 输出抽象车辆编号，却在项目后面把这个编号直接当成 EV_/CV_ 实体车 ID。

判别标准很简单：给同一个子代重复检查一次，能否明确回答“谁决定切趟、谁决定实体车、谁重建充电”。如果任何一个问题有两个答案，混合就没有成立。

## 七、推荐与用户选择

### 我的推荐

DECISION：推荐混合版本，但只推荐上面“一个决定一个负责人”的版本。

理由有三条：

1. 甲的论文给出了较清楚的客户顺序到多趟结构的学术依据；2014 作者预印本 §3.1–§3.2（pp.4-8）明确描述了无趟分隔符的客户排列、插入趟边界、辅助图和 labeling。2016 论文的官方摘要也明确把 giant-tour representation 和 efficient labeling 作为核心。
2. 乙的官方实现提醒了一个甲单独容易忽略的问题：车辆分配和趟分隔符是不同层的信息，不能只保存客户顺序。但乙的分隔符复制机制不能直接承担本项目的时间窗、双车场和充电语义。
3. 当前项目解对象已经明确是实体车整日任务，并且 63/63 充电候选都没有通过充电窗；因此最终装配和充电重建必须是项目自己的正式环节，不能由论文或教程的表面表示代替。

### 如果用户选甲

需要额外补齐：实体车槽位表、两车场企业归属接线、车型和 home depot 匹配、实例趟数上限、连续 #T 编号、充电账重建、SOC 连续检查、充电窗失败的 typed gap，以及 PhysicalVehicleDuty 的完整装配。

甲的主要代价是：表示比较轻，但从客户段到真实实体车整日任务的 materializer 较重。

### 如果用户选乙

需要额外补齐：把抽象 VehicleAssignment 升级成实体车登记、重写分隔符同步和可行创建、接入两车场企业归属、实例趟数上限、车型/班次约束、充电重建、SOC 连续检查和 PhysicalVehicleDuty 完整装配。

乙的主要代价是：车辆归属信息更早暴露，但路线替换后分隔符是否仍有意义会成为核心维护问题；不能直接照搬 MultiTripRBX。

## 八、给非专业读者的大白话说明

### 甲：先排一条长清单，再切成每辆车的当天任务

甲先把所有客户排成一条长清单，然后寻找合适的位置，把长清单切成一段一段的送货任务。接着再把这些任务分给不同车辆，尽量让每辆车的容量、工作时间和回场安排都合适。它的好处是清单很简单、论文里有成熟做法；代价是最后还要补一层，把“第几段任务”翻成“哪一辆真实的车、属于哪个车场、途中什么时候充电”。如果这一步补得不完整，清单看起来漂亮，车辆当天却可能根本跑不完。

### 乙：一开始就给每辆车写好任务单和回场位置

乙一开始就把每辆车的任务单和每次回场的位置一起保存，路线交换时也尽量把这些信息带走。它的好处是车辆归属和每次回场的位置更直观，不必到最后才猜哪辆车接了哪几段。代价是客户一旦换了位置，原来的回场位置可能马上不合适，甚至让时间和充电安排失效。它像把旧行程单贴到新客户名单上，方便，但每次换名单后都必须重新核对整天行程。
