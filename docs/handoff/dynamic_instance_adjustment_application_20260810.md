## 已经证实的问题

独立算法在 `cn-jjj-50c-01-V2-LOCATIONS`、动态流 seed 1 的第 7 次更新中无法继续。直接算术表明，这次失败不是搜索预算不足：

- 客户 `C030` 在 `44740.68534` 秒出现；
- 最晚服务时刻为 `46780.88874` 秒；
- 北京车场到该客户的最短已登记行驶时间为 `2107.10` 秒；
- 即使有车在订单出现时立刻出发，也只能在 `46847.78534` 秒到达，晚 `66.89660` 秒；
- 当前固定半小时触发到 `45000` 秒才重算时，最早到达为 `47107.10` 秒，晚 `326.21126` 秒。

因此，这一个动态订单从公开的那一刻起就已经物理不可服务。延长算法时间、增加种群或更换搜索动作都无法补救。该证据只证明当前动态事件流的出现时间生成有问题，不证明 China81 的静态客户、路网、需求或时间窗整体有问题。

## 已经确定且不重开的部分

用户已选择 A1：建立大于当天实际订单集合的预登记潜在客户池；真实未来订单和算法内部情景从同一潜在池分别独立抽样，算法不得读取本轮尚未揭示的真实订单。本申请不重开 A1，只处理“抽到的订单何时出现才算物理可服务”。

## 三个真实选项

### 选项 A：保留固定半小时触发，并约束订单出现时间

生成器只接受满足“下一次固定重算时刻 + 至少一个兼容车场的最短直达时间 ≤ 客户最晚服务时刻”的出现时间。

- 改动范围：只改潜在订单出现时间的抽样与验收；不改路网、需求、车辆、客户时间窗和静态算例。
- 结果：每个新订单在出现时至少存在一个理论上的及时出车机会；算法仍可能因自己早先调度不当而失败，那才是真正的动态算法问题。
- 代价：出现时间分布会受半小时触发规则约束；如果以后更换触发规则，需要重新生成动态流。

### 选项 B：订单一出现立即触发重算，并约束即时可服务

生成器只要求“出现时刻 + 至少一个兼容车场的最短直达时间 ≤ 最晚服务时刻”，每个订单出现即触发一次重算。

- 改动范围：同时改变出现时间生成和动态触发规则。
- 结果：保留更宽的出现时间范围，也不会因为等待下一次固定触发而人为失去订单。
- 代价：重算次数增加，动态实验含义从定时调度变成事件驱动调度；这会直接影响论文动态机制口径。

### 选项 C：保持出现时间和触发规则，放宽客户时间窗

把抽到的动态客户最晚服务时刻延后到足以从至少一个车场到达。

- 改动范围：改变客户时间窗，因此静态与动态使用的同一客户输入会出现不同版本。
- 结果：可以保留现有出现时刻和触发规则。
- 代价：对基础算例含义改动最大，也可能改变静态路线和机制效应；需要重新核对所有依赖该客户时间窗的实验。

## 获批后的最小施工与验证

只改动态潜在池／事件流生成器，并保存生成前后的参数与种子。每条真实订单和每条算法内部情景都独立检查上述可服务条件；真实流与算法情景只共享事先登记的分布和潜在池，不共享当天抽中的客户身份。随后只做三个地区各一个 50 客户技术短试，检查完整服务、需求守恒、历史锁定和当前独立 HGS 能否跑到底；不据结果再倒改生成条件。

## 当前未作的决定

本申请不替用户选择 A、B 或 C，也不据此选择统一主算例、正式触发规则或论文叙事。用户批准前，动态生成器保持不变，当前失败包原样保留。
