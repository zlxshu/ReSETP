# E2 真混合算法开发与验收合同（HGS + 机制感知破坏—修复）

日期：2026-07-24
状态：`APPROVED_DESIGN__STATIC_IMPLEMENTATION_PASS__REAL_BUNDLE_G0_PENDING`

## 1. 为什么另立这条线

当前正在运行的 E2 v7 是一条强 HGS 家族基线：三个 HGS 视角分阶段搜索，经完整模型
核查后再进行限时路线池组合。它可以继续作为可信基线和诊断证据，但不能仅凭“三个
HGS 视角 + 路线池组合”被包装成“不同算法的深度混合”。路线池 MIP 是辅助候选生成器，
也不能冒充第二种独立搜索算法。

用户对论文最终算法的要求是：必须能够形成真正的“算法 A、算法 B、A+B”对照，并且
A+B 的优势来自两种不同搜索方式之间可核验的信息往返，而不是改名、增加视角或事后
从多个完整结果中择优。

本项目所称“1+1>2”不是把两个成本数值相加。它有三个同时成立的含义：

1. 在相同完整候选评价总数下，A+B 的最终成本必须低于 A，也必须低于 B；
2. A+B 必须出现由 A 传给 B、再由 B 传回 A 后继续产生新改进的证据，不能只是并行
   跑完后取 `min(A, B)`；
3. 这种优势必须在预注册的多题、多种子确认中稳定出现，并在正式未参与开发的题上
   达到统计显著和有实际幅度的改善。

这是最终算法的硬验收标准，不是对尚未运行结果的承诺。达不到就停止该候选并承认
“没有实现 1+1>2”，不得为了保留“混合算法”名称而降低门槛。

因此，从本合同起：

- 正在运行的 E2 v7 保持原样，记为
  `INTERIM_STRONG_HGS_FAMILY_BASELINE`，不得中止、改写或并入新算法开发数据；
- 论文最终算法候选另立为“协同 HGS–破坏修复搜索”，开发简称
  `COOP-HGS-RR`，简称只用于开发登记，论文名称待结果通过后再定；
- 新算法未通过本合同全部门槛前，不得替换主 TeX，不得写“显著优于”“协同增益”或
  “混合算法有效”等结果性结论。

## 2. 文献依据与本项目取舍

本设计不是凭空拼接，主要吸收以下可复核做法。
逐篇对照与本项目取舍另见
`docs/handoff/e2_genuine_hybrid_literature_basis_20260724.md`。

1. Simensen 等（2022）把独立的 string removal / ruin-and-recreate 大邻域嵌入 HGS
   的教育过程，并分别比较 HGS、SISR 与混合算法，证明“遗传搜索 + 独立破坏修复”
   可以形成真实的 A、B、A+B 结构，而不是 HGS 内部参数消融。
   DOI：`10.1007/s10732-022-09500-9`。
2. Zhao 等（2026）在 HGS 教育过程中加入面向库存—路径耦合决策的专用大邻域：
   一次移除并重新安排某客户的全部访问，再用动态规划处理耦合决策。其关键启示是：
   有效的大邻域必须改变本问题真正耦合的决策，不能只是通用 relocate/swap 的重复。
   DOI：`10.1016/j.ejor.2025.11.021`；本地 Zotero PDF 键：`KTRXSD43`。
3. Castro 等（2026）将独立 ILS 的问题专用解码与局部搜索能力嵌入 HGS，强调融合点
   必须针对原问题的耦合结构。DOI：`10.1016/j.cor.2025.107376`；本地 Zotero PDF
   键：`9ZVGTI45`。
4. 金东遥等（2024）把电动车路径与固定路径充电拆成上下层决策，并用回溯充电策略
   补全路径。该工作说明 EV 路径搜索不能只比较客户顺序，充电可行性必须进入候选
   生成或完整补全。DOI：`10.16182/j.issn1004731x.joss.23-0863`；本地 Zotero PDF
   键：`N7BVHTZL`。

本项目不照搬这些问题的算子。吸收的是结构：HGS 负责种群式全局探索，独立破坏—
修复搜索负责对整段路线和车场/车型/充电安排做大幅重构；两者共享同一完整模型，
并在搜索过程中双向交换完整可行解。

## 3. 模型与算法必须逐项咬合

新算法不是通用 HGS、ALNS 或 SISR 的直接套用。解的内部表示、解码和大邻域必须对应
本论文模型中的耦合决策：

| 模型中的真实决策 | 算法必须提供的专用处理 |
|---|---|
| 客户访问顺序与时间窗 | HGS 巨环负责广域重排；修复时使用时间窗余量和迟到风险筛选插入位置 |
| 广州/深圳车场归属与跨场协同 | 染色体保留客户顺序但不永久锁死车场；专设整路线换场和双向跨场片段交换 |
| 燃油车/电动车选择与有限车队 | 解码同时核对各车场两类车辆余量；换车型必须计入固定成本、能耗和车队占用 |
| 电动车续航、充电站与“先充电后发车” | 路线骨架交给专用充电—时间解码器，联合决定充电位置、充电量和发车时刻 |
| 分时电价与分时碳强度 | 充电—时间解码器按城市、日期和半小时档位逐段计价、计碳，不用全日平均值代替 |
| 分城市柴油价 | 燃油路线按车辆所属车场对应的城市和日期取价，跨场后必须重新绑定 |
| 动态新订单与已执行状态 | 动态阶段冻结已完成路段，继承实体车位置、时刻、载重和电量，只搜索尚未执行部分 |
| 成本、排放与成员收益的一致核算 | 任何候选进入接受、种群或最终比较前，都必须由同一完整模型给出唯一目标值 |

### 3.1 双层解表示

上层表示客户访问次序和可移动的路线分隔；下层不是静态标签，而是一个面向本题的
“车场—车型—充电—时间”解码器。对给定客户序列，下层在有限候选中联合选择：

- 起讫车场；
- 具体车辆类型及有限车队占用；
- 电动车充电站、充电量、充电开始时刻和发车时刻；
- 燃油/电力/碳成本所对应的城市、日期和半小时档位。

下层必须保留完整模型作最终裁判，但不能每次从头穷举。实现时使用路线前缀状态、
时间窗支配、续航支配、车队余量和分时价格边界进行剪枝；只有未被支配的少量方案
进入完整评价。缓存键必须包含路线客户序列、车场、车型、日期和动态状态，防止错误
复用不同地区或时段的结果。

### 3.2 本题专用大邻域

除文献中的连续客户串移除外，至少实现并单独验收以下专用操作：

1. **跨场整路线重归属**：整条路线在广州/深圳之间迁移，并重新选择车型和价格参数；
2. **双向跨场片段交换**：两个车场各移出一段客户，再交叉修复，以释放局部车队或
   时间窗瓶颈；
3. **油电车型翻转**：在不改变或小幅改变客户顺序时，重新评估燃油车与电动车，并
   连带重算充电、固定成本、能耗和碳成本；
4. **充电—发车时刻重构**：保持客户集合，允许改变充电位置、充电量和发车时刻，
   利用分时电价与分时碳强度的错峰空间；
5. **时间窗压力串重排**：围绕最小时间余量客户移除相邻串，在两个车场和两类车型
   的可行位置中重插；
6. **动态未执行尾段重构**：仅作用于尚未执行的客户和路线尾段，严格保留已执行事实。

每个操作必须证明它实际改变了自己负责的模型决策；若只生成与通用 relocate/swap
相同的候选，判为 `HALT_OPERATOR_NOT_PROBLEM_SPECIFIC`。

实现层不得用“解哈希变化”替代上述证明。整路线换场必须保持该客户集合为一条完整
路线并迁往登记的另一车场；双向交换必须证明两个客户串分别由对方车场服务；车型
翻转必须证明相同客户集合实际换用另一车型；充电调整必须改变充电地点、能量或起始
时刻；时间窗串和动态尾段必须改变相应客户的结构位置。充电站节点不得进入客户移除
或重插列表。

### 3.3 高性能实现要求

“定制”不能以不可接受的速度为代价。实现必须同时具备：

- 候选邻接表和相关性筛选，避免全量两两枚举；
- 路线级增量距离、时间、载重、能耗和排放下界；
- 下层解码的支配剪枝与安全缓存；
- 完整评价的统一预算账本，缓存命中不得伪装成新评价；
- 一次候选失败后明确记录失败原因，不重复提交相同签名；
- 可复现的多进程任务级并行，但单个算法臂保持单线程，避免比较时偷用更多核。

性能门不仅比较成本，也比较单位完整评价产生的有效新解比例、每次改进所需时间和
峰值内存。若定制解码器让 A+B 的中位墙钟超过 A 的 4 倍且没有相应质量增益，判
`STOP_HYBRID_OVERHEAD_NOT_JUSTIFIED`。

缓存键必须至少包含 `instance_id/date/region/city/price_area/
carbon_source/diesel_zone/home_depot/vehicle_type/charge_strategy/
carbon_weight/customer_sequence/dynamic_state/runtime_authority/fleet_authority`。
任一字段变化都必须导致不同缓存项；缓存只允许复用路线局部可行性和局部成本，不能
复用或免计整解完整评价。

## 4. 三个正式对照臂

### A：HGS 家族搜索

A 使用当前已修正、已通过物理规则检查的两阶段多视角 HGS 搜索核心。首次开发门中
关闭路线池 MIP，避免把辅助精确求解器混入 A/B/A+B 的归因。A 的三个视角可以作为
HGS 内部候选来源，但论文主消融不再把三个视角伪装成三种独立算法。

A 必须记录每个完整候选的来源视角、生成阶段、种子、完整核查序号、完整成本、可行性
和解签名。

### B：机制感知破坏—修复搜索

B 不调用 PyVRP 种群、交叉、HGS 教育或路线池 MIP。它从与 A 完全相同的初始可行解
出发，独立进行以下循环：

1. 根据完整解中的时间窗余量、续航余量、车场归属、车辆类型、充电时段和成本/排放
   贡献，选择一段需要重构的路线区域；
2. 使用以下三类破坏之一：
   - 同一路线连续客户串移除；
   - 整条路线移除，用于重新选择车场、车型和发车安排；
   - 两个车场之间的成对路线片段移除，用于跨场交换客户；
3. 使用 regret 式修复建立客户顺序，但允许在广州/深圳车场、燃油车/电动车之间重新
   选择；候选短名单必须经现有完整完成器补齐充电与时间安排；
4. 每提交一个完整候选给完整评价器就消耗一次主预算；不可行候选也计数，不得免费
   丢弃；
5. 接受规则、破坏规模和算子权重在预注册后固定，不能根据结果临时调整。

B 的修复不得重现历史错误：不得忽略时间窗、固定车辆成本、有限车队、充电顺序、
地域参数映射或跨场约束；不得把增加车辆数当作免费操作。

### A+B：双向协同混合搜索

A+B 不是“A 跑完再让 B 收尾”，也不是“A 与 B 各跑一次后取较好值”。固定循环为：

1. A 执行一个 HGS 搜索阶段并产生多个候选；
2. 完整模型从中确认可行且有差异的精英解；
3. B 从这些精英解中选择起点，执行有预算上限的破坏—修复；
4. B 产生的完整可行解若通过接受规则，必须通过现有解投影接口送回下一阶段 HGS
   种群；
5. 下一阶段 HGS 必须实际引用该解，而不是只把它放在最终候选列表中；
6. 搜索结束后，仅在 A+B 自己产生的候选中执行完整模型最终择优。

每次双向传递必须记录：

- `source_algorithm`：解来自 HGS 还是破坏—修复；
- `parent_signature` 与 `child_signature`；
- `transfer_direction`：`HGS_TO_RR` 或 `RR_TO_HGS`；
- `accepted_into_next_hgs_epoch`；
- `complete_evaluation_index`；
- 送回 HGS 后是否产生了不同签名的后代；
- 该后代是否进一步改进完整成本。

只有同时观察到 `HGS_TO_RR` 和 `RR_TO_HGS`，且后者确实进入下一阶段 HGS，才可称为
“协同混合”。只有最终取优而没有回送，判为 `HALT_NOT_A_COOPERATIVE_HYBRID`。

## 5. 公平比较规则

三臂必须使用：

- 同一 China81 输入文件及其哈希；
- 同一日期、城市、经纬度区域、电价、碳强度、柴油价、车队和充电桩参数；
- 同一初始完整可行解及其签名；
- 相同种子集合；
- 同一个完整完成器、`cost.py`、`check.py` 和 `exact_china81_score`；
- 相同的完整候选评价总数；
- 相同的安全墙钟上限，但墙钟只负责防止失控，不是主要预算；
- 独立的随机流派生规则，禁止 A+B 偷用 A 或 B 的正式结果作为热启动。

完整评价次数是唯一主预算。首次微型门为每臂 80 次；确认门和后续正式 E2 为每臂
280 次。A+B 的 280 次是 HGS 完整候选核查与破坏—修复完整候选核查的总和，不是
`280 + 280`。所有不可行、重复和被拒绝候选均如实入账。

A+B 的固定分配为约 60% HGS、40% 破坏—修复，且共同初解在每臂各计一次：

- 80 次门：`1 + 16(HGS) + 16(RR) + 16(HGS) + 15(RR) + 16(HGS)`；
- 280 次门：`1 + 56(HGS) + 56(RR) + 56(HGS) + 55(RR) + 56(HGS)`。

该分配在读取新算法结果前冻结，只表示完整评价次数，不冒充相同墙钟。A+B 的 HGS
内部总迭代数同步取 A 的 60%，避免在完整评价次数之外偷偷保留 A 的全部 HGS 算力。

除完整评价次数外，还要分别披露 HGS 内部迭代数、破坏—修复尝试数、CPU 时间、
墙钟时间和峰值内存。不得把“相同完整评价次数”写成“相同墙钟”或“相同总算力”。

## 6. 开发集与确认集

开发实例不得根据正在运行的 v7 中间结果选择。使用输入结构和固定哈希规则，在小、
中、大三个规模层各选一题，且三个题分别来自京津冀、珠三角、成渝。登记后不得因
结果难看换题。

这三题只用于开发和失败定位，必须在最终论文中标为开发题。若新算法进入正式 E2：

- 81 题全部结果可作描述性汇总；
- 主要确认性结论以其余 78 题为准；
- 三个开发题单列，不混入“完全未见数据”的表述。

开发过程中只允许一次实现性修复窗口：修复代码错误、账本错误或违反本合同的行为。
任何为改善成本而改变算子、破坏比例、接受规则或预算的行为都算重新设计，必须换新
编号并重新选开发题；不能在同一编号下反复调参救援。

## 7. 分阶段验收

### G0：零搜索行为门

使用人工构造的小解，不运行优化，只验证：

- 三类破坏都能产生不同签名；
- 修复会实际考虑两个车场和两种车型；
- 完整完成器负责充电与时间安排；
- 不可行候选也消耗预算；
- HGS 解能进入 B，B 的解能投影并进入下一 HGS 阶段；
- 全部地域和时间参数绑定保持不变；
- 账本可证明 A+B 不是最终取优伪混合。

任一失败即 `HALT_G0_HYBRID_SEMANTICS`。

截至 2026-07-24，人工小解的静态子门已判
`PASS_G0_STATIC_SEMANTICS__REAL_BUNDLE_PREFLIGHT_PENDING`：预算、客户/充电站
区分、五个静态专用操作的实际效果、动态冻结前缀的结构口径、缓存身份和双向谱系
11/11 通过；19 项轻量单元测试通过。该子门不加载真实 China81、没有搜索，也不证明
算法质量或 1+1>2。真实 bundle 的零搜索解码、完整评价及投影回放仍是 G0 剩余硬门。

### G1：三题单种子微型门

三题 × 种子 1 × A/B/A+B，每臂 80 次完整评价。必须同时满足：

- 9 个运行全部完成、全部最终可行、独立重算逐位一致；
- A+B 相对 A 和 B 均无超过 `1e-9` 的成本劣化；
- A+B 至少在两题上严格优于 `min(A, B)`；
- 至少一题出现可核验的“B 改进解回送 HGS，后续 HGS 后代再次改进”；
- A+B 的 80 次完整评价精确闭合，无隐藏免费评价；
- 不得因墙钟上限提前截断。

不满足即停止该候选，判 `STOP_G1_NO_HYBRID_GAIN`，不得在相同三题上调参救援。

### G2：三题三种子确认门

G1 通过后，三题 × 种子 1--3 × A/B/A+B，每臂 280 次完整评价。G1 的种子 1 必须
从零重跑，不复用开发成绩。必须同时满足：

- 27 个运行全部可行并独立重算一致；
- A+B 对 A 的 9 个配对中无负，至少 5 个严格胜；
- A+B 对 B 的 9 个配对中无负，至少 5 个严格胜；
