## 1. 任务一：Z3 在求解什么，是否需要 Z3

### 1.1 第 2029 行模型和 assumptions

- **FACT：** `run_e3e6_formal.py:1936-1962` 为每个“客户—允许目的场—路线槽”建立布尔变量；每个客户恰好进入一个槽，每个槽施加载重上限。路线槽数等于该场 D2-A 的油车数加电车数。
- **FACT：** `run_e3e6_formal.py:1987-1998` 先把所有两客户不可行组合加入路线子集 cut；`2037-2083` 对 SAT 模型中的路线组调用既有路线可行性检查，把失败组缩成不可约失败子集，再对所有对称槽加入 lazy cut。
- **FACT：** `destination_assumption()` 在 `2000-2012` 返回“该改派客户被放进指定目的场任一槽”的 `Or`。`2023-2026` 的 `assumptions` 是当前词典序前缀中每个客户的这类目的场固定式；它们不固定后缀客户，也不固定具体路线槽。
- **FACT：** `solver.check(*assumptions)` 在一次 `exact_completion(prefix)` 内会因 lazy route cut 重复调用；外层还会为全次近映射、空前缀和逐客户词典序候选前缀调用 `exact_completion`。因此调用次数是“所有前缀尝试数 + 所有被路线 cut 拒绝后重解数”，不是一个源码常数。
- **FACT：** 第 57 单元为 150 客户、50% 名义错配，前缀全次近检查含 75 个目的场 assumptions。取证探针在约 408 秒内未返回，`solver_checks` 只在函数返回后写产物，所以不能从 0 字节日志伪造“已完成调用次数”；743 个采样中的 728 个落在 `solver.check` 调用链，只能证明当时主要墙钟位于该调用。

### 1.2 当前 Z3 路径与任务卡的语义差异

- **FACT：** 第 2029 行所在的当前路径求的是“存在一个不超过给定路线槽数的任意可行集合分区”。它没有要求这些路线槽恰好等于冻结 First-Fit 逐客户处理得到的路线组。
- **FACT：** 最终复核 `2204-2219` 只检查 Z3 给出的每个路线组本身可行、覆盖完整且槽数不超限，没有再运行 `_pack_depot` 比较该映射的冻结 First-Fit 结果。
- **INFERENCE：** 该路线槽模型是物理可分组性的模型，但它比任务卡要求的“该映射经过冻结 First-Fit 后不超上限”更宽；不能把它当成任务卡 First-Fit 存在性判定的等价实现。

### 1.3 采用的构造器

- **FACT：** 新实现为 `baselines/china_e3_e7/e3e6_inputs_20260730/first_fit_lexicographic.cpp`，由 `build_inputs.py` 调用。它对每个完整后缀严格执行冻结客户序、First-Fit 首个可追加路线、只在需要时新开路线、路线数超过 D2-A 总车数才剪枝。
- **FACT：** 它不使用 Z3。安全剪枝仅包括总需求/Hall 必要条件、可证明的成对不相容下界和 First-Fit 已超上限；任何启发式只负责寻找见证，失败后仍进入精确枚举。
- **FACT：** Python 在 C++ 返回 PASS 后重新调用既有 `_pack_depot`；C++ 路线组与 Python 路线组有任何差异都会 `HALT_CPP_PYTHON_FIRST_FIT_DISAGREEMENT`。
- **FACT：** 性能实现先后消除了两类不改变判定的复制：搜索期间不再复制整条客户列表；递归时只替换当前目的场状态并在失败后可逆回滚。已知 `cn-prd-150c-01/50%` 工程探针中，原 C++ 为 25.437438 秒，去客户列表版为 9.686368 秒，最终回滚版为 5.896163 秒；映射、路线组、节点数和路线检查数一致，累计约 4.31×。
- **FACT：** 最终版本再次完成 56 单元等价检查，结果 56/56、0 不一致。
- **FACT：** 失败的替代探针均已明确拒绝：失败模式缓存减少了路线检查但墙钟反而变慢；轻量 membership-SAT 在 10 分钟内检查约 1.5 万个完整映射、加入约 1.79 万个精确 no-good，仍无 SAT/UNSAT；精确 Z3-FirstFit 在约 2 分钟内接近 1 GB RSS且未返回；只负责找见证的结果盲局部修复探针运行约 4 分钟仍无见证，已终止并完全撤回，未替换权威二进制。
- **FACT：** 撤回局部修复探针后，主 C++ 源码已重新编译并再次通过 56/56、0 不一致等价门；日志为 `equivalence_post_probe_revalidation.log`。这消除了“源码时间戳已变但等价证书仍指向旧编译物”的审计歧义。
- **INFERENCE：** Z3 不是该判定的必要工具；但完整映射存在性仍需要精确组合搜索或等价的约束求解。最终 C++ 显著降低了常规单元的墙钟和内存，却尚未使所有高负载 50% 格在可接受时间内终态化。

## 4. 任务四：旧 L-main 与当前 China81 的错配语义

### 4.1 是否一致

- **FACT：** 旧 L-main 只有 D0/D1 两个场。`e3_mismatch_fair_probe_20260713.py:52-64` 只允许 25% 和 50%，在两场原责任组中各随机无放回抽取同样数量，再做 D0→D1、D1→D0 的对称互换；它不按客户—车场距离决定目的场。
- **FACT：** 当前 China81 先按原责任场做 largest-remainder 比例分配，用任务/实例/档位/原场/客户的 SHA-256 冻结选客；目的场按有向“车场→客户”距离取绝对次近，次近等于原场者不入选，完整 First-Fit 被阻断时才按第三/第四近顺延并跳过原场。
- **FACT：** 当前域含 3 或 4 个场，改派不要求两两对称回交换；因此两者只有“搜索前冻结一张非零责任错配表”这一高层语义相同，选客、目的场、场数和平衡结构均不同。
- **INFERENCE：** 旧 L-main 的 25%/50% 数值不能按同名百分比直接移植到 China81。

### 4.2 旧大效应的条件

- **FACT：** 旧 25%/50% 展品使用固定 L-main 200c、固定错配表、零跨场费和十个搜索种子。合作臂仍锁定原每场 7 油+7 电，即系统总 14 油+14 电。
- **FACT：** 25% 的各自经营测量起点需要 D0=8 油+8 电、D1=8 油+7 电；50% 需要 D0=7 油+12 电、D1=8 油+8 电。两档都超过至少一个场原 7+7 本地资产，因此被明确标为“资产内不可行后的测量值”。
- **FACT：** 历史比较是“合作最终解 vs 各自经营测量起点”。合作搜索为每种子 4000 次评价，各自经营测量子问题每场 200 次评价；这不是 LOCK/FREE 同起点同预算的净机制比较，也不是等算力证据。
- **INFERENCE：** 旧 16.55%/24.72% 大效应主要与“责任错配把独立经营推到本地资产瓶颈之外，而共同资产池仍能通过跨场服务排开”这一条件共同出现；不能只归因于名义错配百分比。

### 4.3 China81 上的对应条件和最可能维度

- **FACT：** 当前主实例 `cn-prd-150c-01` 的 D2-A 车队为：东莞 4 油+1 电、佛山 4+1、广州 9+3、深圳 10+3，总上限分别为 5、5、12、13。
- **INFERENCE：** 与旧条件相对应的 China81 条件应是：某一 LOCK/I 责任场在其本地、分车型、含充电与时间窗的冻结资产下出现真实瓶颈，而 FREE/U 在不扩大系统共同资产的前提下能通过跨场服务/资产共享消除该瓶颈。
- **FACT：** 本次输入构造只检查“油车数+电车数”的未分型 First-Fit 路线数；它不做车型分配、续航/充电完成或成本评价。因此“输入技术上可构造”既不能证明上述分车型资产瓶颈存在，也不能证明 FREE 会改善。
- **INFERENCE：** 若未来经用户批准要寻找与旧展品相近量级的效应，最可能起作用的设计维度不是单独提高错配百分比，而是“责任—地理错位的方向和集中度 × 各场异质有限车队/充电资产瓶颈 × FREE 的共同池调剂空间”。最应先检查的是责任图是否把需求系统性推向小车队或不合适车型/充电能力的场，而非把 25% 或 50% 当作必然有效阈值。
- **FACT：** 0%-25% 在旧证据中没有采样；本报告不声称任何 China81 档位一定产生效应，不修改任何档位、预算或实例。
