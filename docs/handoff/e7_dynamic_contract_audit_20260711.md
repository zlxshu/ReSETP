# E7动态需求正式合同与合法性审计（2026-07-11）

状态：`HALT_CURRENT_M1_DYNAMIC_ENTRY / CONTRACT_PREPARED`。本文件只记录当前事实和后续门槛，不启动E7，不修改正在运行的E3。

## 人话判决

当前M1分支上的动态入口不能直接跑正式实验。它虽然能识别新增、取消和需求变化，但正常阶段仍调用旧`run_alns_wouda`；下一阶段的旧计划会被重新拼成“车场—剩余客户—车场”，没有真正从车辆当前位置、当前时间、剩余载重和剩余电量继续。最后收尾还会再次调用`_solution_for_customer_subset()`生成`FINAL_`路线，把剩余客户重新安排。阶段表中的`min_fairness_ratio`也仍硬编码为`off`。

因此，当前入口最多证明“事件触发壳存在”，不能证明动态staged hybrid、实时车辆状态继承、动态公平或动态低碳。现在跑五条正式事件流只会得到昂贵但不能用于论文的新数字。

历史`dr-x86`分支曾修复“最终收尾偷偷重排锁定客户”的漏洞，但该事实不能凭聊天记录直接算作当前M1已修。E7启动前必须逐行核对并最小移植相关提交，确认不会把x86绝对结果或DR训练线带入M1。

## 第一阶段：动态合法性门

先做四个极小测试，不训练、不跑事件流榜单：

1. 途中继续：车辆已经离开车场时，下一阶段从当前节点或在途位置、当前时间继续，不能瞬移回车场。
2. 低电继续：下一阶段继承剩余SOC，不能自动恢复满电；必要充电必须进入路线和充电桩占用。
3. 充电继承：上一阶段尚未结束的充电继续占用原充电桩，下一阶段不得让其他车辆同时使用。
4. 锁定保护：已执行和已承诺客户不换车、不换顺序；最终收尾不得调用新求解器重排锁定部分。

测试中应让旧ALNS入口和`_solution_for_customer_subset()`最终收尾路径直接抛异常。动态流程仍能完成，才证明旧路径确实被移除，而不是只改了导入名称。

每阶段还必须满足客户守恒：原有效客户+合法新增-合法取消=已服务+已锁定待服务+可重排待服务；任何客户不得凭空消失或重复服务。

## 第二阶段：冻结动态求解合同

正常阶段全部调用当前M1的staged hybrid入口，使用280 kWh、真实48槽碳强度、统一评价器和检查器。旧粗糙碳destroy/repair保持关闭；低碳作用来自已验证的固定路线充电调度。

每条事件流给定一个总评价预算，按实际触发阶段预先分配，所有动态方案使用相同总预算。不能每阶段各拿4000次、再与只拿4000次的静态方案直接比算法质量。若论文另报“每次重规划固定预算”的运营场景，必须同时报告累计评价数和累计墙钟，不能与等总预算账本混在一起。

一次性提前知道所有事件的静态方案是完美信息下界，只用于计算信息代价，不能写成现实可执行基线。真正的动态对照必须处在相同信息条件下。

## 第三阶段：最小事件流比较

先使用一个中等规模L-main v3实例和3条固定事件流，每条都包含新增、取消和需求变化。合法性和机制信号成立后才补到5条。

配对方案为：

- `no_reoptimization`：事件发生后不改原计划；新增订单按预注册拒单/未服务规则记账，不能假装提前知道。
- `rolling_full`：staged hybrid+协同+已由E6确认的公平阈值+低碳充电。
- `rolling_no_cooperation`：客户只能由归属车场吸收，其他条件相同。
- 第四臂只选择前面证据更强的一项：若E6公平阈值确实激活，则用`rolling_fairness_off`；否则用`rolling_carbon_naive`。不做无意义全因子排列。

## 三类交互证据

动态×协同：报告新增/变更订单中由非归属车场服务的数量、需求量和比例，至少给一个路线级案例；对比关闭协同后的接纳率、成本和可行性。

动态×公平：每阶段报告两个车场的独立基准、合作利润、利润比和约束状态。若仍显示`off`，只能判未完成，不能写公平参与动态决策。

动态×时变碳：报告事件发生前后EV/CV分工、充电次数、每次充电原/新时段、充电电量加权碳强度和新增碳排。必须用同路线或严格配对的碳盲对照证明差异来自充电时间；只报累计总碳不够。

三项不必强行同时显著。合法性通过但交互弱时，论文降级为“滚动重规划接口与车辆状态继承可行”，不继续扩大事件流或改参数制造故事。

## 每阶段必须保存

事件清单和触发原因；当前时间；车辆位置或在途弧；剩余SOC和载重；正在进行的充电及充电桩占用；已服务/锁定/待服务/取消客户集合；冻结路线签名；阶段预算和累计评价数；阶段及累计成本/碳；跨场服务；每场利润比；最终未服务和重复服务客户数；完整保存解和hash。
