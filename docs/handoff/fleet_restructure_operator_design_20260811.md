# 车队级重构算子：必要性复核与备用设计

日期：2026-08-11  
任务边界：只读现有实现、定位文献、运行秒级合成诊断；不跑正式实验，不修改保护文件、China81 或活动结果目录。

## 结论先行

**FACT——终端 Claude 的判断只有前半句成立。** DSS／协调器确实是排程裁判：它接收已经构造好的 `reference`、`candidate` 和 `changed_duty_ids`，再判断连续 SOC、非线性充电、趟间时序及共享容量是否可排（`schedule_oracle.py:1062-1082`）。它不负责决定把哪一趟交给哪辆车。

**CORRECTION——“当前动作生成器在结构上永远不会提出整车停用或柴油整日工作量转给电车”不成立。** 当前私有 Problem-HGS 已经有三条直接通道：

1. `WholeDutyTypeExchangeMove` 交换同车场一辆 EV 与一辆 CV 的完整、未锁定趟链（`operators.py:572-620`）。一边为空 Duty、另一边非空时，动作执行后就是“柴油车清空，电车接走全部趟”。
2. `MechanismProposalEngine` 会枚举上述 EV/CV 整 Duty 动作（`proposals.py:108-141`）；它没有排除“空 Duty 对非空 Duty”。
3. 复制内核的路线局部搜索被接成当前私有搜索的首个教育阶段（`integrated_private.py:215-229,597-622`）。内核在搬空来源路线时显式扣除来源车辆固定成本（`third_party/setp_hgs_kernel/.../Exchange.h:86-105`；`SwapTails.cpp:40-55`），解码器先把全部注册车辆置为空，再只填充内核返回的非空路线（`kernel_proposals.py:299-329`），因此它可以返回“某个实体 Duty 变空”的完整骨架候选。

固定车队注册表本身也把空 Duty 规定为合法状态（`fleet_registry.py:12-70`），并专门检测空／非空变化（`:73-108`）。现行消融 A3 已定义为“A2 + 固定注册表内空 Duty 启用／清空”（`solver/scripts/run_private_ablation.py:66-91`）。所以再新增一份同义的 `fleet_restructure.py` 和 `A4-fleet`，会重复现有能力与现有消融身份。

**执行决定（代理按用户给出的停止条件执行）**：本轮不创建 `fleet_restructure.py`，也不把重复能力登记为新臂。下面保留标准文献位置、现有能力仍未证明的部分，以及只有在 A3 轨迹证明确实存在“定向可达性缺口”时才应启用的备用设计。

## 一、现有能力到底覆盖到哪里

| 目标动作 | 当前能否生成 | 代码证据 | 尚未证明 |
|---|---|---|---|
| 把一辆 CV 的全部趟交给同车场空闲 EV，并停用该 CV | 能 | `WholeDutyTypeExchangeMove` 交换完整趟链；生成器枚举空／非空 EV-CV 对 | 在真实实例中能否通过 DSS、完整评价并被接受，当前为 `UNKNOWN` |
| 把一辆车的客户／趟逐步并入其他已启用车辆，最终少用一辆车 | 结构上能 | 内核 relocate 搬空全路线时扣固定成本；SwapTails 可搬空末趟；内核完整骨架解码允许注册 Duty 为空 | 多趟情况下部分动作受“不能跨 reload depot”限制；能否跨越需要暂时变差的中间态为 `UNKNOWN` |
| 一次原子动作把多趟分别分配给多辆接收车，再由 DSS 联合排程 | 当前没有发现专门的定向生成器 | `NOT FOUND`：现有整 Duty 换型只是一对一交换；复制内核靠局部搜索形成完整骨架 | 这才是可能存在的“定向 route elimination”缺口，但不能从弱结果倒推出它必然存在 |

秒级合成诊断构造一辆含两趟的 CV 与一辆空 EV，调用现有 `WholeDutyTypeExchangeMove` 后得到：CV `trips=()`，EV 获得原 CV 的两条客户链，所有客户链保持。诊断输出为：

```text
PASS existing whole-duty type exchange: CV active->idle, EV idle->active, all trips preserved
```

这证明“柴油整日工作量整体转给电车”不是搜索空间中缺失的动作。它没有证明该动作在 China81 上经 DSS 后有正收益；本轮按边界没有读取活动试验目录，也没有运行真实算例。

## 二、文献中的标准做法与适用前提

### 2.1 路线／车辆数最小化

1. **Nagata and Bräysy (2009)**, *A powerful route minimization heuristic for the vehicle routing problem with time windows*, Operations Research Letters 37(5):333-338, DOI [10.1016/j.orl.2009.04.006](https://doi.org/10.1016/j.orl.2009.04.006)。论文把 VRPTW 按词典序处理：先减少路线数，再缩短距离；核心是反复 `DeleteRoute`，把被删路线客户放入 ejection pool，再用强化插入／扰动恢复可行解。**适用前提**是单车场、同质车、每车一条 depot-to-depot route、容量和时间窗。仓库能确证论文页幅为 333-338；`DeleteRoute` 的精确原文页码当前 `UNKNOWN`，不伪填。
2. **Bräysy et al. (2008)**, *An effective multirestart deterministic annealing metaheuristic for the fleet size and mix vehicle-routing problem with time windows*, Transportation Science 42(3):371-386, DOI [10.1287/trsc.1070.0217](https://doi.org/10.1287/trsc.1070.0217)。作者稿 pp.3-4 的 `ELIM` 对每条候选路线依次尝试：删除整路客户，按关键性排序，枚举所有其他路线和插入位置，用含固定车辆成本的总成本选最佳可行插入；任何客户插不回去，或插入增量超过消车节省，就回滚整次尝试。**适用前提**是单车场 FSMVRPTW、每车一条路线、异质容量／固定成本、时间窗；没有实体车多趟、跨趟 SOC 或充电资源。
3. 仓库复制的 PyVRP 上游还保留 `minimise_fleet()`：每次把可用车辆减 1，再求第一个可行解（`third_party/setp_hgs_kernel/setp_hgs_kernel/minimise_fleet.py:8-85`）。同一文件明确拒绝多车型与可选客户（`:18-22,45-57`），所以不能直接用于本项目有限异质车队。

### 2.2 弹射链

**Potvin and Naud (2011)**, *Tabu search with ejection chains for the vehicle routing problem with private fleet and common carrier*, Journal of the Operational Research Society 62:326-336, DOI [10.1057/jors.2010.102](https://doi.org/10.1057/jors.2010.102)；可核作者报告 [CIRRELT-2009-50](https://www.cirrelt.ca/documentstravail/cirrelt-2009-50.pdf) pp.7-9。其做法是：把客户插入另一条路线，挤出该路线的另一个客户，再继续传递；用分层图上的最短弹射路径限制链结构，并规定每条路线至多发生一次弹射，以保持增量费用可计算。作者报告 p.17 同时指出异质车队有收益，但计算代价明显。**适用前提**是每辆私有车一条路线，容量／路线时间等路线级约束；不含本项目的多趟连续能量状态和共享充电资源。

### 2.3 异质电动车队中的车型—路线联动

**Hiermann et al. (2016)**, *The Electric Fleet Size and Mix Vehicle Routing Problem with Time Windows and Recharging Stations*, EJOR 252:995-1018, DOI [10.1016/j.ejor.2016.01.038](https://doi.org/10.1016/j.ejor.2016.01.038)。期刊 pp.1003-1004 给出 `Resize`（路线客户顺序不变、改变所配车型）和 `RelocateAndResize`（搬客户并同步尝试车型变化）；跨车型动作必须用新车型重新处理路线，充电站位置再由标签过程优化。**适用前提**仍是一车一路；没有同一实体车的多趟 Duty、趟间 SOC 继承、多个车场或跨车共享充电容量。

### 2.4 本项目不能直接照搬的地方

| 文献中的对象 | 本项目对象 | 迁移影响 |
|---|---|---|
| 一辆车等于一条路线 | 一辆实体车包含多趟 Duty | “删路线”必须改写为“清空实体 Duty”；不能把一趟消失误报成少一辆车 |
| 载重／时间窗决定插入可行性 | 还要连续 SOC、非线性充电、趟间因果时钟 | 容量或松弛量只能排序，不能代替 DSS 裁决 |
| 路线彼此主要通过客户覆盖耦合 | 充电站容量让多辆车的排程耦合 | 多个接收 Duty 必须交给同一协调器联合裁决，不能逐车独立判可行后拼接 |
| 单车场或路线车场固定 | 多车场、实体车有 home depot | 车辆身份和所属车场不得随客户搬移；跨场服务还须保留现行费用与责任语义 |
| 通常可更换抽象车型 | 有限注册实体车槽位与动态锁 | 只能在注册表内激活／清空；已执行历史和锁定前缀不可移动 |

## 三、为什么端点天花板不能证明“必须新增一个算子”

效应天花板报告确证九题全电构造相对全油构造的成本差为 371.240-2027.318 元（17.109%-26.235%），排放差为 47.239%-82.354%（`solver/reports/effect_ceiling_forecast_20260811/report.md:42-59`）。这说明混合车队的可行域有大尺度作用空间。

但端点同时改变了车型、启用车辆数、路线能耗和电／油费用，不能单独识别“缺失定向算子”就是当前瓶颈。当前代码已经能生成整 Duty 换型和 Duty 清空；真正缺的证据是 A3 轨迹账：目标动作有没有被提出、DSS 各状态各多少、完整评价后有没有被接受。读取这些活动结果不在本轮授权范围内，因此当前效果为 `UNKNOWN`。

另外，2026-07-19 历史上已经实现过一套“整条燃油路线退役—待安置池—regret-2—一次腾位”的定向算子。绑定行为题形成了全电候选，但最佳全电候选比源解贵 64.6248 元，0 次接受，随后按合同停止（`docs/handoff/memory/fuel_route_retirement_ev_repack_20260719.md:15-36`）。该证据属于退役 ALNS／旧算例时代，不能作为当前性能结论；但它足以说明现在不能换名复活同类实现、忽略既有负结果。

## 四、只有证明确有可达性缺口时才启用的备用设计

以下是**条件性设计，不是当前开工决定，也不新增参数或阈值**。触发条件只有一个：在现行 A3 的已保存轨迹中，确认目标车队状态有明确改善空间，但现有整 Duty 交换与内核骨架从未生成可供 DSS 裁决的相应候选。

### 4.1 来源车辆候选规则

不把多个指标加权成一个自造分数。按外部消融开关一次选择一种规则，并用车辆 ID 稳定决胜：

| 规则 | 用途 | 代价／局限 |
|---|---|---|
| 工作量最少优先 | 最接近经典 route elimination，待重分配趟少 | 可能忽略工作量大但昂贵的柴油车 |
| 完整评价中的单位服务成本最高优先 | 直接针对昂贵 Duty；分母分别报告完成需求量或客户数 | 成本归因必须来自现行完整评价；零服务空 Duty 不参与来源排序 |
| 非空柴油车优先，且同车场存在空闲 EV | 定向检验“柴油整日工作量转电车” | 只改变车型时不会减少总启用车数；EV 排程可能更紧 |
| 固定成本可节省额最高优先 | 针对真正消车 | 当前车型固定成本若相同会大量平局，辨别力可能为零 |

### 4.2 趟的重分配顺序

1. 在事务副本中把来源 Duty 标记为待清空，原解保持不可变。
2. 对每一趟，先枚举注册且未锁定的接收 Duty 和合法插入位置。
3. “可放位置最少”的趟先处理；平局依次按原来源车辆 ID、原趟序号和客户 ID 串决胜。这里的“可放”必须来自 DSS／协调器返回 `FEASIBLE`，不能用代理载重或时窗阈值冒充。
4. 每次结构分配都把所有受影响 Duty 一起交给协调器；只有最终来源 Duty 为空、客户与需求完整覆盖、且完整评价通过，才把原子候选交给 HGS 接收逻辑。中间状态不进入种群。

### 4.3 接收车辆与“余量”

“有余量”不设用户未批准的 SOC、时间或载重百分比门槛。严格定义为：加入该趟后，协调器至少返回一个完整 `FEASIBLE` 排程见证。载重剩余、预计时间松弛、SOC 松弛只可用于确定性排序；它们不能越过完整评价。EV 可优先排序，但优先不等于放宽可行性。

### 4.4 回退与三态结果

- `FEASIBLE`：保留协调器前沿中经完整评价最优、指纹稳定决胜的候选，再按现行 HGS 接收准则判断；不在算子内部另设改善阈值。
- `INFEASIBLE`：只有协调器穷尽其合同规定的完整搜索空间后才能记录。
- `SEARCH_EXHAUSTED`：记录为“未知／未裁决”，不得计入不可行率；若没有其他 `FEASIBLE` 完成分支，算子返回 `SEARCH_EXHAUSTED`，原解逐位不变。
- 任一异常、客户丢失／重复、车辆身份变化、完整评价失败：原解逐位不变并保留错误状态。

当前 `education.py:131-158` 会把协调器所有非 `FEASIBLE` 状态映射成外层 `REJECTED_CHARGING`，但同时在专项账中保存 `channel:SEARCH_EXHAUSTED` 或 `channel:INFEASIBLE`。若将来实施专用算子，接口应把三态直接保留到算子结果；不能用统一的“充电拒绝”标签做科学统计。

### 4.5 确定性与随机流

备用算子不接收主 GA RNG，也不调用 `random`／NumPy RNG。车辆、趟、接收位置、DSS 前沿和最终候选都使用稳定元组排序；最后以候选指纹决胜。两次输入指纹、评价合同和 DSS 合同相同，输出状态与候选指纹必须相同。这样不会推进主 GA 随机流。

## 五、“不可能是挂件”这句话需要纠正

**INFERENCE**：成功事件是离散结构变化，但这不等于算法贡献必然非挂件。

- 真正“消车”成功：总非空 Duty 数减少 1，固定成本发生离散变化。
- “换型”成功：非空 CV 数减少 1、非空 EV 数增加 1，总用车数可不变；收益主要来自车型相关能源、里程、碳和排程差。
- 失败、`INFEASIBLE` 或 `SEARCH_EXHAUSTED`：原解指纹不变。

算子仍可能成为挂件：它可能从不成功、成功极少、与 A3 现有动作重复，或换型后的排程／能耗代价抵消固定成本与油电差。只有同预算消融能回答。应逐臂报告：

- 尝试数、生成完整候选数；
- `FEASIBLE`、`INFEASIBLE`、`SEARCH_EXHAUSTED` 分开计数；
- 接受成功数、成功种子数；
- 被清空车辆数，以及换型次数（两者分开）；
- 固定成本、柴油／电费、其他车型里程成本和碳成本变化；
- 直接、间接和总排放变化；
- 完成客户数与完成需求量；
- DSS 调用时间、完整评价次数和固定墙钟下的最终净值。

## 六、消融身份

现行事实源已经把 A3 定义为“A2 + 内生车队选择／注册空 Duty 激活和清空”；旧 A4（碳／电价目标项）已从当前施工包移出（`duty_schedule_core_design_20260810.md:40-50,89-99`；`experiment_master_map_20260811.md:34-35`）。因此：

- 本轮不新增 `A4-fleet`，否则与 A3 重复，也会重新制造 A4 身份冲突。
- 若将来轨迹证明 A3 的问题是“能激活／清空，但缺少定向多接收车消除动作”，可把新增开关暂记为候选名 `A3F-directed-fleet`，只表示“A3 上增加定向生成器”；是否正式采用该名称和是否增加新臂仍由用户批准。
- 新臂若获批，必须与 A0-A3 同种子、同预算，A3 是直接对照；不能只拿 A0 作对手夸大增量。
