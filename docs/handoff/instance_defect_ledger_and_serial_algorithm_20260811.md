## 第一部分　算例缺陷台账（`FACT`，全部可复算）

被查算例：`cn-prd-50c-01-V2-LOCATIONS`（珠三角 50 客户，广州＋深圳两车场，各带一个公共充电站）。

### 缺陷 1｜多车场协同的作用条件为零（阻断"协同"与"利益分配"两大机制）

| 量 | 实测 | 含义 |
|---|---|---|
| 两车场直线距离 | 64.1 km | 广州黄埔 ↔ 深圳龙华 |
| 客户到两场距离差 < 10 km 的"可争夺客户" | **0 / 50** | 没有任何一个客户处在两场势力交界 |
| 归属城市 ≠ 最近车场的客户 | **0 / 50** | 每个客户的最近车场恰好就是它所属城市的车场 |
| 到广州场距离中位 | 76.6 km | 深圳客户离广州场极远 |
| 到深圳场距离中位 | 23.0 km | 客户紧贴各自城市车场 |
| 见证解中的跨场服务次数 | **0** | 构造时即无跨场 |

`INFERENCE`：用户要求"给客户分车场是算法的优化动作"。在本算例上这不是优化动作——每个客户有且只有一个几何上更优的车场，任何跨场指派都是纯亏损。**协同配送与多车场利益分配在此算例上的效应恒为零，且是构造决定的，不是搜索能力问题。** 这与记忆 `mechanism-condition-absent-in-instances`（E3 错配率 0/150）是同一个病，本次在几何层面确认了根因。

### 缺陷 2｜配送时间窗与最清洁时段完全重合（阻断"时变碳强度"）

广州电网 2025-02-12 逐小时投影剖面（以48个30分钟积分行存储，`china81_runtime_parameter_authority_v4_20260723/tariff_carbon_hourly_calendar.csv`）：

| 时段 | 场站电价（元/kWh） | 碳强度（kg/kWh） | 性质 |
|---|---:|---:|---|
| 00:00–07:30 谷 | 0.3182 | 0.2960–0.3574 | **最便宜、最脏** |
| 08:00–09:30 平 | 0.7921 | 0.2134–0.2661 | |
| 10:00–11:30 峰 | 1.3272 | 0.1120–0.1765 | |
| **12:00–13:30 平** | **0.7921** | **0.0355–0.0490** | **最清洁**（光伏大发） |
| 14:00–18:30 峰 | 1.3272 | 0.0360–0.2206 | 最贵 |
| 19:00–23:30 平 | 0.7921 | 0.2145–0.2262 | |

**电价与碳强度近乎完全反相关——这是一份极好的档案，本身没有问题。**

问题在客户时间窗：全部 50 个客户的服务窗落在 **11:58–18:29**（跨度 6.51 h），窗宽中位仅 **46.6 分钟**。

`INFERENCE`：**车辆正好在全天最清洁的 12:00–15:30 在路上跑，无法在场站充电。** 唯一的充电机会落在夜谷（便宜且脏）与早间峰段（贵且较清洁）之间。

### 缺陷 3｜碳价比盈亏平衡点低约 20 倍（单目标下清洁充电永不被选，属算术事实）

取最有利于清洁充电的一对时段比较（夜谷 vs 13:00）：

```
Δ电价 = 0.7921 − 0.3182 = 0.4739 元/kWh
Δ碳强度 = 0.3574 − 0.0355 = 0.3219 kg/kWh
盈亏平衡碳价 = 0.4739 / 0.3219 = 1.472 元/kg
现行碳价（china81.py:1016） = 0.07502 元/kg
```

`FACT`：**1.472 ÷ 0.07502 ≈ 19.6 倍。** 即使取最有利的时段配对，把充电从夜谷移到最清洁时段，每 kWh 省下的碳成本也只有多付电费的 1/20。

`INFERENCE`：在**单目标总成本最小化**下，任何搜索算法都不会选择清洁充电——这是算术必然，不是搜索失败。**先前把"充电择时"判为失败零件的结论需要改写：它不是零件坏了，是在这个碳价下这个机制在数学上不可达。** 出路只有两条：①双目标（P39 已批，排放列为独立目标，Pareto 前沿上自然出现清洁充电点）；②碳价情景（把碳价提到接近盈亏平衡点，作为政策情景分析）。**任何算法改进都不能替代这一步。**

### 缺陷 4｜容量不紧且两种车型载重几乎相同（阻断"混合车队装得多"）

| 量 | 实测 |
|---|---|
| 50 客户总需求 | 12 223 kg |
| CV 载重 / EV 载重 | 1 735 kg / **1 700 kg（仅差 2%）** |
| 容量下限所需车次 | 7.04 |
| 见证解实际车次 | 9 |
| 平均容量利用率 | **78%** |

`INFERENCE`：绑定约束是时间窗不是容量。且两种车型载重只差 2%，**"混合车队比纯电车队装得多"在现有车型参数下无法表达**——可表达的差异是**续航**（EV 77.28 kWh 电池 vs CV 加油），不是载重。若一定要讲"装得多"，须引入第三种更大载重的车型，属新的建模决定。

### 缺陷 5｜多趟的可行空间被客户时间窗封死

`FACT`：所有客户必须在 6.51 h 内服务完毕；见证解 9 条路线共 740.4 km，均值 82 km/路线。代码中未发现单车最长工作时长上限。

`INFERENCE`：**放宽"车辆可出勤时段"（例如允许 06:00 出车、24:00 收车）不解锁多趟**——第二趟仍必须挤进同一个 6.51 h 客户窗内。**只有放宽客户时间窗才能解锁多趟。** 这两件事必须分开决策：

- **甲：放宽车辆出勤时段**（客户窗不动）。仿真代价极低（真实车队本就早出晚归），解锁的是**充电时刻自由度**。
- **乙：放宽客户服务时间窗**。触碰标记为 `OBSERVED_JOINT_EMPIRICAL_DELIVERY_WINDOW` 的实证数据，仿真代价高，但**多趟机制只能靠它解锁**。

## 第三部分　串行传导算法设计（`PROPOSAL`）

### 3.1 对齐陈雨蝶的设计骨架

陈雨蝶 2025 模板（`docs/paper_submission_final/design_templates/陈雨蝶2025论文模板手册.md` §3）的叙述骨架是：

> 该算法以[主体算法]为主体，通过[策略A]、[策略B]和[策略C]进行优化，增强其[能力A]。

她的填法：遗传算法为主体＋改进两点交叉、动态灾变机制、多种群并行进化三个策略；消融从 7 个角度做。**零件全是成熟件，胜在"每个策略对着模型的一个特点、解决它带来的一个搜索困难"。**

`INFERENCE`：本项目照搬这个骨架，但把"策略"换成对着本问题各层决策的算子，形成一条**串行传导链**——上层决策改变下层的可行域，下层的真实代价回传成为上层的评价信号。

### 3.3 传导的关键：修掉唯一可指认的"零件打架"点

`FACT`：`kernel_proposals.py:399-434` 中，L4 路线搜索的代理成本对电车用的是**全天平均电价与平均碳强度**（分时类别价在48个等时长积分行上取日均；24个逐小时碳值各重复两次后取日均）；而真实评价按实际充电时刻计价（谷 0.3182、峰 1.3272，相差 4.2 倍）。

`INFERENCE`：L4 在用一个平均值猜 L5 会付多少钱，猜错时两层就打架——这正是用户担心的"零件打架"，也是当前唯一可指认的一处。**修法：让 L4 的代理成本按该路线预计的返场时段取价，而不是取全天平均。** 这是本设计里"传导"的实体：上层用下层的真实规则评价自己，两层不再各算各的。

`BOUNDARY`：此修法尚未实测，不得先当成结论。它必须作为一个独立的消融开关，与其它零件同样接受"关掉它是否变差"的检验。

### 3.4 消融表形态（对齐陈雨蝶 §3.4 逐组件加法）

主体（L4 单独）→ ＋L2 → ＋L5 → ＋SISR → ＋L1 → ＋L3，每步同种子配对、固定墙钟、10 次重复报 Best/Avg。**已知 L2 单独用为 0.00、必须与 L4 配合才有效**——这个"单独无效、组合有效"的形态正是 1+1>2 的最强证据形态，消融表要专门设计一行展示它。

## 第六部分　追加缺陷 6｜电车在本算例上严格优于油车，"混合车队"没有存在理由（2026-08-11 补查）

用户裁决混合车队卖点时提出的框架是"比较优势随任务条件与外部环境切换……真正的问题不是 EV 用得越多越好，而是什么条件下应该用 EV"。为验证该框架在本算例上是否可答，逐项复算两种车型的竞争关系。

### 6.1 三个维度全部由 EV 胜出（`FACT`）

**固定成本**：`prices.vehicle_fixed_cost = 170.0` 是**单一标量，两种车型相同**，不存在电车购置溢价。

**每公里运行成本**（EV 实测能耗 0.3641 kWh/km，取三条真实弧均值；CV 燃油 722.678 元 ÷ 740.404 km）：

| | 电费/油费 | ＋非能源里程 | 合计 |
|---|---:|---:|---:|
| CV | 0.9761 | 0.78 | **1.7561** |
| EV 谷电 0.3182 | 0.1159 | 0.67 | **0.7859** |
| EV 平段 0.7921 | 0.2884 | 0.67 | **0.9584** |
| EV 峰段 1.3272 | 0.4832 | 0.67 | **1.1532** |

**即使在最贵的峰段充电，EV 每公里仍比 CV 便宜 34%。**

**每公里排放**（CV 262.729 kg ÷ 740.404 km = 0.3548 kg/km）：

| 充电时段 | 碳强度 kg/kWh | EV 排放 kg/km | EV 比 CV 干净 |
|---|---:|---:|---:|
| 深夜最脏 00:00 | 0.3574 | 0.1301 | **2.7 倍** |
| 深夜谷电 03:00 | 0.3172 | 0.1155 | 3.1 倍 |
| 收车即充 18:30 | 0.2206 | 0.0803 | 4.4 倍 |
| 早间 09:00 | 0.2134 | 0.0777 | 4.6 倍 |
| 最清洁 13:00 | 0.0355 | 0.0129 | **27.5 倍** |

**续航与补能**：EV 满电续航 77.28 ÷ 0.3641 = **212 km**；见证解平均路线 82 km，单趟远不卡续航；两趟 164 km 仍在一次满电内。场站充电功率 22 kW、每场 2 把枪，但 `fleet_caps.csv` 中 `depot_charger_capacity_default = UNBOUNDED`——**充电桩数量约束默认不生效**。

### 6.2 结论与更正

`INFERENCE`：**在本算例的现行参数下，EV 在固定成本（相同）、每公里成本（各时段均更低）、排放（各时段均更低 2.7–27.5 倍）三个维度全面优于 CV，且续航与充电容量都不构成约束。最优车队是 100% 纯电，"混合"不是优化结果而是人为设定车队上限的产物。** 用户提出的研究问题（"什么条件下应该用 EV"）在本算例上的答案是平凡的"永远用 EV"，因此这一章现在写不出内容。

`CORRECTION`：用户转述的"EV 并非天然低碳"在本算例上**不成立**——EV 在任何充电时段都比 CV 干净，最脏时段仍干净 2.73 倍。可成立且经实测支持的表述是：**EV 的减排幅度随充电时刻在 2.7 倍与 27.5 倍之间摆动，摆幅 10.1 倍。** 环境优势的**方向**不取决于充电时刻，**量级**取决于充电时刻。正文须按后者表述。

### 6.3 让"什么条件下该用 EV"成为真问题的候选（`PROPOSAL`，待裁决）

需要至少一个维度让 CV 具备比较优势，否则混合车队一章无内容。三条候选，均可由现有数据或公开参数支撑：

- **F1｜电车购置成本溢价**：现行两型固定成本同为 170。中国轻型物流车电动版购置价显著高于柴油版，把该溢价接入固定成本即产生真实权衡。须补车型官方价格来源。
- **F2｜启用充电桩数量约束**：数据里每场已有 `depot_gun_count = 2`，但默认设为 UNBOUNDED。改为有限即产生排队——9 台车争 2 把枪、22 kW 充满需 3.5 小时，EV 规模一大就被补能卡住。**零新增数据，只是把已有约束打开。**
- **F3｜多趟下续航与补能时间变紧**：两趟 164 km 仍在一次满电内，但三趟 246 km 需 89.6 kWh > 77.28 kWh 电池，必须趟间补电。用户已批准放宽客户服务窗（决策 B2），放宽后三趟成为可能，F3 自动生效。

`INFERENCE`：F2 与 F3 互相强化且都不需要新数据——**放宽客户窗使多趟可行 → EV 需趟间补电 → 2 把枪成为瓶颈 → CV 因免补能获得比较优势 → 混合车队成为真正的优化结果**。这条链条同时把用户要的多趟、混合车队、充电三个机制串起来，与第三部分的六层串行链结构一致。F1 可作为独立的经济维度补强。

`FACT`（根因，代码级）：`solver/src/setp_solver/algorithms/problem_hgs/sisr.py:262-300` 的 `_greedy_insertion_with_blinks` 为三层嵌套，且**每评估一个插入位置都完整重建并重评一条路线**：

```
for customer in customers:            # 约 10 个被删客户
```

`INFERENCE`（复杂度）：现版每个候选位置带额外 `O(m)`（m 为路线长度）；忠实增量版把候选检查压到与路线长度无关的常数段合并（多载重时为 `O(载重维度数)`），每个客户只在接受插入后付一次 `O(m)` 的 `route.update()`。

## 第十七部分　测试规程再收紧：检验，不是跑分（2026-08-11，用户第二次纠正）

### 17.1 收紧后的原则

1. **每次测试必须先写清「这一次要查的是哪一件具体的事」**，再挑最便宜的手段查那一件事。不许用"跑一轮基准"代替"查一个问题"。

### 17.2 各层的触发条件（不是流程，是闸门）

| 要查的事 | 用什么查 | 耗时 | 通过才做下一步 |

## 第四十二部分｜真正的机理：不是充电，是趟次时刻撞车（2026-08-12 凌晨）

### 42.1 决定性数据：100 个被拒的交叉后代

来源 `charging_rejection_diagnosis_20260812/duty_crossover_rejected_candidates.jsonl`（Codex 第二步抓取，100 条）。`FACT`

| 原始报错 | 次数 | 失败 duty 的车型 |
|---|---:|---|
| `no feasible depot charging window` | **60** | **EV** |
| `E3_STRICT_MULTITRIP_V2: … has overlap or incomplete recharge` | **40** | **CV（油车）** |

异常类型 100/100 为 `ChargingRepairFailure`；失败 duty 100/100 在 `D_chengdu_pidu_dp`（郫都场），交叉改动的 305 个 duty 也全在该场。

**40% 的交叉死亡是油车。油车没有电池、不充电，却被"充电修复"判死。**
→ `REJECTED_CHARGING` 这个桶里装着大量根本不是充电问题的失败。此前所有以「充电拒绝率」为名的分析都受此污染。

### 42.2 契约代码：那条判据判的是行程重叠，不是充电

`solver/src/setp_solver/search/multitrip_schedule.py:1765-1767` `FACT`：

```python
for previous, current in zip(ordered, ordered[1:]):
    if current.departure_second + 1e-6 < previous.recharge_end_second:
        raise ValueError(f"{CONTRACT_ID}: {vehicle_id} has overlap or incomplete recharge")
```

对 CV，`recharge_end_second` 即返场时刻（无充电）。该判据展开＝**下一趟的发车时刻早于上一趟的返场时刻**——车还没回来就要求它出发。**纯行程时长问题。**
对 EV 同理，只是返场与发车之间还要塞进充电，故表现为 `no feasible depot charging window`。

**统一机理**：交叉重组客户 → 某一趟变长 → 返场推迟 → 撞上下一趟的发车时刻 → 整个后代作废。
这解释了为什么 `INSUFFICIENT_ENERGY` 恒为 0：**从来就不是电不够，是时间排不开。**

### 42.3 班次契约（`shift_contract.json`）`FACT`

- AM 480–660 分（08:00–11:00，**3 小时硬窗口**）
- 午休 660–780（11:00–13:00），`return_to_depot_required: true`，`loading_and_charging_sequential: true`
- PM 780–1140（13:00–19:00，6 小时）
- 订单分配 AM 17 单 ／ PM 33 单；装货 0.1 小时/m³（满载 7.2 m³ ≈ 43 分钟）

PM 段 33 单、6 小时，单车需跑 2–3 趟 → **趟间发车时刻是最紧的资源**。

### 42.4 必须查实的疑点（决定这是缺陷还是模型约束）

**路线改变后，修复有没有重算各趟的发车时刻？**
- 若**没有**重算（第 2 趟沿用旧发车时刻，而第 1 趟已变长）→ **算法缺陷**。多趟 VRP 的正常语义是第 2 趟在第 1 趟返场＋装货后顺延出发。修好后交叉存活率应大幅上升。
- 若**有**重算、顺延后仍撞上 19:00 收工或客户时间窗 → **模型约束**，那要谈的是班次结构与订单分配，不是算法。

这是本轮最后一个岔路口，两条路的修法完全不同。**在查清之前不得动手改任何东西。**

### 42.5 对前面几节的连锁修正

- §39.3「88.9% 提案死于充电检查」→ 数字不变，但**定性错了**：其中相当比例（交叉通道 40%）根本不是充电失败，而是趟次重叠被记进了充电桶。

- §40（丢站）→ 权重进一步下调。补站仍要做（确凿的算例缺陷），但它救不了趟次撞车。
- 根设计审计 G8（硬拒绝 vs 罚分）→ **依然成立且重要**：无论根因是时刻还是电量，把可行性做成硬过滤而非罚分，都会让搜索无法穿越。但其效应量必须在时刻问题查清后单独测。

- 日里程 ≈ 3 趟 ×（往返约 20 km ＋ 群内约 8 km）≈ **84 km**，落在 71.9–109.6 带内；
- 上午最远客户单程约 15 km → 往返 33 分钟（按实测路网均速 54.8 km/h）→ 3 小时窗口有余量，EDF 可过；
- 两场分居两侧 → 最近场归属接近对半，车队均衡保持。

新池选择空间充足（成都 180 个物流设施跨 66 km、6079 个客户点），**该目标可达**。

### 49.5 处置

第三轮重建：**沿用新池不重采**（数据已就位且质量好），只改第三步的选择规则——
- 车场对：从新池中选间距 **15–25 km** 的一对真实物流设施；
- 客户：从该对车场**之间的走廊**内抽取，使客户云跨度约 10–15 km（而非整个 66 km 框）；
- 充电站：取落在客户云内的站，并**报告站数**——新套件 25–186 个站远超文献密度（BHGS 用的 E51 是 50 客户 / 9 站），过密会使充电不再成为约束，反而抽空非线性充电与时变碳强度两个机制的作用条件。此项需一并核。
- 验收：EDF 81/81、两场车队均 ≥1、**日里程带下与带内均须有车**、可争夺占比回到 0.30–0.45。
