# M1 静态 ALNS 独立根因审计

日期：2026-07-10

## 结论先说

当前 M1 线不是一个单一问题，而是五层问题叠在一起：正式实验身份混乱、独立化重构留下真实运行错误、共同起点并不公平中性、默认动作调度会锁死、以及场景本身未必支持稳定混合车队。过去长期没有闭合，主要原因是这五层经常被当成一个“再调一点参数”的问题处理。

本轮最重要的新事实是：**当前 ALNS 的基础动作并不缺少改变车队结构的能力。真正的第一算法瓶颈，是完整循环没有稳定调用这些动作。** 在当前正式 v3 三班实例上，单步枚举能直接造出可行且更便宜的电车变化和路线减少；但默认 AlphaUCB 调度在共同一电车起点下，五个种子全部没有调用一次车辆类型切换，几乎一直重复同一组动作。强制动作覆盖后，五个种子全部更便宜。

这不等于“balanced selector 已经解决 ALNS”。旧 16 实例证据已经显示，调度修复在 4000/8000 次评估有帮助，但到 16000 次仍落后 LNS。因此，调度锁死是确定根因之一，但不是全部长期差距的解释。

## 当前正式事实源

正式算例已切换为审计通过的 L-main v3 九阶三班族。九个源规模标签是 `10,15,20,25,50,75,100,150,200`，实际合并客户数是 `22,34,45,55,114,163,221,322,449`。激活证据位于 `baselines/e2_alns/l_main_v3_activation/`，判定为 `LMAIN_V3_READY`。所有正式入口现在必须先验证活动 manifest 与该审计决定完全匹配。

因此，7月5日至8日基于旧 16 实例 hard subset 的 selector、结构救援和 A13 结果，只能保留为旧平台机制证据，不能直接充当 v3 性能结论。A13 的 576/576 精确一致仍能证明“抽出的 LNS policy kernel 与 LNS 实现等价”，但不能证明它是独立 ALNS 创新，也不能证明它在当前 v3 上优于其他算法。

## M1 身份不统一

仓库里至少有三条都被称作 M1/ALNS 的真实路径。

第一条是公开 API `run_resetp_alns = run_winner_kernel`，使用显式的 lean flags。第二条是 formal candidate 的 `run_candidate(PRIMARY_ALGORITHM)`，走 `run_alns_wouda`，依赖另一套运行方式。第三条是当前 T3 closure，走 `run_e2_alns_throughput` 并打开 local search。它们的初始化、接受方式和开关并不相同。

因此，过去“ALNS 健康”“ALNS 赢/输”“某算子贡献”如果没有同时写清入口、flags、起点、价格、电池和算例版本，就不能视为同一个算法的连续证据。

## 找到的实现错误

独立化提交 `fca004fad` 后，独立包存在至少三处真实运行断点。

一是 `alns_core.py` 定义了一个名字，却返回另一个不存在的 bundle loader，`run_alns_wouda` 会直接 `NameError`。二是独立 strong-bridge 副本缺少 `json/hashlib`、缺少 `_ThinPolicy`，并且 `_OperatorOutcome` 丢了 dataclass 装饰；诊断 trace 和 strong-bridge 打开后都会崩。三是 DR-ALNS 分支调用了不存在的 `_lazy__lazy_run_candidate`，还多了一层调用。

这些错误已经用真实失败测试复现并修复。静态扫描当前独立包不再有 undefined name。它们说明旧“独立测试通过”只证明了导入关系和少量烟雾路径，没有覆盖真实求解分支，不能作为实现完全健康的证据。

## 实验合同和结果来源问题

旧 formal runner 曾把正式主实例写成不存在的 `L-main-threeshift-200c`，真实注册名带 `-01`；E0 仍硬等 23 行，而正式注册表已经是 9 行。活动 v3 目录曾在没有 `LMAIN_V3_READY` 的情况下存在，manifest 还把 AppleDouble `._*` 算进 hash。以上问题现已通过激活门和 E0 实跑修正。

旧所谓 fair SA 对比并不公平：SA 显式使用 `make_shared_initial_solution`，winner 则没有收到同一个起点，回到自己的默认构造。当前 280 kWh、55 实际客户的 v3 实例上，CV 起点是 8 条路线、0 EV、成本 1730.390718；所谓 `SHARED_ONE_EV` 起点是 9 条路线、1 EV、成本 1811.837477。它不是在同一路由上简单换一辆车，而是新开一条单客户 EV 路线，所以既改变车队结构，也把起点成本抬高约 81.45。过去“EV seed 有帮助”和“SA 优于 ALNS”都必须在同一起点重测。

仓库中未找到可追溯到原始行的“ALNS 验证集强约 3.23%”证据，暂按未证处理。旧 09y Stage B 六种算法、三种子全部返回同一个构造解，只能说明构造的混合解存在，不能说明任何算法发现了它。

## 单步可达性结果

证据目录：`baselines/e2_alns/m1_structure_reachability_20260710/`。

实例为当前 v3 `L-main-threeshift-25c-01`，实际 55 客户，电池 280 kWh。所有候选都继续使用原来的 evaluator 和 checker。每个现有 ALNS destroy/repair 组合从两个冻结起点各重复 5 次。

当前 throughput profile 从 CV 起点做了 90 次单步尝试，得到 42 个可行结构变化，其中 28 个立即降成本；从共同一电车起点做了 90 次，得到 24 个可行结构变化，24 个全部立即降成本。可用动作包括车辆类型切换、整路线移除、区段移除和相关客户移除。判定为 `ALNS_SCHEDULER_OR_MULTI_STEP_BARRIER`。

同一轮中的 SA 直接动作从 CV 起点 30 次没有得到结构变化，从共同一电车起点得到 4 个结构变化，其中 3 个立即降成本。这个小样本不能做算法排名，但足以否定“只有 SA 能直接改变结构、ALNS 完全不能”的说法。

## 完整循环中的调度锁死

证据目录：`baselines/e2_alns/m1_scheduler_realization_20260710/`。

实验只比较同一个 throughput 循环的两种现有调度方式：默认 AlphaUCB 和已有 diagnostic balanced coverage。固定同一 v3 实例、280 kWh、400 次完整评估、两个相同起点、5 个相同种子，共 20 个配对运行。

共同一电车起点下，默认调度五个种子的平均 dominant pair share 为 0.9964，五次都没有选择一次 `vehicle_type_swap`，最终全部停在 1 条 EV 路线。balanced coverage 五次都覆盖 18 个组合，最终得到 6至8条 EV 路线，并且 5/5 都比对应默认运行便宜，平均少 178.873473。

CV 起点下，默认结果高度路径依赖：五个种子的最终 EV 路线数是 `8,1,1,7,1`，其中三个种子一次车辆切换都没有。balanced coverage 3胜2负，平均少 30.891017。它修复了漏试动作，但强制覆盖也会浪费预算，所以不是最终方案。

锁死机制很直接：所有动作初始分数相同，确定性 tie 会先选第一个组合；一旦它得到一次 8 或 20 的高奖励，未试动作的探索值即使到 16000 次也只有约 1.88，永远追不上。默认调度不是“根据长期贡献学习”，而是很容易被最早几次结果永久定型。

## 为什么 SA 过去可能看起来更强

SA 每轮从 relocate、swap、2-opt、vehicle flip 中直接抽一个动作，并且允许以概率接受暂时变差的解。它没有 ALNS 的 destroy×repair 二维调度锁死，所以在某些起点上更容易持续尝试不同结构。

但当前 SA 也不是天然更强。它的车辆切换没有 ALNS 的完整充电修复能力，路线消除只靠随机 relocate 抽中单客户源路线；而旧 fair runner 又给 SA 和 winner 不同起点。因此，“SA 更容易找好车队结构”目前是一个有实现理由的解释，不是已经公平证实的普遍结论。

## 哪些旧结论保留，哪些降级

仍然成立的结论包括：默认 selector 会过度集中；增加覆盖在短预算能改善一部分结果；现有 ALNS 与 LNS 的长期差距不能只靠加预算消失；旧 route-elimination/relaxed compression 组合没有成功；280 kWh 三班条件下确实存在真实、零违约、经济和排放都更好的混合方案；A13 与 LNS 精确一致证明代码等价。

需要降级的结论包括：A4/A6/A7 的短预算通过不能写成长期解决，尤其 16000 次仍输 LNS；`SELECTOR_SPRINT_8000_SUPPORTED` 只表示某些 8000 次门槛通过，不能覆盖同一产物里 16000 次的 LNS gate 失败；09y Stage B 的全平不是算法健康证据；旧 fair SA 和不可追溯的 3.23% 不应继续引用。

不值得继续的路线包括：继续给旧 route-compression 组合叠补丁；单纯加大预算；为了证明 ALNS 创新而把整个 LNS policy kernel 改名为 ALNS；以及为了得到混合比例而改评价器、价格或物理约束。

## 根因层级

第一层是证据身份：过去没有固定“哪个入口才是 M1”，算例、起点和采集合同也漂移。第二层是实现健康：独立化后有真实运行错误，但旧测试没有覆盖。第三层是初始化：共同一电车构造同时增加路线和成本，不是中性种子。第四层是调度：有用结构动作存在，但默认选择器会饿死它们。第五层是长期搜索能力：即使修复覆盖，旧 16000 次结果仍落后 LNS，说明多步路线重组和全局重打包能力仍不足。第六层是场景物理：有些 280 kWh 场景本来就偏全 EV，算法不应该为了论文叙事强行产出混合。

## 建议的攻关顺序

第一步先把唯一 M1 身份冻结为一个公开入口、一个显式 profile、一个共同起点合同；formal runner、T3 和 API 不能继续各跑一套。第二步做真正公平的起点矩阵：CV 起点和共同一电车起点都保留，但 ALNS 与 SA 每个配对必须拿到同一个对象，并单独报告起点成本和结构。

第三步只测试“最低覆盖保障”，不再把 balanced selector 直接当答案。最值得尝试的是按动作家族保证早期和周期性覆盖，同时删掉无意义的重复组合：`vehicle_type_swap` 现在与三个 repair 配对时实际行为相同，却占三个动作格。覆盖一次后再让自适应选择器工作，比每个组合强制十次更省预算。

第四步在改搜索前做“车队组成机会图”：对一个质量较好的固定路线集合，逐路线测试 CV/EV 转换和充电修复的真实边际成本。如果最优闭包是全 CV 或全 EV，就把该实例标为物理单一车队区，不把“没有混合”算成算法失败；只有闭包本身是混合时，才测试算法能否发现。

第五步用最小有区分度的实验验收：当前 v3 选小、中、大三个三班实例，5 个相同种子，两个相同起点；先跑 4000 次评估的默认 M1、最低覆盖 M1、SA，并记录动作覆盖、路线减少、EV 变化和最佳更新来源。只有最低覆盖在三个规模上都减少锁死且不靠欠评估，才升到 8000/16000。若长期仍输 LNS，就停止 selector 调参，转向明确的 ALNS-LNS hybrid，或者把 ALNS 降级为普通求解器。

## 论文口径

现在没有证据支持“ALNS 必须优于 SA”或“ALNS 已经稳定发现混合车队”。可以保留的故事是：现代电池加多班次能产生有价值的混合车队机制；算法是否能稳定发现该结构是另一项独立问题。

如果公平长预算结果最终不能显示独立 ALNS 的稳定优势，论文应把 ALNS 写成求解框架而不是主要算法创新。若采用 A13/LNS 机制，应诚实命名为 hybrid 或 adaptive LNS kernel，不能把代码等价包装成 ALNS 原创成功。
