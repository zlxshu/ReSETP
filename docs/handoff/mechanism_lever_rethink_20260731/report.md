**效应分解:原文未做定量分解。** 原文的归因是定性的(第16页):"独立配送客户点位置十分分散,配送路径存在迂回运送、交叉运输等不合理现象,分区配送客户点比较集中,联合配送模式共享产品、客户、车辆等社会资源。"这段话把"分区"的改善归因于"客户点比较集中"(客户重分配),把"联合"相对"分区"的进一步改善归因于"共享......资源"(车队/资源共享),但没有给出量化拆解百分比。

### 1.3 陈雨蝶等(2023)《"双碳"背景下联合配送冷链物流模型及其求解算法》

本文只对比**两种**模式(分区配送、联合配送),没有"独立配送"这一档。

原文定义(第1957页,3.2.1节):"在分区配送模式下,所有客户点分别划分至4个区域,每个配送中心只服务其所在区域的客户,此时每个配送中心的碳配额T_m为50kg;在联合配送模式下,各配送中心共享产品、客户、车辆等资源,共同服务所有客户,此时碳配额T_m为200kg。"

表5(第1957页,"不同配送模式结果对比"):

| 指标 | 分区配送 | 联合配送 |
|---|---|---|
| 总成本(元) | 3648.97 | 3426.86 |
| 总距离(km) | 837.90 | 784.81 |
| 车辆数(辆) | 9 | 8 |
| 碳排放量(kg) | 520.69 | 495.77 |

- **客户能否跨中心**:分区不能("只服务其所在区域的客户"),联合能("共同服务所有客户")。
- **车辆能否跨中心调度/车队**:分区不共享(原文:"分区配送并没有共享配送中心的客户和车辆资源,易造成车辆装载率低的现象"),联合"共享产品、客户、车辆等资源",即车队为**全局共享车辆池**。
- **充电设施**:全文为纯燃油冷藏车模型,无电动车/充电桩要素,原文未涉及。
- **车辆数**:模型内生输出(每个配送中心均拥有"足够多的冷藏车",第1952页),非外生上限。

**效应分解:原文未做。** 唯一的归因原句(第1957页):"分区配送并没有共享配送中心的客户和车辆资源,易造成车辆装载率低的现象,如路线[D39,22,33,D39]和[D37,31,10,16,9,D37]的装载率仅为58%和68%,而联合配送的车辆数为8,每条路线的装载率均在70%以上......可见这种配送模式可充分利用车辆资源,减少运输过程中的车辆数。同时总距离、总时间和总成本相对于分区配送也分别减少了6.34%、5.07%、6.09%。"

**车辆数变化的原因:** 原文把车辆数下降(9→8)统一归因为"车辆资源共享+装载率提升"。但由于本文只对比"分区"和"联合"两档,而"联合"同时打开了客户跨中心与车队共享两个开关,**客户重分配和车队池化两个渠道在数据上同时发生,原文没有把两者的贡献分开量化**,不应替原文下"主因是哪个"的结论。

### 1.4 任务一小结

三篇论文对"客户重分配"与"车队/资源池化"这两个杠杆的分解程度不同:

- 王勇2023:客户归属**在对比前已用聚类固定**,Case1-5全程只变资源共享程度,是三篇里唯一严格隔离出"纯资源池化效应"的论文,该效应达到43.2%总成本降幅。
- 陈雨蝶2025:三档对比(独立/分区/联合)里,"独立→分区"是纯客户重分配(车辆数不变,但成本/碳排/距离降30-50%),"分区→联合"是资源共享追加(车辆数降12.5%,但成本只追加降3.44%)。**这篇论文的证据方向与王勇2023相反**:客户重分配贡献了大头,资源共享贡献的是车辆数下降和一个小的成本追加。
- 陈雨蝶2023:分区/联合两档合并测试,两个杠杆同时开关,无法拆解。

三篇原文均未给出"车辆共享贡献X%、充电站共享贡献Y%、客户重分配贡献Z%"这类正式分解,凡本报告或Codex后续设计提及类似百分比归因,均须标注为"基于两两对比数字的直接读数",不能包装成原文结论。

### 2.2 E3当前ZONE/JOINT两臂约束

`baselines/china_e3_e7/formal_e3_runner.py` L101-104:

```python
ARMS = {
    "status_quo_responsibility": True,       # ZONE: hard_home_depot_lock=True
    "optimized_responsibility_cooperation": False,  # JOINT: hard_home_depot_lock=False
}
```

两臂加载**完全同一个bundle**(L776),`fleet_caps_by_depot`、`num_cv/num_ev`全部相同,没有按arm切换任何fleet输入。唯一差异化参数是传给`route_pool_sp.py`的`hard_home_depot_lock`:

- `hard_home_depot_lock=True`(ZONE)时,任何"客户home depot≠路线home_depot_id"的候选路线在路线池构造阶段(L480-485)和MIP阶段(L596-605)被直接过滤掉。
- `hard_home_depot_lock=False`(JOINT)时不过滤,允许一条起讫于depot X的路线服务本属于depot Y的客户。
- **车队上限约束(L649-689,`bundle.fleet_caps_by_depot[depot_id][...]`)在两个分支里完全一样,不受`hard_home_depot_lock`影响。**

路线本身恒定绑定单一车场:`solver/src/setp_solver/check.py` L567-575要求路线必须起止于同一个`home_depot_id`,这条check在两臂里都跑,不分arm。`search/evaluation.py`的`cross_depot_violations`(L125-143)判断的是"客户服务归属"而非"车辆归属"——车辆的depot归属(`route.home_depot_id`)本身就是固定字段,不因arm而变。

paper_main.tex正文自己也这样描述(L314):"车队由燃油车(CV)和电动车(EV)混合组成,每辆车只属于一个车场,但允许服务其他车场的客户"——这句话本身就是JOINT臂的确切数学含义:车辆-车场绑定(d(k))不变,只放开客户服务归属。

**paper_main.tex自己给出的第二个收缩来源(L1420-1421):** "两算例客户行政归属与最近车场完全重合,分区基线已是地理最优分工,因此本节测得的是在此基础上的剩余协同价值,而非重新划分责任范围带来的空间组织增量。"这句话与任务一发现的陈雨蝶2025证据方向一致——项目的ZONE基线已经是"分区最优"状态,类比陈雨蝶2025的"分区"档,而非"独立"档;JOINT测的是"分区→联合"这一步(资源共享的追加效应),按陈雨蝶2025的证据,这一步本来就是小效应(3.44%),不是大效应(33.55%)所在的那一步。

### 2.3 资源共享阶梯改造的影响面

改造存在两种方案,影响面差别很大:

- **方案(a)物理跨车场调度**:车辆当天可从任意depot出发、在另一depot还车。China81的9个车场分属三大城市群(京津冀/珠三角/成渝),跨群车场相距数百公里,单日窗口内物理调车不现实。这个方案会牵涉跨城市道路矩阵(可能未加载)、`check.py`的flow-balance规则(L567-575,要求route起止depot相同)、`cost.py`的城市定价归属逻辑(L239-269,按`route.home_depot_id`所在城市定电价/油价)。**方案(a)会触及check.py和cost.py两个受保护文件。**
- **方案(b)车队规模跨车场可调剂**:车辆依然从固定车场出发/返回(`route.home_depot_id`语义不变),但每个depot分到的num_cv/num_ev不再是fleet_caps.csv里的固定输入,而是在一个全局总量约束下由算法重新分配。这更贴近王勇2023"资源池"的含义,改动面小得多。**方案(b)不触及cost.py和check.py**(cost.py只消费固定的`route.home_depot_id`定价,check.py的flow-balance规则不涉及车队规模)。

**需要改动的文件(按方案b):**
1. `fleet_caps.csv`(及gate1_d2a复制件)——schema改造,加入全局总量/可调剂规则字段。
2. `solver/src/setp_solver/china81.py`——`fleet_caps_by_depot`构造逻辑、`China81Bundle`结构、`FLEET_CAP_SEMANTICS`标签。
3. `baselines/algorithm_prototypes/china81_mechanism_hybrid_20260720/route_pool_sp.py` L649-689——核心改动点,把per-depot上界换成全局总量约束。
4. `solver/src/setp_solver/china81_completion.py` L201-289, L399-425——per-depot上限检查逻辑同步放松。
5. `baselines/china_e3_e7/formal_e3_runner.py` L565-592——独立复核逻辑同步改写;`ARMS`定义可能需要新增"资源池是否共享"这个独立维度。
6. 十余个`baselines/algorithm_prototypes/*_20260725/*.py`原型文件也直接读`fleet_caps_by_depot`做per-depot约束,如果仍被引用需同步排查。

**三个受保护文件的判定:**
- `cost.py`:方案(b)不碰(只要每条route仍有唯一固定home_depot_id);方案(a)会碰(需要新的调车成本/时间项)。
- `check.py`:方案(b)不碰(flow-balance规则不涉及depot车队规模);方案(a)一定会碰(需要重写"route必须起止同depot"这条规则)。
- `search/evaluation.py`:**两个方案都会碰**,但改法不同——`cross_depot_violations`判定客户归属而非车辆归属,这是ZONE/JOINT机制本体,可以不改;但`EvaluationContext`大概率需要新增字段(如`fleet_pool_mode`)来把"资源池"信息传给下游,所以这个文件at minimum需要扩展dataclass和参数传递。

**是否改变paper_main.tex已定稿的模型公式和符号:** 会改变,改变点集中在符号表和文字表述,不在趟内部的flow/load/time/battery约束里。

- 符号表(`tab:symbols`,L353/370)里的`K_d`("车场d的车辆集合")和`d(k)`("车辆k所属车场")目前的定义就是"车辆归属固定车场",方案(b)下车辆归属仍固定,只是`K_d`的基数(车场车队规模)从外生固定数变成受全局总量约束的可调剂量——**符号定义需要补充说明,但符号本身不必新增**。
- 模型正文L314"每辆车只属于一个车场,但允许服务其他车场的客户"这句话在方案(b)下仍成立,但需要补一句"各车场车队规模在总量约束下可调剂"。
- `\label{eq:stage_profit}`(L571-576)用`d(k)`定义跨场服务客户数,方案(b)下`d(k)`语义不变,这条公式不必改。
- 论文里**没有发现"车队规模上限"被写成显式不等式约束的equation环境**——`K_d`的基数目前只是符号表里的隐含外生输入。这意味着方案(b)很可能不需要新增/修改任何`\begin{equation}`,只需要在文字说明(L314、E3小节L1385-1421)里补充资源池设计的描述。
- E3小节文字(L1385-1421,"责任错配与跨场协同")的实验设计描述需要重写以反映新设计,否则与代码不一致。

**是否让已封存的E2/E4/E5/E6结果作废:** E2、E3、E5的runner全部直接调用`load_china81_bundle`共享同一份`fleet_caps.csv`;E4/E6/E7通过`baselines/china_e3_e7/adapter.py`共享同一bundle加载路径。方案(b)下`cost.py`/`check.py`不变,意味着**给定一条路线方案,它的成本/碳排计算规则不变**,但车队规模约束改变后**搜索空间边界变了**,已封存的正式数值结果所对应的搜索空间已经不是新设计下的搜索空间,**必须重新生成**,不是逻辑上"错误"而是输入前提变了。这一点对E2(算法对比)、E3(ZONE/JOINT效应)、E5(非线性充电可行域)尤其直接;E6的独立经营基准Π_d^0(依赖"车场d仅服务自身客户、禁用跨场服务"这一定义,`eq:participation`附近L602-604)本身定义不因车队规模约束改变而变,但如果要保持与新设计下的可行解集合一致,也需要重算。

## 任务三:E5非线性充电在文献里何时binding

Zotero库中确认存在Montoya等(2017)"The electric vehicle routing problem with nonlinear charging function"和Froger等(2022,非用户提到的"2019","The electric vehicle routing problem with capacitated charging stations")两篇。库中没有Froger 2019这个版本,已用2022版作为替代读取来源,不假装读了一篇不存在的2019论文。

### 3.1 算例参数

两篇论文用同一个120-实例测试集(Froger 2022直接继承Montoya 2017的实例库):

- **电池容量**:"The EVs in our instances are Peugeot iOns. This EV has a consumption rate of 0.125 kWh/km, and a battery of 16 kWh."(Montoya 2017, p.13;Froger 2022, p.21同一表述)
- **路线长度**:客户分布在120×120km地理区域("semi-urban operation"),最大路线时长统一设为10小时(p.13)。原文未给出"平均路线里程"汇总数字。16kWh÷0.125kWh/km=单次满充理论续航128km(本报告据原文两个数字推算,原文未直接写128km)。
- **充电功率**:三级充电,"Slow/Moderate/Fast"对应"11/22/44 kWh/h"(kW)(Montoya 2017, p.13, Fig.8表格),数据拟合自真实厂商实测数据。Froger 2022沿用同一功率设置,新增充电桩数量限制(每CS 1-2把充电枪)。
- **SOC工作区间**:Montoya 2017专门统计了最优解里实际发生的中途充电的SOC分布(p.17-18):"over 90% of the mid-route charges are partial charges"、"around 12% of mid-route charges...restore the battery to above 80% of its capacity"、"good E-VRP-NL solutions often include routes with mid-route charges that take the battery level into the nonlinear part of the charging function"。

### 3.2 非线性充电为什么binding

**Montoya 2017:** 充电曲线两阶段,第一阶段恒流线性,SoC≈80%后进入第二阶段电流指数衰减(p.2-3,图1图注)。作者做了一个对照实验——如果假装电池只能充到80%(FS近似,回避非线性段),结果是:"in 3 of the 20 instances the FS approximation increases the number of routes...9 instances become infeasible with the FS approximation...(solutions) are (on average) 2.70% more expensive."(p.14)。卡住的环节是:最大路线时长(10h)+电池容量共同作用下,如果不让用非线性段,远距离客户的路线需要更多绕行/充电时间,直接导致9/20个实例不可行。

**Froger 2022:** 核心贡献是充电桩数量容量约束,并明确指出这个约束比充电函数曲线本身更binding:"55 of the BKSs (best-known solutions) become infeasible if there is only one charger per CS. This figure drops to 23 and three for the cases with two and three chargers."(p.2-3)。正文直接用"binding"一词:"When the CS capacity constraints are very binding, the energy reasoning-based algorithm detects infeasible route selections much more frequently..."(p.24)。是"非线性充电耗时长+充电桩数量有限导致排队"两者叠加才真正卡死可行性。

### 3.3 与本项目参数的差距

| 参数 | 文献算例 | 本项目 | 差距 |
|---|---|---|---|
| 电池容量 | 16 kWh | 77.28 kWh | 本项目约为文献的**4.83倍** |
| 充电功率 | 11/22/44 kW三级 | 22 kW单一 | 本项目落在文献"moderate"档,等于文献中档,是快充档(44kW)的一半 |
| 充电倍率(功率/容量) | 22kW÷16kWh≈1.375C(取同功率对照) | 22kW÷77.28kWh≈0.28C | 本项目充电倍率只有文献同功率下的**约1/4.9(约20%)** |
| 终止SOC | 最优解中约12%充电越过80%进入非线性区,90%以上为部分充电 | 196次真实会话:均值46.95%,中位37.03% | 本项目终止SOC比文献~80%触发点低**33-43个百分点** |

结论:本项目电池容量近文献的5倍,充电功率只是文献中档水平,两者叠加使等效充电倍率只有文献同功率场景的约1/5;实际运营终止SOC均值不到50%(中位数37%),远低于文献~80%的非线性折减触发点。按本项目现有真实参数,非线性充电折减区间被触发的频率应远低于Montoya/Froger算例中的情况——这与本项目已查明的"196个充电会话终止SOC均值46.95%、中位37.03%,绝大多数不进入功率折减区"根因结论完全吻合,文献进一步给出了"文献里binding场景到底长什么样"的定量对照。

### 3.4 若要让非线性充电binding,最小场景改动选项(仅列选项,不做取舍)

**选项A:降低充电功率**——从22kW降到接近文献slow档(11kW)。文献先例:11kW是Montoya/Froger三级充电体系里明确存在的一档,直接有先例支持。代价:需要重新定义车场设备参数,若与已跑实验(E3-E7当前22kW口径)不一致,破坏跨实验可比性,需要在论文里解释为什么换了充电功率假设。

**选项B:在数值实验里假设性调小电池容量**(非改变真实车队参数)——调到16-30kWh区间做对照场景,接近文献1.375C水平。文献先例:Xiao等(2021)在电池容量敏感性实验里测试过16/20/24/32kWh四档,说明"缩小电池容量做敏感性"这类操作在文献里有先例;但这与"保持77.28kWh不变、想办法让它binding"字面相反,原文未说明有先例支持"故意调大电池容量假设来触发非线性"这个方向。代价:脱离本项目"真实车队77.28kWh"这个数据锚点,需要明确标注为假设性/敏感性场景,可能被质疑数据来源真实性。

**选项C:拉长路线/扩大服务半径,迫使更深度放电后充电**——仿照Montoya等的120×120km"semi-urban operation"+10小时最大路线时长设计。文献先例:这正是Montoya 2017/Froger 2022自己构造算例的方式,是有直接先例的场景设计。代价:需要改变整个实验的场景设定(路网范围、任务密度、班次结构),而不只是车辆参数,需要说明这是压力测试场景而非常规运营场景,与已有E3-E7场景假设的可比性需要额外论证。

**选项D:改变SOC触发充电的阈值策略**——人为设定"SOC降到某阈值以下才允许/触发充电"的规则(而非纯路径可行性驱动)。文献先例:原文未说明——Montoya/Froger的充电决策本身是路由优化的连续/整数决策变量,不是规则触发的,这个选项如果要做是本项目自己设计的新假设,不是照抄这两篇文献的现成设定。代价:引入与现有E3-E7框架不同的充电决策逻辑,需要重新设计决策变量和约束结构,四个选项里工作量和对现有实验体系的冲击可能最大。

### 4.2 四篇论文的共同规律

1. **算法章图表极简**:四篇论文的算法设计章节普遍只放1张算法流程图(有时加1张算法内部机制示意图),几乎不额外配图,复杂度和创新点主要靠公式和文字说明,不靠图。
2. **收敛曲线图是标配但只有1张**:四篇里三篇(陈雨蝶2025图4、陈雨蝶2023图3双轴线图部分类似、陈婉茹图2)都有,但都只用**一张图对比多种算法**,不是每个实验/每个算法配一张。王勇2023反而没有严格意义的收敛曲线图。
3. **敏感性分析绝大多数以表格呈现,不画连续曲线**:四篇论文合计只有陈雨蝶2023的图3(碳价格双轴折线图)和陈婉茹的图4a(环形图,非曲线)勉强算敏感性可视化,其余全部是表格(如陈婉茹表9/10/11,王勇表11/12,陈雨蝶2025表7)。**没有一篇论文对每个机制/每个敏感性维度都单独画一张曲线图。**
4. **机制对比(如资源共享阶梯、配送模式对比)的核心呈现方式是一张"多情景并列汇总表"+至多一张"多情景柱状/折线组合对比图"**,不是每个case/每个模式单独一张图。王勇2023用表13+图11覆盖全部5个Case;陈雨蝶2025用表9+图5覆盖全部3种配送模式;陈婉茹用表9/10/11分别覆盖三个敏感性维度,不额外配曲线图。
5. **路径示意图数量普遍不多(0-4张)**,且往往集中呈现"before/after"或"多方案对比"于同一组子图里,不是每个实验一张。
6. **算例网络图0-1张**,且只在有真实地理坐标/真实城市案例时才画(陈婉茹图3a、王勇图7),纯数值算例(陈雨蝶两篇)不画网络图。
