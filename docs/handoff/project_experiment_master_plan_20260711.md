# ReSETP 论文与课题总实验计划（白话执行版）

版本：2026-07-11

用途：这是整个项目的实验施工总图。它回答五件事：为什么做、先做什么、每个实验具体怎么做、什么结果算数、结果怎样进入论文。

截止时间：2026-07-31 投稿。当前论文仍是草稿，因此本计划同时服务于“按时形成可投稿版本”和“保留课题后续可扩展空间”。

## 一、先把项目说清楚

这篇论文想回答的核心问题不是“某个算法能不能多赢几个百分点”，而是：

> 在有油车和电车、多个车场、时变电网碳强度、收益公平和临时订单的配送系统中，怎样得到成本可控、碳排可解释、车场之间相对公平、发生变化后仍能执行的调度方案？

论文要站得住，至少需要四组证据：

| 论文想说的话 | 必须拿出的证据 | 对应实验 |
|---|---|---|
| 模型真的能解决这个复杂问题 | 有可行路线；油车、电车、充电、跨车场服务都能解释；成本能对账 | E1 |
| 求解方法不是随便找个解 | 与健康的强基线公平比较；多次运行结果稳定 | E2 |
| 碳、车型、协同、公平不是摆设 | 关掉某个机制后结果确实变化；变化方向讲得通 | E3、E4/E5、E6 |
| 临时订单来了以后系统还能合理调整 | 同一事件流下，重规划可行，并展示协同、公平、充电时段发生了什么 | E7 |

如果其中某一组证据做不出来，正确做法是收缩论文说法，而不是改实验直到“看起来成功”。

## 二、项目怎么管理

### 2.1 一条主线，五个阶段

```text
地基检查
  ↓
关闭 E2，冻结求解算法
  ↓
冻结论文场景和其余实验合同
  ↓
依次完成 E1、E3、E4/E5、E6、E7
  ↓
统一做表图、改论文、审计和投稿
```

研究问题按这个顺序推进。只有当前已经批准的实验批次，才把实例、随机种子、算法或参数组合拆成多个任务同时跑。

### 2.2 看板状态

每个任务只能处于以下一种状态：

| 状态 | 大白话解释 |
|---|---|
| BACKLOG | 以后可能做，但目前不排期 |
| READY | 前置条件齐了，可以启动 |
| RUNNING | 正在跑；同一研究问题允许多个 worker 同时工作 |
| VERIFY | 已跑完，正在复算、查违规、核对记录 |
| ACCEPTED | 证据通过，可以进入论文 |
| HALT | 没通过；保留失败证据，不继续硬救 |
| ARCHIVE | 历史材料，只能参考，不能作为新正式结论 |

项目同时只能有一个“正在判断的科学问题”。例如 E2 可以有 30 个任务同时运行，但不能一边还没决定算法，一边又开始用这个未定算法跑 E4。

### 2.3 每个实验的固定流程

每批实验都必须走六步：

1. 先写实验卡：想证明什么、比较谁、哪些参数不许动、失败后怎么办。
2. 做小型预检：确认入口、实例、预算、输出目录、内存和并发数没问题。
3. 冻结运行身份：commit、Python、NumPy、实例 hash、评价器、初始解和预算。
4. 并行运行任务：worker 各写自己的结果，不能多人同时改一张总表。
5. 统一验收：重新计算成本和可行性，检查实际评价次数，做配对统计。
6. 做决定：ACCEPTED 或 HALT；不得发明“看似成功”的中间词拖延。

### 2.4 证据最低要求

每个正式实验都要有：

- `metadata.json`：这批实验是谁、在哪个环境、用什么参数跑的。
- `raw_runs.csv`：每次运行的原始结果。
- `decision.json`：是否通过、为什么。
- `artifact_hashes.json`：正式证据文件的哈希。
- `report.md`：用人话解释结果和边界。
- 保存解或可恢复 checkpoint：至少保存进入论文的代表解。

另外必须记录：实际评价次数、实际用时、是否超时、是否违规、随机种子、初始解身份、算法名称、场景是 80kWh 还是 280kWh。

### 2.5 谁负责什么

| 角色 | 负责的事 | 不负责的事 |
|---|---|---|
| 用户/课题负责人 | 决定论文最终主张、场景定位、是否接受降级、是否提交 | 不需要盯每个worker和日志细节 |
| Codex/项目执行负责人 | 读事实源、写实验卡、检查入口、拆任务、运行、监控、复算、汇总、更新看板 | 不能为了“成功”擅自改科学问题或评价器 |
| 自动runner | 按冻结合同运行并保存原始证据 | 不能替项目做科学解释 |
| 验收环节 | 查成本、违规、预算、hash、统计和论文映射 | 不能只看report标题就宣布完成 |

需要用户决定的事情应集中成清楚的二选一或少量选项，不把成百行日志丢给用户。普通运行和技术检查由Codex承担。

### 2.6 怎样提出和批准变更

任何会改变正式结果含义的修改，都先写一张“变更说明”：改什么、为什么、影响哪些旧结果、是否需要重跑、会不会影响7.31。以下变化必须重新过对应阶段门：

- 换算法或给算法增加组件。
- 改默认电池、碳价、车辆数、实例或事件流。
- 改评价器、检查器、预算计数或共享初始解。
- 改正式比较算法集合或删掉失败seed。

只修日志、报告格式、并行调度和不改变结果的路径问题，可以做最小修复，但仍要绑定commit并做回归测试。

### 2.7 如何判断项目有没有推进

不使用“写了多少代码”作为进度。每天只看四个数字：已验收阶段门数、当前批次完成任务数/总任务数、失败任务数、距离下一里程碑还差什么。一个实验只有进入ACCEPTED或HALT才算关闭；RUNNING很久不等于有进展。

## 三、历史踩坑转成的风险清单

| 风险 | 以前发生过什么 | 这次怎样防止 | 触发后怎么办 |
|---|---|---|---|
| 算错预算 | 局部搜索做了大量完整评价，却没有记进预算 | 所有目标计算经过同一计数器；报告实际评价数 | 该批排名作废，先修计数再决定是否重跑 |
| 基线只是“看起来在跑” | 多个算法被同一个共享捷径推到完全相同的平台 | 先做基线体检，记录算法靠自己产生了多少次最优解更新，以及结果是否有差异 | 不健康基线退出正式排名 |
| 起点不公平 | SA和ALNS曾使用不同起点 | 同一实例/seed共享同一冻结起点及hash | 配对结果作废，不做胜负解释 |
| 环境换了结果翻盘 | M1系统Python和RL venv/x86给出不同绝对成本 | 正式数字只用M1固定Python/NumPy；写清环境 | 跨环境只报各自相对结果，不混表 |
| 正式实例漂移 | L-main曾在旧3档、混族23个和九阶三班之间变化 | 只通过活动registry和manifest解析实例 | 发现旧目录即HALT，不迁移旧胜负 |
| 诊断场景冒充默认 | 280kWh能显示机制，但论文默认仍是80kWh | 每一行结果写scenario_role和battery_kwh | 分表展示，正文明确“基准/扩展” |
| 动态阶段丢客户 | 活动、待处理、已承诺集合曾出现客户漏失 | 每阶段做客户守恒检查和最终全量检查 | 先修合法性；该批动态结果不得入论文 |
| 并行写坏总表 | 多进程若直接写同一CSV会互相覆盖 | worker写独立task，单一汇总器合并 | 从task文件重建总表，不信损坏CSV |
| 外置盘AppleDouble污染 | `._*`进入Git/哈希并导致fsck噪声 | hash排除污染文件；提交前做完整性检查 | 标记污染、清理并重新计算hash |
| 长跑中改代码 | 结果可能绑定启动时和结束时不同代码 | 长跑启动后冻结代码；metadata记录启动commit | 若核心代码变化，运行继续留档但不作正式证据 |
| 结果不好就加实验 | E2持续多轮rescue，消耗了大量时间 | 预注册通过/HALT和截止日期 | 到点降低主张，不新开分支 |
| 旧数字混进新论文 | 旧471次表图仍存在且看起来完整 | 新输出放独立目录；生成表前检查来源commit | 发现混用就停止论文更新并替换来源 |

## 四、哪些旧东西能用，哪些不能直接用

### 可以复用

- 2026-06-20 已跑过 471 次 E1--E7，说明正式 runner、表格和图片管线不是空壳。
- T3--T9、F1--F6/F5b 的导出格式可以继续使用。
- `evaluate()`、`check_solution()` 和预算记录器继续作为统一裁判，语义不改。
- L-main v3 九阶三班倒实例、实例审计和独立 ALNS 包可以作为当前地基。
- 旧报告可用于估计运行时间、发现坑和对照字段。

### 不能直接当新正式证据

- 旧 471 次结果绑定的是旧算法/旧实例口径，只能当历史锚。
- 旧 T3 中出现过预算漏记、共享捷径把不同基线推到同一平台等问题。
- 280kWh 目前是机制可见的诊断/扩展场景，不是论文默认 80kWh。
- x86 和 M1 的绝对成本不能放在一起比较。
- 当前 `formal_runner.py` 仍有旧算法入口和串行 ledger 写入方式，正式重跑前必须做最小接线校正。

## 五、阶段门：什么时候才能进入下一步

| 阶段门 | 必须回答的问题 | 通过条件 | 不通过怎么办 |
|---|---|---|---|
| G0 地基门 | 实例、环境、评价器是否可靠？ | L-main v3 审计通过；保护文件未变；正式入口绑定正确 commit | 只修合同/入口，不跑科学实验 |
| G1 算法冻结门 | staged hybrid 是否至少稳定不差于 LNS？ | 当前 30 次完成、全解复算、三个规模均值和中位数不系统性落后、用时优势明确 | 停止算法开发，降低算法主张 |
| G2 正式 E2 门 | 在论文口径下，与健康基线比较是否可解释？ | 同环境、同起点、同预算；至少 5 seeds；基线真的在搜索；结果可复算 | 如实写同一梯队或较弱，不再 rescue |
| G3 场景冻结门 | 80/280kWh 各自扮演什么角色？ | 80=文献基准；280=有来源且只作机制扩展；论文表述不混 | 收缩机制主张，不再扫电池找“好看比例” |
| G4 机制证据门 | 碳、公平、动态是否真的改变决策？ | 每项至少有一个直接指标或案例成立 | 对应贡献降级，不修改裁判救场 |
| G5 投稿门 | 表图、正文、原始数据是否一致？ | 所有数字可追溯；LaTeX通过；没有旧数混入 | 只修缺口，不开探索性实验 |

## 六、各子实验详细计划

## E0：地基和算例检查

### 想证明什么

不是证明算法好，而是确认“比赛场地没搭错”：九个正式算例存在、客户数和三班结构正确、每个算例能构造合法起点、正式入口没有指向旧目录。

### 具体怎么做

- 检查 L-main v3 九个实例：10/15/20/25/50/75/100/150/200c 标签，对应实际客户数 22/34/45/55/114/163/221/322/449。
- 核对 manifest、审计 hash、碳强度 48 个时段、D0/D1 两车场、三班窗口。
- 每个实例构造一次共享起点并用统一裁判复算。
- 检查正式 runner 使用活动 registry，不读 legacy/archive。
- 检查保护文件无未批准语义修改。

### 任务量和并行

九个实例可拆成九个轻量任务，2--4 个 worker 足够。这里只做结构预检，不做长搜索。

### 通过标准

九个实例全部可加载、起点零违规、manifest/hash一致、正式入口和实例清单一致。任何一项失败都停止后续正式实验。

### 进入论文哪里

生成 T1 算例说明和复现性附录，不直接贡献“算法胜利”。

## E1：完整模型和车辆结构

### 想证明什么

完整模型不只是能给一个总成本，还能形成可解释的油车/电车分工、充电行为和跨车场服务。

### 比较什么

- mixed：让模型自己选择油车和电车。
- CV-only：只允许油车。
- EV-only：只允许电车；若物理不可行，必须写“不可行”，不能当作成本更差。

### 场景

- 80kWh：论文文献基准，回答“在原始参数下模型怎样工作”。
- 280kWh：机制扩展，回答“当电车和充电真正活跃时，车型和充电结构怎样变化”。

两者要分表或明确分栏，不能混成一个默认场景。

### 运行设计

- 主分析：200c旗舰实例，mixed/CV-only/EV-only × 5 seeds，共15个任务。
- 跨规模检查：50c、100c、150c各取 mixed × 5 seeds，共15个任务；只验证结论不是旗舰实例偶然现象。
- 若时间充足，再扩为九阶 mixed；不是投稿硬门。
- 算法使用 G2 冻结后的正式方法，预算合同与 E2 一致。

### 必须输出

总成本及固定、里程、燃油、电费、碳交易分解；油车/电车路线数和实体车辆数；客户、需求、距离由两类车辆承担的比例；充电次数、电量、车场/公共站比例；跨车场服务数量；全部违规。

### 通过标准

完整模型零违规、成本分解能加回总成本；mixed 不是简单复制 CV-only/EV-only；至少在机制扩展场景中能看见真实电车工作和充电。若 80kWh 下电车弱，照实报告，不为凑混合改电池。

### 论文产物

T4 解结构表；必要时增加一张车型工作量图。它支撑“模型能工作”，不支撑“算法比别人强”。

## E2：算法有效性

### 想证明什么

冻结后的 staged ALNS-LNS hybrid 在公平条件下，至少是一个稳定、有竞争力、速度合理的求解方法。

### 最后一轮开发门已经完成

100c/150c/200c × seeds 1--5 × hybrid/LNS，4000次评价、900秒上限、280kWh诊断场景，共30次，已于2026-07-11全部完成。30/30状态正常、零违规、全部跑满4000次评价。三个规模的hybrid平均相对LNS分别改善6.45%、0.69%、14.08%，成本胜出合计11/15；verdict=`STAGED_HYBRID_STABILITY_SUPPORTED`。

这证明hybrid值得进入一次最小正式比较，但仍不是正式T3，也不证明碳算子有效。按照7.31止损规则，从这里开始永久停止算子开发，不接受runner中“再跑九规模/更长预算”的自动建议。

### 正式比较分两步

第一步是“基线体检”：每个候选基线只跑少量任务，检查它是否真的更新过最优解、是否跑满预算、是否零违规、是否出现不同算法完全复制同一个共享捷径。体检不过的算法不进入正式排名，只在附录解释。

第二步是“最小正式表”：

- 实例：100c、150c、200c。
- seeds：至少 1--5；若7月16日前有余量，可补到10，不因补种子延长算法开发。
- 方法：staged hybrid、LNS，以及通过体检的1--2个近年强基线；SA只作地板参考。
- 主账本：同墙钟上限，报告各算法实际完成的评价次数。
- 副账本：固定4000次评价的闭合子集，避免把“跑得慢”误写成“解得差”。
- 所有方法用同一个共享起点、同一 evaluator/checker、同场景、同随机种子集合。

### 统计和结果解释

报告均值、中位数、标准差、胜负次数、运行时间和实际评价数。配对检验只作为辅助，5个种子统计能力有限，不能因为一个 p 值就写“显著全面领先”。

### 通过标准

- 所有保存解复算零违规。
- hybrid 在三个规模上不出现稳定、系统性落后。
- 至少对一个健康强基线具有可解释优势，或者能诚实定位为同一梯队但更快。

如果不满足，就把算法贡献降为“面向复杂模型的统一混合求解框架”，不再继续修算法。

### 论文产物

T3 算法比较、F2 收敛/最终结果图、baseline health附录、复现环境说明。

## E3：车型反事实和模型消融

### 想证明什么

论文中的多车场协同、时变碳、碳交易和收益公平不是把名词堆在一起；关掉其中一项，结果应该发生能解释的变化。

### 两部分

车型反事实已经在 E1 完成，不重复跑。这里重点做 M0--M5 累积消融：从简化模型开始，逐层加回协同、EV间接碳、时变碳、碳配额/交易和收益公平。

### 运行设计

- 旗舰实例：200c。
- 机制可见场景优先使用280kWh扩展场景；同时保留80kWh完整模型锚，说明默认场景的机制强弱。
- M0--M5 × 5 seeds，共30个主要任务。
- 每次只改变被测机制；算法、起点、预算、其他参数全部冻结。

### 必须输出

总成本、总碳、油车直接碳、电车充电碳、跨场服务数量、每场收益与最小公平比、车型结构、充电量。

### 通过标准

至少能解释每一层“加了什么、改变了什么”。不要求每一层都显著改善；如果某层几乎没影响，要写成“在当前场景作用弱”，不能偷偷改实验定义。

### 论文产物

T5 消融表。贡献文字必须跟表中真正出现的变化一致。

## E4/E5：碳和充电机制

这两项合并管理，避免为了一张独立表重复跑大量相似实验。

### 想证明什么

最关键的问题不是“总碳排算出来了”，而是：在路线、车型和总充电量尽量不变时，模型是否会把充电从高碳时段移到低碳时段。

### 第一步：固定路线的充电时间实验

- 从 E1/E2 保存解中选择有真实充电的代表解。
- 固定客户分配、路线顺序、车辆类型、车辆数量和总充电电量。
- 比较“回场立即充电”和“允许选择低碳时段充电”。
- 输出每次充电从什么时段移到什么时段、平均碳强度、总充电碳、是否影响可行性。

这是最干净的碳机制证据，因为排放下降不能归因于换车、改路线或少送客户。

### 第二步：小型敏感性矩阵

- 碳价倍数：0.5、1.0、2.0。
- 配额倍数：0.8、1.0、1.2。
- 5 seeds，共45个任务。
- 如果三档已经显示清晰趋势，不再扩到4×4大网格；只有出现无法解释的拐点才补点。

### E5如何处理

E5不再单独做大规模充电技术参数扫描。投稿版只保留“立即充电 vs 择时充电”和必要的充电功率/曲线来源说明。车场桩容量、公共桩可用性等作为课题后续工作，除非它们是让当前机制成立的必要条件。

### 通过标准

固定路线条件下，择时充电的平均碳强度或充电碳明显下降，且配送任务和总电量不变。如果充电几乎不能移动，就收缩“时变碳参与决策”的表述。

### 论文产物

T6 两层碳排、T7 碳敏感性、F3/F4/F5。图必须直接显示充电时段迁移，不能只画总碳柱状图。

## E6：收益公平

### 想证明什么

多车场协同降低总成本时，没有让某一个车场承担全部损失。

### 运行前先检查

- 分别求每个车场独立经营时的基准收益，确认都大于0。
- 确认公平约束真的进入搜索，而不是只在跑完后计算一个指标。

### 运行设计

- 旗舰实例：200c。
- 公平阈值先用 0.90、0.95、1.00、1.02、1.04；5 seeds，共25个任务。
- 如果1.04附近出现可行/不可行边界，再在边界附近补1--2个点；不再机械扫0.80--1.10全部网格。
- 固定算法、预算、场景和独立收益基准。

### 必须输出

每个车场收益比、最小收益比、总成本、总碳、跨场服务数量、是否可行。重点画“公平要求提高后，要付出多少额外成本”。

### 通过标准

阈值变化确实改变最小公平比、总成本或跨场合作范围。如果多个阈值结果完全一样，说明约束没有被激活，只能报告“当前范围内不敏感”。

### 论文产物

T8 公平阈值表和F6公平代价曲线。

## E7：动态需求和滚动重规划

### 想证明什么

临时增加、取消或修改订单后，系统能在不破坏已经执行部分的前提下重新安排剩余任务；并观察协同、公平和充电时段如何受影响。

### 先过合法性门

动态代码历史上出现过“客户从活动集合消失”“最后一段漏服务”“已承诺路线重放语义变化”等问题。正式跑前必须用固定事件流检查每个阶段和最终结果：所有客户要么已服务、要么待服务、要么合法取消，不能凭空消失。

### 最小比较设计

使用同一批事件流，做四个配对方案：

1. 静态/不重规划：作为代价基线。
2. 正常滚动重规划：证明动态接口有价值。
3. 关闭跨车场协同：观察临时订单由谁吸收。
4. 碳盲或公平关闭对照：根据前面哪个机制已经证明有效，选择对应对照；不做无意义全因子排列。

事件包含新增、取消、需求量变化。使用一个中等规模代表实例，5个固定事件流；若运行成本过高，先3个流完成机制判断，再补到5个。

### 必须输出

每阶段新增/取消/变更数、已冻结路线、剩余客户、阶段成本、累计成本、累计碳、跨场吸收订单比例、每场收益比、EV/CV分工、充电时段平均碳强度、最终未服务客户数。

### 通过标准

最基本要求是所有阶段和最终结果零违规、无客户丢失。协同、公平、碳三个故事分别看自己的直接指标。做不出三者耦合时，E7就写成“动态滚动接口和状态继承可行”，不继续扩大实验。

### 论文产物

T9 动态结果表、1个代表事件时间线或案例图。避免把几十行阶段日志全部塞进正文。

## 七、统计、复算与公平比较规则

- 同一比较必须使用相同实例、相同seed集合、相同初始解合同。
- 优先做配对比较，因为同一个seed下比较更公平。
- 正式算法表至少5 seeds；条件允许补到10。机制实验以5 seeds为主。
- 同时报告效果大小和不确定性，不只报p值。
- 对多个算法做多次显著性检验时，使用Holm等校正，避免“测得越多越容易显著”。
- 超时后如果返回“截至当时找到的最好解”，必须记录实际评价次数；不能和跑满16000次的结果混写。
- 每个进入论文的解都重新经过 `check_solution()` 和 `evaluate()`；保存成本与复算成本差超过1e-6即HALT。
- 不用M1绝对值和x86绝对值横比。

## 八、CPU和运行管理

### 基本原则

当前M1为8核、8GB内存。并行目标是减少总墙钟，不是强行让CPU显示100%。

每批任务先做资源预检：

1. 单worker跑一个小、中、大代表任务，记录时间和峰值内存。
2. 用2 workers重复，计算总吞吐是否接近翻倍。
3. 只有内存稳定、无swap、单任务没有明显变慢时才试3或4 workers。
4. 正式运行采用实测得到的最大稳定worker数。

当前经验显示4000-eval hybrid平均约2分钟，LNS平均约7.6分钟，200c更慢。预计M1上重型任务以2个worker为稳妥起点，实际数字必须通过预检确认。

### 安全并发写入

每个worker只写：

```text
.tasks/<run_id>.json
solutions/<run_id>.json
logs/<run_id>.log
```

所有worker结束后由单一汇总器生成 `raw_runs.csv`、统计表、decision和hash。禁止多个进程同时重写同一个manifest或CSV。

## 十二、常用词翻译

| 文件里常见的词 | 人话意思 |
|---|---|
| instance / 实例 | 一套具体配送题目，例如100c代表一个规模档；真正客户数以实例文件为准 |
| seed / 随机种子 | 控制算法随机过程的编号；同一个编号用于公平配对 |
| baseline / 基线 | 拿来比较的对手算法 |
| budget / 评价预算 | 允许算法调用统一成本计算多少次，相当于每个算法的“答题机会” |
| wall-clock / 墙钟 | 从开始到结束真实经过的时间 |
| gate / 阶段门 | 进入下一步之前必须达到的条件 |
| worker | 同时运行一个实验任务的独立进程，可理解为一个干活工位 |
| manifest | 任务清单或完成账本，记录哪些已跑、哪些失败 |
| hash | 文件指纹；用于确认正式证据后来没有被偷偷改过 |
| evaluator / checker | 统一计算成本、检查路线是否合法的裁判 |
| ablation / 消融 | 关掉某个模型机制，看结果会不会变化 |
| counterfactual / 反事实 | 人为规定只用油车或只用电车，与混合车队进行对照 |
| staged hybrid | 当前分阶段混合算法：普通ALNS搜索、LNS强修复、再回普通搜索 |
| ACCEPTED | 证据合格，可以进入论文 |
| HALT | 没过门，停止这条实验并如实记录 |
