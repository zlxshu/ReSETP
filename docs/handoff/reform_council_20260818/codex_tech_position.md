# 第二层独立立场：底层代码质量必须靠生产机制治理

## 结论

这个仓库的问题不是“AI 不会写 Python”，而是现行生产方式会稳定地产生烂代码：每个会话被要求局部跑通、兼容旧入口、少碰核心、补齐报告，于是 AI 用新变量、新分支、新缓存、新状态和新脚本绕过矛盾；测试奖励“能退出、能写包”，却没有约束唯一事实源、对象生命周期和接口语义。

机制性治法只有一条：**通用算法只准使用可核上游；项目自写部分压缩成有尺寸上限的语义适配件；所有质量要求交给机器执行，AI 的报告和自我保证一律不算验收。**

## 一、这些烂码是怎样被生产出来的

1. **局部任务闭环，代替了全链责任。**  
   私有技术脚本同时承担工厂、运行、计时、验收和写包，后来又被约 17 个消费者反向进口；runner 记录的引擎与 integrated 实际执行的引擎不是同一对象，同一个 `wall_seconds` 还有两种含义。每个局部任务都“方便地补一点”，最终便出现两套身份、双时钟和开关漏传。事实见 `solver/reports/foundation_review_20260817/report.md:82-88,135-152`。  
   **判断**：任务书如果只写“把这一段跑通”，却不指定谁拥有最终配置、时钟和状态，就必然诱发接口两边各算一本账。

2. **奖励“看起来完成”，而不是语义完成。**  
   mixed 曾经只要有成本就算成功；public 审计失败仍可写 `COMPLETE`、退出 0；dynamic 捕获停机后也可返回 0。代码自然会围绕文件、状态词和退出码做表面闭环，而不是围绕可行、完整服务和正常终止闭环。见 `foundation_review_20260817/report.md:64-72`。  
   这不是一次疏忽，而是一种激励：只要报告能写“完成”，局部作者就得到正反馈。

3. **不肯在语义源头停下，改在下游猜。**  
   `Violation` 没有结构化严重度，下游便从英文 `detail` 用正则反推；“departs before”不匹配只识别“late by”的正则，罚值退化为 1.0。见 `problem_hgs/evaluation.py:1034-1091,1202-1242`。  
   **判断**：当任务要求“不动 producer 但把 consumer 修好”时，正确动作本应是停下申请修改源头；AI 为了交付，往往会复制规则、解析文本或补默认值，于是变量和判断从诞生起就不可信。

4. **短试奖励缓存命中，却不检查所有权和寿命。**  
   `cost.py` 曾用短命列表的 `id()` 作键，又在 value 中强持有它，缓存从 45.3 万涨到 362.3 万项，解释至少 4.5 GiB 增长；浅层测试完全看不出来。见 `CURRENT_PROJECT_CONTEXT.md:425-449`。随后 SISR 又复刻了 `id(data)` 加强引用模式，见 `foundation_review_20260817/report.md:100-112`。  
   **生成机制**就是“先让这次调用快一点”，却没人被要求回答缓存由谁释放、运行结束后是否归零。

5. **学习了算法名词，却没有继承人类实现。**  
   解码器面对标准 Split 问题仍保存全部历史，形成指数膨胀；换成 DAG 后解码快 541 倍，证明病因是实现写笨，不是问题本身困难。见 `CURRENT_PROJECT_CONTEXT.md:375-394`。自造种群又重复了上游已有的双池和自适应罚分，且自身罚分窗口没有真正触发，见 `pending_decisions.md:1551-1558`。  
   更严重的是，`IntegratedGeneticAlgorithm`、`ExternalPopulation`、`HGSControl` 不属于 PyVRP 0.12.2，却被放进 `third_party`；当前包的 README 反而声明项目 controller 应位于目录之外。见 `walk_first_20260818/report.md:90-97`、`third_party/setp_hgs_kernel/README.md:16-25`。

6. **“以后可能有用”制造防御性垃圾。**  
   零调用的退役外循环保留约 924 行，`CandidateStatus.RESTARTED` 没有生产者也没有消费者，SISR 全局缓存默认路径又不使用。walk_first 一次便净删 947 行生产源码，相关事实见 `walk_first_20260818/report.md:136-146`、`source_changes.csv:1-9`。  
   **判断**：只要新增字段、fallback 和兼容分支不需要证明真实消费者，AI 就会不断用代码购买虚假的“稳妥”。

## 二、必须落成机器闸门

以下成本是工程估算，不是本轮实测；当前可用锚点是相关 228 条回归仅用 4.25 秒，见 `walk_first_20260818/report.md:148-154`。

| 机器规则 | 能拦住的历史事故 | 现成工具 | 单轮成本 |
|---|---|---|---:|
| `third_party` 必须与冻结 upstream manifest 逐文件一致，新增或改动文件立即失败 | 三件项目造件混入 PyVRP 目录 | `pre-commit`＋`git diff --no-index`＋SHA-256 manifest＋`reuse lint` | 1–2 秒 |
| 固定依赖方向：生产包不得 import `solver/scripts`；项目代码不得进入 vendor；实验只能调用统一 runtime | 技术 CLI 被 17 个消费者进口、双身份、载具复制控制流 | `import-linter` 或 `grimp` | 1–3 秒 |
| 新增函数复杂度≤10、分支≤12、语句≤50；薄适配文件≤250 个有效源码行；旧债只准下降 | 指数解码、千行 main、924 行退役外循环 | Ruff `C90/PLR/SIM/PERF`＋`xenon`或短 AST 行数检查 | 1–3 秒 |
| 新增未使用函数、枚举成员、参数和 import 直接失败；公开状态必须同时有 producer 与 consumer | `RESTARTED`、无效开关、退役函数 | `vulture --min-confidence 90`＋AST 引用检查 | 2–5 秒 |
| 禁止用 `.detail`、异常字符串或正则决定罚值、可行性和终态；禁止宽捕异常后返回默认业务状态 | 正则罚值、已知失败样本 fallback、异常被降级 | `semgrep`＋Ruff `BLE/TRY` 规则 | 1–3 秒 |
| 禁止模块级可变缓存、`id()` 缓存键和无上限 `lru_cache`；缓存必须属于一次 run/instance | `cost.py` 与 SISR 泄漏、成群无界缓存 | `semgrep`/AST；再用 `pytest`＋`tracemalloc`或 `pytest-memray` 做重复构造释放测试 | 静态 1 秒；内存门 30–90 秒 |
| 转换、排序、时间、SOC、服务量和配置身份必须做性质测试 | `A,B,A→A,A,B`、双时钟、开关漏传、状态继承错位 | `pytest`＋`hypothesis` | 10–30 秒 |
| 任一终止、可行、客户、需求或审计事实失败，必须 `accepted=false`、退出 2、无 `DONE`，批处理必须拒收 | 全套假完成链 | 复用 `experiment_acceptance.py`，对每个载具做 pytest 故障注入 | 5–10 秒 |
| 适配件支持的共同子域必须与上游逐项对拍；测试再用 mutation testing 检查是否真能发现错误 | 重写 HGS 行为却自称 copied、测试只验证自己 | `pytest` differential test＋`mutmut` | 对拍 20–60 秒；单件验收 2–10 分钟 |

前六项进每次提交，通常不到 20 秒；后三项在合并适配件时执行。它们不跑正式求解实验，也不再产生一套人工审计报告。

## 三、薄适配件怎样才能信

“薄适配件”只能做四件事：类型转换、单位转换、项目状态补充、上游调用结果回填。它不得拥有种群、选择、重启、搜索循环、候选枚举、分支定界或接受策略；一旦需要这些，它就不是 adapter，而是新的算法组件。

建议采用以下硬规格：

- 单件生产代码不超过 250 个有效源码行；单函数不超过 50 条语句、复杂度不超过 10。
- 输入输出使用不可变的 typed dataclass；禁止 `Any`、模块全局状态和隐式默认开关。
- 每件只连接一个上游职责，由一个 `RunContext` 持有其生命周期；缓存随 context 销毁。
- 文件头明确写 `PROJECT-OWNED ADAPTER`，并指向机器可读的 `component.toml`：上游 URL、commit、许可证、原文件、项目合同、源码哈希。
- 强制五类测试：共同子域与上游对拍、输入输出往返、失败原样传播、时间/SOC/服务量守恒、重复创建后对象与缓存释放。
- “逐件验收单”不由 AI 手填，而由 Ruff、覆盖率、Hypothesis、内存门、upstream diff 和 pytest JUnit 自动生成；一次只验一件。

walk_first 剩余缺件中，动态切点、唯一执行身份、企业事实账、typed violation 可以成为薄适配；typed violation 仍须单独获准改 producer。shared charger coordinator、第二父代属性遗传、非负代理候选枚举会改变搜索空间，**不能借 adapter 名义偷渡**。完整 HGS evaluator bridge 只有在不重写 GA 生命周期时才算 adapter；否则宁可继续缺件。

## 四、终态代码应该多大

先更正一个数字：`7949` 是 walk_first 触及的八个生产文件之和，不是全仓生产代码总量，证据是 `source_changes.csv:1-9`。本轮只读计数显示，单是 `problem_hgs/` 已有 24,338 行，`solver/scripts/` 还有 37,314 行；其中混有条件路径、历史载具和构造脚本，不能全部算活跃算法，但足以说明真正的清理量级。

**我的工程判断**：

- 论文算法核心＋四至六个 adapter：3,000–5,000 行；
- 必须保留的项目真值——Duty、实体车、多趟、SOC、动态锁、企业账、完整评价：4,000–6,000 行；
- 活跃项目生产代码合计目标：**7,000–11,000 行，中心约 9,000 行**；
- walk_first 那八个文件应从 7,949 行继续降到 **2,500–3,500 行**；
- vendor、测试、数据构造和历史证据不计入上述数字；测试代码可以多于生产代码。

终态目录只需要四层：原样 `third_party/`；项目 `domain/` 真值；`adapters/`；一个 `runtime/` 加薄实验配置。技术脚本不得再成为被生产代码反向进口的库。

## 五、出处卫生

唯一可靠规矩是：**目录名和 docstring 不算出处，manifest 与字节差异才算。**

每个文件必须且只能属于四种身份：`UPSTREAM_UNMODIFIED`、`UPSTREAM_PATCHED`、`PROJECT_ADAPTER`、`PROJECT_DOMAIN`。原样上游留在 `third_party`；修改过的上游保留原快照和独立 patch，不再称“机械改名后行为未变”；项目适配和项目真值全部移出 `third_party`。CI 对 upstream manifest 多一个文件、少一个文件或哈希不同都直接失败。

现有三件应立即在账面上更正为：**项目拥有、于提交 `15ea99190…` 首次出现、上游不存在、具体由人还是 AI 编写为 UNKNOWN**。Git 历史只能证明它们属于本项目，不能证明作者身份。直到逐项来源比对完成，都不得再称 copied PyVRP。

这套方案的核心不是再要求 AI “谦虚、认真、少写一点”，而是让错误的局部聪明无法通过机器闸门，让真正不可外包的项目语义保持小、单一、可对拍、可释放、可追根。
