## 第二部分：两层反思的结论（两 AI 独立成稿后合流，分歧已定案）

### 方向层（该怎么走）

1. **需要"明显效应"的只有三行**（你 08-08 的 P07 原文）：时变碳、混合车队、动态；
   其余五行达标线是"正确、合格、不拖累"，其中三行已见合格证据。"八行全卡死"不成立。
2. **总病根＝四件事绑成一件**：底座能不能跑／机制有没有被触发／对照是否回答正确问题／
   算法强不强。任何一处出错都被当成"修算法"，算法修快了实验还是没数据。
   E3、E5、E7 三次翻车同源：没先证明"待研究的差异真的被送进了算法"。
3. **顺序反过来：先算后造**。每行开工前先用算术算效应上限（不需要求解器），
   上限不清就改已批准的设计参数（碳价扫描、溢价），不开跑。
4. **算法是量具不是选手**（对机制行）：对照臂同预算即公平；机制行预算按需。
5. **"跑完了"≠"跑到了"**：谈"无效应"之前必须先证明机制被执行过（提案计数非零）——
   八臂 0 提案照过包完整性验收就是反例。但提案非零而接受或改解为零，本身就可以是合法的
   零效应结果，须如实报告；执行证书只区分"没执行"与"执行了但无改善"，**不筛选结果方向**。

### 技术层（为什么代码烂、怎么机制性治）

**六条病理**（每条有仓内实锤，详见技术立场原文）：写码免费删码要证据→只加不减；
局部任务闭环无全链责任→双身份双时钟；奖励"看起来完成"→围绕退出码闭环；
代码长得像任务书→防御性噪音；语义源头不肯停、在下游猜→文案正则定罚值；
学名词不继承人类实现→指数解码、自造种群、三件出处不明文件。

**治法总纲**：通用算法只准用可核上游；项目自写压缩成有尺寸上限的薄适配件；
**一切质量要求交机器执行，AI 的报告与自我保证一律不算验收。**
九条机器闸门全部用现成开源工具组装：其中**前六条进每次提交（合计约 20 秒内）**，
后三条（内存释放门 30–90 秒、上游对拍与变异测试 2–10 分钟）只在合并适配件时运行。

**标注**：闸门耗时、适配件行数上限（≤250 行等）、终态代码量（活跃项目生产代码
7,000–11,000 行）均为 **AI 工程提案值**，不是实测事实；批准后按实际运行校正。
现状实测：仅算法主目录即 24,338 行、脚本目录 37,314 行。方向判断：论文配套开源仓库的
主体通常是成熟库本身、作者自有代码只是薄壳——**出路是缩小我们的代码面，不是把几万行写漂亮**。
