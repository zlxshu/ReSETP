# 对《实验方案设计》的平级挑战（2026-08-19）

`STATUS_READ_ONLY_CHALLENGE_COMPLETE`

审查对象：`experiment_plan_20260819.md`。本轮只读源码、剖析包、碳价批原始产物和最新提速试跑包；
没有修改源码、配置、测试或既有实验产物，也没有启动求解器。唯一写入是本文件。

## 先给结论

我攻得动，而且攻到的是主梁：**这份方案证明了“私有求解器有一个值得修的吞吐瓶颈”，但没有证明
“修完后八行目标必然出现”。** 主张链最迟在第 4 环必断，第 2、3 环本身也需要更正：路线内核并非
没有执行；“9/9、平均 8.52%”无法由原始成功包复现。

如果“达成目的”指**产出完整、诚实、可解释的八行答案，允许其中有零效应或反向效应**，方案可以改成
一份能闭合的实验方案；如果“达成目的”指**八行都必须出现预定正效应**，现有证据不支持“一定”，
任何随机优化试跑也不能把正效应事前变成数学必然。要使用“一定”，只能逐行给出解析下界或穷举证明；
当前只有若干“存在作用空间”的上限与见证，不是正效应下界。

## 一、主张链逐环攻击

### 第 1 环：瓶颈定位——这条我攻不动，但要收窄措辞

`FACT`：单个 `0.20/asap/seed_1` 剖析单元中，互斥分类确实给出：路线级估价 29.396%、充电修复与
排程 24.535%、路线内核 `LocalSearch.__call__` 0.024%。分类总和等于 cProfile 可归属的
595.459076 秒。证据：`solver/reports/cycle_profile_20260819/report.md:91-108`。

这足以证明：**该私有单元的主要墙钟花在系统级候选的充电修复、估价和完整真值链，不在原生路线
局部搜索本体。** 这条我攻不动。

但它只是一种实例、价格、策略、种子的剖析，而且 cProfile 显著放大绝对墙钟；它不能自动代表动态、
协同、公平和公开 28 题。报告自己也明确说绝对墙钟不可当生产吞吐，见同报告 `:24-27`。

### 第 2 环：“搜索几乎没被执行”——不成立

`CORRECTION`：0.024% 是**耗时占比**，不是**执行次数占比**。

同一个剖析包记录：

- `LocalSearch.__call__` 实际调用 **81 次**；
- 教育循环完成 **81 轮**；
- 路线内核提出 92 个动作、38 个进入评价、3 个被接受；
- 全部机制动作共进入 `evaluate_move` **81,561 次**；
- 其中跨场协同提出 51,254 次、多趟 24,256 次、时变充电 5,474 次、整车类型交换 485 次；
- 跨场协同接受 50 次、整车类型交换接受 24 次、多趟接受 2 次，时变充电接受 0 次。

原始入口：`solver/reports/cycle_profile_20260819/run/metadata.json:5-49,25115-25160`；
调用路径：`integrated_private.py:1124-1204`、`education.py:488-604`、`kernel_proposals.py:470-600`。

所以更准确的叙述是：**搜索已经执行，但一次外层遗传迭代会展开出大量昂贵的系统级候选评价，600 秒
只完成 3 个外层迭代。** “搜索没执行”把“外层迭代吞吐低”和“搜索链没有动作”混成了一件事。

这也直接否定“不是机制设计、不是作用条件”的排他归因：本包没有机制开/关反事实，只能定位即时
瓶颈，不能在机制、场景、算法和实现四类原因中排除前三类。

### 第 3 环：“时间有因果作用，9/9、平均 8.52%”——原始数据不支持

我按自然、可复算的定义重新读取 30 个成功单元：`decision.json.accepted=true`，并以各自
`convergence_diagnostics.csv` 的最大 `cycle` 判断是否“跑满至少 4 周期”，比较 cycle 2 与最终周期的
`current_solution_raw_cost`。

`CORRECTION`：结果不是 9 个，而是 **19 个**；不是 9/9 都再降超过 1%，而是 **12/19**；
平均再降 **6.151961%**、中位 **4.581612%**、范围 **0%–18.097025%**。有 7 个反例不超过 1%：

| 单元 | 第 2 周期后降幅 |
|---|---:|
| `0.20/asap/seed_5` | 0.879612% |
| `0.20/cost_min/seed_2` | 0% |
| `0.20/cost_min/seed_3` | 0% |
| `0.20/cost_min/seed_4` | 0.826637% |
| `0.20/cost_plus_carbon/seed_2` | 0.805403% |
| `0.60/asap/seed_4` | 0% |
| `0.60/cost_min/seed_2` | 0% |

如果原 9 个采用了另一条筛选规则，当前方案没有写出该规则，因此 `9/9` 无法复现；若筛选规则包含
“后面确实改善”，则会形成按结果选样。原事故复盘中的分组也写成“4 周期 n=6、5 周期 n=3”，
但原始 `raw_runs.csv` 中成功单元实际出现 6、7、9、10 周期，说明那张分组表也需要回查。

即使修正后仍能安全说：**部分单元在第 2 周期后还有明显的总成本改善空间。** 不能安全升级为：
“更多时间必然使每个机制效应露出来”。最优值轨迹本来就只能持平或下降；总成本继续下降，也可能来自
普通重排、跨场、车型交换或多趟，未必来自正在画图的那一个机制。

### 第 4 环：“吞吐提高 → 机制效应露出来”——全链最弱、当前必断

`INFERENCE`：提速后，在相同墙钟下外层迭代和候选评价数通常会增加；这是合理预期。
但下面三种结局都与现有证据相容：

1. 两个对照臂都同速变好，臂间差仍为 0；
2. 当前未收敛造成的假差异被消掉，效应反而缩小；
3. 搜索最终稳定在与预期相反的结构上。

项目自己的效应算术已经写明这些最坏情形：时变碳可能因车辆可用窗锁死而三策略重合；混合车队可能
因路线重排和充电约束抵消纸面优势而车辆数不变；动态阈值可能只改变批次数而成本、排放和路线不变。
证据：`effect_arithmetic_20260818.md:91,141-143,186-188`。这些不是我新造的担忧，而是方案上游已经
承认的零效应可能。

剖析包还给了一个直接警告：时变充电候选已经提出并评价 **5,474 次，却 0 次接受**。这不能证明
时变机制无效，也不能证明再多时间一定会接受；它恰好说明“动作执行过”和“效果出现”必须分开验证。

**能提前降低不确定性的最便宜证据**，不是再看总成本曲线，而是做“机制差值—预算曲线”：同一实例、
同一随机种子、同一固定工作量，在至少两个预算档上同时跑机制开/关或策略 A/B，观察配对差是否随着
预算增加从噪声中稳定出来。它仍只能增加把握，不能证明数学必然。要排除“无限机时仍为零”，必须有
该机制的正效应下界或可穷举的小实例反例；当前只有作用空间上限和一粒见证。

### 第 5 环：提速动作——方向成立，但当前方案还不能开工，也没有提速数字

最新提速试跑已经返回 `HALT_PROTECTED_COST_REQUIRED`：前三项都必须直接修改受保护的 `cost.py`；
在装载层预建索引或先小写化，无法删除 `cost.py` 内无条件发生的遍历、`.lower()` 与 `getattr`。
没有启动短对拍、600 秒前后对比、RSS 测量或 568 回归。证据：
`solver/reports/speedup_trial_20260819/report.md:5-25` 和同目录 `decision.json`。

因此原方案的“前四项纯装载期去废码、可以直接做”已经被新证据推翻：前三项需要用户当次批准触碰
受保护文件；第 5 项仍需用户批准逻辑改动。**当前方案的第一阶段在授权上是 HALT。**

提速量级也不能从 53.9% 直接推出：

- 29.396% 的 `route_model_cost_delta` 累计时间已经包含它下面的 `cost.evaluate`、城市查表、价格读取等
  子调用；把这些叶函数占比再与 29.396% 相加会重复计算。
- 即使把 `route_model_cost_delta` 整段变成零，Amdahl 上限也只有 **1.416 倍**；最新试跑报告已给出
  同一算式，见 `speedup_trial_20260819/report.md:44-49`。
- 另一个 24.535% 的充电候选构造与排程不是第 5 项增量估价本身，当前五项没有证明能消掉整段。

所以“十倍提速后仍可能无效应吗”的答案是：**逻辑上完全可能；而且当前五项连十倍提速本身都没有
量级依据。**

## 二、八行中，哪些不是“多给机时”能救的

这里分清“能填一行数字”和“能交出该机制的正效应”。描述性行通常能填；正效应不是机时承诺。

| 行 | 当前方案能否保证 | 机时以外缺什么 | 解锁它的最小动作 |
|---|---|---|---|
| 1 时变碳 | 能保证跑出数据；**不能保证正效应** | 可用充电窗可能锁死策略差异；现有 5,474 个时变候选 0 接受 | 先做固定路线的可行时窗精确反事实，再做同种子、同工作量的策略配对预算曲线；若精确反事实为 0，换机时无用 |
| 2 混合车队 | 能保证跑出构成；**不能保证构成随碳价变化** | 纸面临界里程会被载重、电池、充电窗和路线重排抵消 | 先对现有路线做逐车 CV/EV 可行成本包络，再用固定工作量配对跑验证结构切换；若一类车在完整约束下支配，换机时无用 |
| 3 多企业协同 | **有较强见证，可救** | 正式 runner 必须关公平；旧伪关闭臂不是单干 | 按 P124 把“真实两家单干之和 vs fairness-off 联合最优”写进正式合同后重跑 |
| 4 实体车多趟 | 描述性趟数能填；**机制增量不能靠汇总得到** | 若该行要说“多趟带来收益”，缺单趟反事实 | 先确定该行只是描述还是因果；若是因果，增加同输入、同预算的 multi-trip off/on 对照，不能再写“增量机时 0” |
| 5 成本分项/参数 | **可交** | 只依赖最终合格解与固定汇总口径 | 冻结字段口径，从已批准正式解汇总；本行不需要独立求解 |
| 6 动态需求 | **当前方案无论给多少机时都不能合法开跑** | 用户尚未批准；且 D 胜全信息静态 S 的把握低，S 具有信息优势 | 用户先在“D 对机械在线 M 的改进，S 只作信息上界”与“仍要求 D 胜 S”之间拍板；前者可实验，后者不能承诺 |
| 7 公平分配 | **在协同有正剩余时可交** | 必须基于 fairness-off 协同赢家做事后分摊，不能继续把公平塞进效率搜索 | 复用现有分摊适配器，对每个正式协同赢家做闭合分摊并报告参与裕量 |
| 8 公开对比 | 数字最终能跑出；**不落下风不能保证** | 私有 `cost.py`/充电链提速不经过公开入口；28 题各臂预算和算法质量均未知 | 独立标定公开两臂并按同批协议跑；预先接受“可能落后”的合法结果，不能靠私有提速担保公开胜负 |

最明确的三个“不是时间问题”是：动态的授权与主张、若多趟要讲因果时缺少对照、公开表与私有充电
提速没有代码依赖。若“目的”要求第 1、2、6、8 行都必须是预定方向的正效应，那么这四行也都不是
无限机时能担保的。

## 三、配不上“一定”的缺证据清单

| 缺什么证据 | 怎么最便宜地补 | 补不上会怎样 |
|---|---|---|
| 每一行究竟要“有数”还是“必须有正效应”，以及对应对照和否证结果 | 用一页逐行合同写清主张、对照、允许的零/反向结果；不跑求解器 | “完成”含义漂移，任何结果都无法证明方案达成了用户要的目的 |
| 第 3 环的可复算预算证据 | 公开脚本或在报告中固定筛选规则，重算全部 30 个成功单元；保留 19 个单元与 7 个反例 | 9/9 和 8.52% 必须撤回，不能用它支撑因果链 |
| 私有提速的授权与可实施性 | 用户选择是否允许最小 `cost.py` 补丁；第 5 项增量逻辑另行选择 | 阶段一保持 HALT，后续“提速后标定”没有前提 |
| 真实提速倍数、固定周期语义一致、固定墙钟吞吐与 RSS | 获批后做同种子固定周期对拍，再做 600 秒前后吞吐/RSS；不先跑全批 | 排产仍是未知数，不能写 2–3 倍，更不能写十倍 |
| “更多预算让机制差值显现”，而非只让总成本下降 | 每个关键机制先做少量同种子开/关配对，在两个固定工作量档保存差值轨迹 | 第 4 环仍断；正式 210 单元只是昂贵下注 |
| 时变碳的可行时窗正效应下界 | 对代表路线做精确充电时窗枚举，先算可移动电量的**下界**而非 216.26 kg 上限 | 只能说有理论上限，不能说一定会出现策略差异 |
| 混合车队完整约束下的非支配性 | 对当前路线逐车计算 CV/EV 完整可行成本，确认至少一部分路线两型各有优势 | 可能收敛得越好越趋向单一车种，图 5 仍无切换 |
| 多趟行的科学角色 | 明确描述性或因果性；因果性则补 off/on 对照 | 只能报告“出现了几趟”，不能归因“多趟带来收益” |
| 动态主张与用户批准 | 把 D−M、路径变化、D−S 信息差三个问句一次性交用户选择 | 动态行不能启动；若强求 D 胜 S，方案可能在信息论上目标错位 |
| 公开轨独立预算与质量证据 | 用 1 题标定每臂收敛，再决定 28×10×2；不等待私有 `cost.py` 提速 | 公开机时和胜负继续 UNKNOWN，私有修复不会解锁它 |
| 目标期刊的重复与报告协议 | 定点读取目标期刊原文页码，冻结种子数、汇总和失败处理形态 | 即使有数，也不能说明正式协议为何成立；但不得自造新门槛替代 |

关键点：这些廉价检验能让方案变成“必然给出可信答案”的方案，却不能让自然界和随机优化器“必然给出
预定正效应”。两种“一定”必须分开。

## 四、优先级：我会改，而且不是小调

原序列是：修引擎 → 重标定 → 协同公平 → 时变碳/混合车队 → 多趟/成本 → 公开 → 动态。
我不同意，理由有三条：阶段一当前缺受保护文件授权；协同/公平合同和动态主张是逻辑前提，不应等机器
修完才定；公开入口不经过私有充电成本链，不存在“私有提速后才能公开标定”的依赖。

我的建议顺序（`DECISION`，不是用户决定）：

1. **先闭合八行的主张与授权**：一次性确认 `cost.py` 是否可改、第 5 项是否可改、动态比较问句、
   多趟是描述还是因果；同时把协同 fairness-off、事后公平分摊的正式合同修正好。
2. **私有引擎最小提速 → 语义对拍 → 私有预算标定**；拿不到实测倍数就不排 210 单元。
3. **先做时变碳与混合车队的廉价作用下界/配对预算试探**；只有差值随预算可辨识，才开 210 单元。
4. **协同＋公平正式批**；多趟若仅描述随解汇总，若讲因果则另配 off/on，不再记“增量 0”。
5. **公开轨独立标定和正式批**；它与私有提速只共享机器资源，不共享性能病灶，可在设计上提前准备。
6. **动态获批后标定并运行**；位置靠后是因为授权和每决策点预算仍未知，不是因为它不重要。

成本分项随每个合格正式解即时汇总，不需要单列成一个晚阶段。

## 五、有没有倒果为因：有，而且是双向反馈被写成单向因果

当前可证的直接原因是：**大量系统级候选会触发昂贵的充电修复、路线估价与完整评价，从而压低单位
墙钟内的外层迭代数。** 这解释吞吐，不解释机制差值。

当前实现的因果结构更接近：

`机制/提案设计 → 候选数量与种类 → 充电修复和真值评价成本 → 墙钟内外层迭代数`

同时：

`机制/提案设计 → 能否提出真正改变该机制决策的动作 → 机制效应`

也就是说，充电链慢既可能是独立的实现浪费，也可能是机制提案枚举过宽的结果；本包里跨场与多趟合计
提出 75,510 次动作，而路线内核只有 92 个动作，就是反方向因果确实存在的证据。把所有弱效应归结为
“搜索没运行”，等于跳过了候选质量、接受边界、对照设计和作用条件。

我不会因此反对先做低风险去废码：它有直接墙钟证据，而且能提高候选吞吐。我要否定的是把“值得提速”
写成“提速后效应必出”的那一步；前者成立，后者目前没有证据。

## 最终五答

1. 主张链最弱的是第 4 环，第 2、3 环还各有一处事实错误。
2. 动态、因果型多趟和“公开不落下风”都不是多给私有机时就能交；第 1、2 行的正效应也不能由机时担保。
3. 最关键缺证是同种子、同工作量下的“机制开/关差值随预算变化”，而不是总成本继续下降。
4. 优先级要改：先闭合主张/授权/对照，再私有提速标定；公开轨独立，动态先拍板后排机时。
5. 有倒果为因：充电链慢是已证直接瓶颈，但“机制设计 → 海量候选 → 充电链慢”的反向路径同样已在原始计数中出现。
