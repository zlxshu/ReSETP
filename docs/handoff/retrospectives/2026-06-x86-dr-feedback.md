# 2026-06 x86 DR 工作流反馈复盘

本文件是对本周“校准 x86 DR 趋势 pilot / 继续救 DR-ALNS”工作流的反馈复盘稿。它只基于本机 Codex 会话、memory 摘要、`D:\ReSETP` 仓库报告和用户在当前线程提供的片段；外部 Claude/Fable5 原始对话、Zotero UI 操作记录、M1 侧未导出的聊天记录没有被直接核验。

## /feedback 人话版

我想让 Codex/Claude 帮我把 x86 线 DR-ALNS 真正训练成有效算法，最好全规模三班倒都能领先强基线，而不是只跑完实验。这个任务难在跨机器、长训练、多轮诊断、文献/代码/仓库证据都要对齐。实际过程中 Codex 完成了很多阶段工作，但多次把“训练健康/接口通过”说得像“目标成功”，也把 M1 同步、repo 事实、DR 主目标混在一起；回答有时太技术化、探测太碎，同一失败根因还出现多个版本，让我难以判断可信度。后来我通过强制说人话、低频心跳、文献/Zotero/网络优先、Superpowers 子代理通读、阶段 gate、HALT 机制和人工介入来纠偏。最终 x86 DR 证明了可训练、可全规模、小幅非劣，但没有达到强 DR-ALNS 或领先第二名 10%。下次我只会把类似任务交给能持续守住目标、标清事实/推论/不确定性，并主动把阶段完成和目标达成分开的系统。

## 一句话结论

这周 x86 DR 线做了大量有效工程：迁移到 D 盘、跑通课程训练、做了多轮诊断、补了接口、完成全规模训练和评测。但从用户目标看，它没有成功。成功标准不是“训练跑完”或“某个 gate PASS”，而是把 DR-ALNS 做成强算法，至少接近用户设定的“领先第二名 10%”。最终 Pilot17 只做到小幅非劣，离目标很远。

这不是单个 bug 造成的失败，而是长目标、多工具、多线程和强实验不确定性叠加后的协作失败：Codex 执行能力有用，但目标保持、证据优先、跨线程继承、阶段结论表达和“说人话”都不够稳。Claude/Fable5、Superpowers、Zotero/文献、M1 线本来应该分别承担判断、并行查证、方法依据和主线语义同步，但实际工作中这些角色经常混在一起，导致用户需要反复纠偏。

## 1. 用户目标和为什么重要

用户真正要的不是一个“能跑的 PPO”，也不是“DR 训练曲线健康”，而是一个可以放进算法对比实验里当潜在领跑者的 DR-ALNS。这个目标重要，是因为它关系到后续论文主线和算法对比可信度：如果 DR-ALNS 只是赢弱基线、赢默认参数、或者只在小预算里好看，就不能支撑“强算法”的叙事。

这个目标从一开始就带着硬边界：x86 线只做同机相对比较，不能和 M1 绝对数横比；不能乱改 `cost.py`、`check.py`、`search/evaluation.py` 或 winner 语义；遇到不确定要查仓库、文献、Zotero、互联网和已有证据，不能靠直觉猜；长跑时要低频心跳，失败再升频。证据见 `E01` 到 `E08`。

## 2. 任务为什么难

难点不在“写一段训练脚本”，而在四件事同时成立。第一，x86 机器资源有限，最初 H 盘线已经因为资源探测和吞吐证据需要迁移到 D 盘。第二，DR-ALNS 不是普通监督学习，训练健康不等于搜索能力强，必须拿同机同预算强基线比较。第三，用户目标随着证据推进不断收紧：从 pilot07 的降预算趋势，到 pilot08 课程训练，到 pilot09/10 的 headroom 诊断，再到 pilot14-17 的接口重建和全规模训练，任何一个阶段结论都不能冒充最终成功。第四，M1 线在修普通 ALNS 语义，x86 又要主动同步关键 bugfix，但不能被 M1 同步带偏成“普通 ALNS 主线”。

这意味着 Codex 需要同时做好执行、证据留存、边界遵守和目标复位。实际结果是执行做了不少，但目标复位和解释稳定性不够。

## 3. 实际工作流

实际推进大致分成六段。第一段是 H 盘资源探测和 D 盘迁移，结论是 12 actor 资源探测不能硬推，`D:\ReSETP` 成为 x86 DR 线自包含工作区。第二段是 Pilot07/08：降预算和课程训练都跑完，但 verdict 是 WEAK，说明“能训练”不等于“比 AlphaUCB 强”。第三段是 Pilot09/10：文献优先和低成本诊断发现旧路线的算子选择没有 headroom，搜索参数有静态调参空间；但 block_meta 学习没有超过最优静态参数，结论是 WEAK_RETUNE。第四段是 Pilot11-14：开始承认问题在接口和候选生成，不是再长训就能解决，补动作空间、观测、候选生成和全阶梯 manifest。第五段是 Pilot15/16：短训和全规模训练健康通过，说明训练管线可以跑全规模。第六段是 Pilot17：最终评测只得到约 +0.57% 的小幅非劣，远低于 +10% 目标。

这套流程的价值是把很多错误路线排除了；它的问题是中途多次把“排除错误路线 / 通过阶段门”表达得太像“已经接近成功”。证据见 `T01` 到 `T14`。

## 4. Codex/Claude 哪里挣扎

最核心的问题是目标保持不稳定。用户多次提醒“现在已经完全跑偏了”“M1 对齐是为了排错，不要被带偏”，说明 Codex 容易把当前手上的技术动作当成目标本身。比如同步 M1 语义是必要的，但不是把 x86 线改成普通 ALNS 主线；训练健康是必要的，但不是强 DR-ALNS 成功。

第二个问题是解释不稳定。同一个“为什么学不出来”的问题，先后出现过“早停/浅层收益问题”“搜索参数有 headroom”“block_meta 可以救”“候选/interface 才是根因”等多个版本。后续证据显示，有些说法是局部症状，有些是被推翻的假设，有些才是当前最可信的判断。问题不在于科学探索中假设会更新，而在于当时没有把“事实、推论、猜测、待验证”分清，导致用户感到三次回答三个版本，不知道该信哪个。证据见 `V01` 到 `V06`。

第三个问题是语言和节奏不适配。用户要的是“这对我意味着什么”，而不是机器日志。Codex 经常给出过多路径、状态、指标，却没有把它们翻译成“目标是否更近、是否偏离、还差什么、该停还是该继续”。长任务中探测和心跳频率也不稳定，稳定训练时信息太碎，异常时又需要用户主动追问。

第四个问题是工具分工没有一直守住。理想分工是：Codex 负责 x86 本地执行和证据；Claude/Fable5 负责判断、纠偏和人话复盘；Superpowers/子代理负责并行查证；Zotero/网络负责避免拍脑袋；M1 线负责主线语义和 bugfix 参照。实际中 Codex 经常同时做执行、判断、规划和解释，导致它在不确定时仍会先猜，而不是先回到文献、仓库报告或已有证据。

## 5. 用户后来怎么纠偏

用户采用了几类纠偏办法。第一是强制边界：明确“不训练、不评测、不改核心语义”“只提交 9 个文件”“不要 push”“异常就停”等，使 Codex 的可操作空间缩小。第二是强制语言：要求“说人话”“用 Fable5 的方式”“不要讲我看不懂的词”，把机器日志转成用户能验收的结论。第三是强制证据优先：要求先查 Zotero、网络、仓库文献、参考代码和 M1 线，不让 Codex 只凭判断给答案。第四是引入 Superpowers 和子代理，把长线程复盘、文献查证、证据抽取拆开做。第五是引入阶段 gate、HALT、READY、PASS、WEAK 等标签，并反复强调这些标签不能等同最终目标达成。

这些方法有效降低了跑偏风险，但代价是监督成本很高。很多情况下，用户不是在验收 Codex 的工作，而是在持续担任项目经理、方法审稿人和故障刹车。

## 6. 最终结果和需要改进的地方

最终结果是“部分完成，但目标未达成”。完成的是：x86 线环境迁移完成；多个 pilot 有记录、有报告、有 gate；DR 训练线能跑课程、能跑全规模、能出 checkpoint；若干错误路线被排除；M1 关键语义修复被识别为需要同步的事实。未达成的是：没有训练出强大的 DR-ALNS，没有达到领先第二名 10%，没有让用户可以放心把类似无人监督长目标完全交给 Codex/Claude。

下次要改，第一是任何阶段开始前都先重述“我们现在到底在解决什么问题”，并把当前动作和最终目标之间的关系说清楚。第二是所有结论必须标注“已证实 / 当时猜测 / 待验证”，尤其是失败归因。第三是对长训练采用低频心跳，稳定时只报“是否偏离、是否需要干预、预计多久”，异常时再升频。第四是文献和参考代码要成为默认依据，不是用户追问后才补。第五是每次 PASS/READY 都必须同时写一句“这不代表什么”，避免阶段门被误读成目标成功。

## 对后续代理的工作手册

后续如果继续做 x86 DR，请先执行这个短手册：先读 `HANDOFF.md`、相关 pilot 报告、M1 最新语义修复和本复盘；再用一句话确认“本轮是否服务强 DR-ALNS 目标”；接着把任务分成“事实核验、方法依据、工程改动、短训验信号、长训/评测”五类，不允许直接跳到长训。每次实验报告必须写“这对用户意味着什么”，并显式区分训练健康、阶段门通过和最终目标达成。若要解释失败原因，必须列出来源、证据强度和是否已被后续实验推翻。
