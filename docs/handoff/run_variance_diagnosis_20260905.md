## 0. 一句话结论

**离散的 69%（A 批）到 96%（B 批）来自"同一车队构成下路线没搜好"，车队选择只占 31% 到 4%；

而"同车队下路线没搜好"这件事，本身几乎完全由一个开关决定：
**这次跑有没有多跑出一个确认轮（round 3）**。在固定车队里，多一轮值 18.5 元（B 批）
和 19.2 元（A 批）——比要检出的 7–10 元择时效应还大。

## 1. 离散的成分分解（问题 1）

### 1.1 按五项成本直接分解会得到不可读的结果，原因本身就是结论

| 批 | sd(total) | sd(cost_fix) | sd(其余四项之和) | corr(fix, 其余) |
|---|---|---|---|---|
| A 批 ideal P=0.2 | 17.09 | 99.38 | 88.08 | **−0.992** |
| B 批 ablation v5 | 12.92 | 83.28 | 78.16 | **−0.990** |

方差恒等式（总体方差，A 批）：
`Var(total) 263.0 = Var(fix) 9876.0 + Var(其余) 7757.8 + 2Cov(−17370.8)`
B 批：`150.2 = 6936.0 + 6108.3 + (−12894.1)`

所以按单项 sd 排名（fix 最大）会完全误导，逐项协方差份额会出现 452%、−214% 这种数，不能作为结论。

## 2. 收敛是否完成（问题 2）

### 2.1 外层轮次是什么、为什么次数会变

`runner.py` 第 722–922 行。外层是"轮"（`accounting.restarts` 是历史误名，等于轮数）：
每轮新建一个内核种群，用上一轮教育后的精确解投影作种子，跑内核直到
**连续 20000 圈无改善**；轮末把内核最终种群整体解码回精确模型评价并教育，取该轮最优。
`confirming_round=True` 时（这三批都是），**只要某一轮没能改善精确最优，整跑立刻停**（第 891–893 行）。

新批 C 的 `improvement_trace.csv` 逐圈核对：每一轮的
`iterations − 最后一次改善的 iteration` **恒等于 20000**（6 跑 × 全部轮，无一例外）。
所以耐心值实际就是 `stagnation_patience = 20000`，与 metadata 声明一致。
（注：`round_patience_by_round`、`round_patience_mode` 在这三批的产物里全是 `None`，
无法从 metadata 直接证实模式，上面这个 20000 是从圈数算出来的。）

### 2.2 内核在自己的代理目标上确实收敛了，精确目标没有

C 批 6 跑第 1 轮的最后一次代理改善出现在该轮圈数的 43%–63% 位置，之后 20000 圈空转。
A 批 10 跑同法反推（第 1 轮圈数 − 20000），最后改善位置在 11395–25650 圈，占该轮 36%–56%。
**内核对代理目标是收敛的。**

但精确目标不是。`convergence.csv` 每行 = 一轮末：

| 批 | 轮数=2 的跑 | 轮数≥3 的跑 |
|---|---|---|
| A | 9 跑，均值 2608.47，第 1 轮末即最终值 | 1 跑（run04）：2618.48 → **2579.91**，多赚 38.57 |
| B | 5 跑，均值 2650.74 | 5 跑，均值 2634.90，第 1 轮末均值 2663.90，多赚 16.34/22.98/17.69/28.31/**59.71** |

C 批 MTC-HGS run_02 更直接：**2614.18 → 2600.80 → 2591.83**，三轮单调下降，第四轮才停。

**判定：最差那几次不是"收敛到差的局部最优"，是"没跑到停就被停机规则叫停了"。**
停机规则是"第一轮没改善就收摊"，这是一次伯努利抽签，不是收敛判据。

### 2.3 最优跑 vs 最差跑的差别

A 批：最优 run04 = 2579.91，最差 run09 = 2625.63。

| | run04（最优） | run09（最差） |
|---|---|---|
| 轮数 | 3 | 2 |
| 总圈数 | 113563 | 58911 |
| 车队 | 2CV/3EV | 2CV/4EV |
| 第 1 轮末最优 | 2618.48（比 run09 的还差） | 2625.63 |
| 初始种群 | 25 个，attempts 25 | 25 个，attempts 25 |
| 参考初始解成本 | 3073.78 | 3073.78 |
| 墙钟 | 717 s | 328 s |
| 精确评价次数 | 153 | 142 |

**关键**：run04 第 1 轮末（2618.48）比 run09 的最终值（2625.63）只好 7 元；
它赢在拿到了第 3 轮，那一轮一次性赚了 38.57 元。
**初始解质量在两跑之间完全相同**（参考解 3073.78，20 跑全一样；初始种群大小 20 跑全是 25）。

同车队的直接对照更干净：A 批 2CV/3EV 里
run04 = 2579.91（3 轮）vs run05 = 2618.75（2 轮），差 38.84 元，可达空间完全相同，
run05 的内核在自己的代理上已经空转满 20000 圈。

### 2.4 内核投影 + 单次 LocalSearch 的检验：**没做，并说明理由**

原计划是把最差跑的解投影进内核跑一次 `LocalSearch.__call__`。放弃，因为它证不了要证的东西：
内核优化的是**摊薄了充电时间的代理目标**，而最终解是精确空间里 `refine` 之后的产物。
代理侧 LS 找到改善不能推出精确目标能降；找不到也不能推出精确目标降不了。
上面 2.2、2.3 的证据（同车队 38.84 元差、C 批三轮单调下降）严格更强，且不需要新代码。

## 3. 初始解的作用（问题 3）

- 20 跑的 `initial_population` **全部**是 `{requested 25, actual 25, attempts_exhausted false, reference_candidate_included true}`，attempts 在 24–31 之间。
- `enterprise_init_constructor = 'random'`：种子构造是随机的。
- `raw_runs.csv` 的 `initial_cost` 在 20 跑里**完全相同 = 3073.7789**——那是参考见证解（reference witness）的成本，不是 25 个初始个体的分布。
- **25 个初始个体的逐个质量没有落盘**：`initial_evaluations` 只在 `runner.py` 内存里，产物里（`best_solution.json` / `metadata.json` / `enterprise_ledger.json` / `raw_runs.csv` / 两个 convergence 表）都没有。

**判定：初始个体质量分布与最终解的相关性、以及"最终解与哪个种子共享最多客户归属"这两问，
在现有产物下不可判定（数据未落盘）。**
可以说的只有：初始种群大小、参考解成本、构造器类型三者在 20 跑之间完全一致，
因此**初始种群规模和参考解不是这 45 元离散的来源**；其余部分不作推断。

## 4. 内核参数与上游对照（问题 4）

`runner.py` 第 657 行 `kernel_params = SolveParams()`（无参构造，全用上游默认），
第 745 行 `KernelPopulation(kernel_bpd, kernel_params.population)`，
第 773–785 行构造 `GeneticAlgorithm`。

metadata 的 `effective_population`（20 跑一致）：

| 参数 | 本项目实际 | 上游 PyVRP / setp_hgs_kernel 默认 | 偏离 |
|---|---|---|---|
| min_pop_size (μ) | 25 | 25 | 无 |
| generation_size (λ) | 40 | 40 | 无 |
| max_pop_size | 65 | 65 | 无 |
| num_elite | 4 | 4 | 无 |
| num_close | 5 | 5 | 无 |
| lb/ub_diversity | 0.1 / 0.5 | 0.1 / 0.5 | 无 |
| tournament_size | 2 | 2 | 无 |
| repair_probability | 0.80（`SolveParams()` 默认，未改） | 0.80（`GeneticAlgorithmParams` 默认） | 无 |
| **num_iters_no_improvement** | **10**9（第 783 行硬写，注释 "no stagnation restart"）** | **20000** | **唯一偏离** |

μ=25/λ=40/elite=4/close=5 与 HGS-CVRP（Vidal 2022）的推荐一致，种群侧没有偏离。

**唯一偏离及其后果**：内核自己的重启被关死了。上游 PyVRP 在预算内会不断内部重启
（每 20000 圈无改善重启一次，重启保留精英），本项目改成**由外层轮次代替重启**，
而外层轮次**在第一次没改善时就收摊**。也就是说：
上游会在同一预算里做很多次"重启—再搜"，这里只做 1–3 次，
而且每次的评判标准是精确目标（每轮只测一次），噪声大。

再看一层，这是最要害的：**外层每轮末才做精确评价**。全程精确评价 102–186 次，
其中 25 次是初始化，剩下的按轮平摊到 40–80 次/轮，全都发生在轮末解码整个内核种群时。
所以精确目标在整跑里只被"采样"了 2–4 次。C 批可以看到极端情形：
MT-HGS run_01 第 2 轮、run_03 第 2 轮的内核代理改善次数都只有 1 次且发生在 iteration 0
（就是种子本身），也就是**那 20000 圈内核搜索在代理上零进展，精确最优却分别降了 9.11 元和 0.70 元**。
（iteration 0 = 种子最优，已按代码核实，不是只看注释：`GeneticAlgorithm.__init__` 里
`self._best = min(initial_solutions, ...)`，`run` 的循环是 `while not stop(cost(self._best))`，
判据在第一次 `iters += 1` 之前就被调用一次；`_KernelImprovementTrace._iteration` 从 0 起、调用后才自增。）
说明后续轮的收益主要来自"把重新多样化的种群再解码一遍、多抽 40–80 个精确样本"，
而不是内核搜索前进——**这是抽奖，不是搜索**。

## 5. 一个已被测出的具体病灶：轮间换代理把种子打成不可行

`runner.py` 第 734–744 行：从第 2 轮起用上一轮最优解实测的"趟间补电预留秒数"重建路网引擎。
A/B 两批（09-04 代码，取最大值）的第 2 轮预留值只有四个取值。按"第 2 轮有没有改善"交叉：

| 第 2 轮预留（秒） | 改善 / 总数 |
|---|---|
| 1875.3 | **3 / 3** |
| 2380.0 | 1 / 4 |
| 2614.1 | 1 / 8 |
| 2641.9 | 1 / 5 |

预留 < 2000 秒 vs ≥ 2380 秒：3/3 对 3/17，Fisher 精确检验 **p = 0.0175**。
第 1 轮的参考预留是 2031.7 秒；一旦第 2 轮把预留抬到 2380–2642 秒，
投影进内核的种子就被自己的预留顶成不可行，`GeneticAlgorithm._best` 永远够不到它们。

这与仓库里 09-05 的代码注释和记忆条目完全对上（取最大值把 25/33 个精确可行解打进不可行子种群）。
09-05 已改成取分位数：C 批实测第 2 轮预留 1250.6–2001.3 秒，全部低于旧的 2380–2642，
轮数随之变成 3/2/3 和 2/4/2。**这条已经修了，不是新设计，但值得在验收里复核。**

## 6. 可压的与不可压的（问题 5）

先把"不可压"的说清楚：
- **初始种群规模、参考解、构造器**：20 跑完全一致，不是离散来源，压它没有收益。
- **内核种群参数**：与上游、与 HGS-CVRP 论文完全一致，改它属于无依据调参，不建议。
- **车队构成之间的差异**：A 批占 31%、B 批占 4%，而且轮数与车队构成是**混淆**的
  （B 批 3 轮跑里 4/5 是 2CV/3EV，2 轮跑里 3/5 是 3CV/3EV）——更好的车队是多跑一轮**找出来的**，
  不是独立抽签。所以不该单独去"稳住车队选择"，稳住轮数它自己就稳了。

再看"轮数"这一维的证据（同车队内，剔除混淆）：

| 批 | 车队 | 轮数=2 | 轮数≥3 | 差值 |
|---|---|---|---|---|
| A | 2CV/3EV | 2599.10（n=5, sd 14.60） | 2579.91（n=1） | **19.19 元** |
| B | 2CV/3EV | 2650.34（n=2, sd 14.60） | **2631.87（n=4, sd 2.49）** | **18.47 元** |

两批各自独立、同号、同量级（18.5 / 19.2 元），n 分别是 1对5 和 4对2，小样本，不给 p 值。
**注意 B 批那一格：拿到第 3 轮的 4 次跑落在 2629.75–2635.22，极差 5.47 元，sd 2.49。**
也就是说，多跑一轮不但把均值拉低约 18 元，还把同格离散从 sd 14.6 压到 sd 2.5。

### 设计表

| # | 改哪里 | 做什么 | 预期效果（有依据才给数） | 速度代价 | 秒级/短跑验证 | 是否需用户批 |
|---|---|---|---|---|---|---|
| a | `runner.py` 第 891–893 行的 `if rounds > 1 and not improved: break` | 把"第一轮没改善就停"换成固定 K 轮（建议 K=4），或"连续 2 轮没改善才停" | 均值：两批同车队实测多一轮值 **18.5 / 19.2 元**。sd：去掉轮数主效应后残差 sd 为 B 批 **12.92→10.46**、A 批 17.09→15.39（A 批只有 1 次 3 轮，这个数不可靠）。**"压到多少"数据不足以判定**；唯一实测锚点是 B 批 2CV/3EV 拿到 3 轮的那 4 次 sd=2.49 | 每多一轮内核 20000 圈，C 批实测 68–82 秒；两批里 3 轮跑总墙钟均值比 2 轮跑高 76%（680 vs 387 秒，B 批）。K=4 约 1.5–2 倍墙钟 | 每臂 3 次短跑，K 强制为 4，与已有 C 批 3 次跑比 sd 与均值 | **要批。这是加预算 + 改停机规则，不是免费的稳定化** |
| b | 已在 09-05 改过的轮间预留分位数（`RELOAD_GAP_QUANTILE`） | 复核而非新改 | 已测：旧取值下 <2000 秒时 3/3 轮改善、≥2380 秒时 3/17，Fisher p=0.0175；C 批修后预留降到 1250–2001 秒，轮数由 2 变成 2–4 | 零 | C 批已有 6 跑；再补几跑核 `kernel_seed_infeasible_by_round`（现为 0–15/24–45）是否稳定压低 | 已改过，只需在验收里核；不另开新决定 |
| c | 轮间保留精英种群 / 提高 `num_elite` / 用上一轮最优的 k 个邻居作种子 | 每轮不再新建空种群（第 745 行），保留上一轮子种群 | **数据不足以判定**。现有产物里没有轮内精确目标轨迹，也没有种群多样性指标，无法估 sd 降幅。且 `num_elite=4` 与上游和 HGS-CVRP 论文一致，改它没有文献依据 | 未知 | 需先落盘轮内精确评价轨迹才能评估 | 要批（改搜索行为，且无依据） |

**先后顺序（要害，别跳）**：**先 b 后 a，不要直接批 a 的预算。**
理由：a 的 18.5/19.2 元证据全部采自 A/B 两批，而那两批的第 2 轮失败**本身就是**
§5 那个取最大值的预留 bug 造成的（Fisher p=0.0175），该 bug 09-05 已改成取分位数。
所以那 18.5/19.2 元里有多少是 bug 造出来的、修完还剩多少，**现在不知道**。
正确顺序是：
1. 先核 b 是否真的修住了（C 批 6 跑已有初步证据：预留降到 1250–2001 秒，轮数变成 2–4）；
2. 在**修后代码**上每臂再跑 ≥3 次，重新估轮效应；
3. 拿修后的数再决定 K 定多少、要不要加预算。
修后目前唯一的正面证据是 C 批 MTC-HGS run_02：4 轮，第 2–3 轮合计还赚 22.34 元
（2614.18→2591.83），说明修完预算仍然偏短——但 **n=1**，撑不起批预算。

**明确标注**：a、c 都改变搜索行为，b 已经改过。
a 之所以有可能站得住，不是"文献这么做"，而是内部标定证据：轮 2→3 仍能赚 16–60 元（修前）、
22.34 元（修后 1 次），说明当前预算**实测低于收敛点**——这正是"预算必须来自本算法本算例本机器"的做法。
但在第 2 步做完之前，a 的效应量不可信。

## 7. 对"理论效应不能被算法性能淹没"的直接回答

要检出的择时效应是 7–10 元。当前单跑离散：
- A 批 sd 17.09、极差 45.72
- B 批 sd 12.92、极差 33.10

其中最大的单一可控项是"这次跑有没有拿到确认轮"，实测值 **18.5–19.2 元**，
**本身就大于要检出的效应**，且它是一次伯努利抽签（A 批 1/10 中，B 批 5/10 中）。
只要停机规则还是"第一轮没改善就收摊"，任何 7–10 元的机制效应都会被这个抽签盖住。

B 批那一格给了个参考量级：同车队、同拿到 3 轮的 4 次跑，极差 5.47 元、sd 2.49——
落到这个量级，7–10 元的效应才有可能被看出来。
**但这个 2.49 不能当承诺，也不能当强制 K 轮的预期值**：这 4 次是"恰好拿到第 3 轮"的跑，
属事后选择——能拿到第 3 轮本身就与落进好的解区间相关，所以 2.49 是**下偏估计**；
n=4 只是次要问题。强制 K 轮实际能压到多少，**数据不足以判定**，必须按 §6 的三步顺序实测。
