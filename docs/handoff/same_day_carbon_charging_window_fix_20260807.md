# 同日出车前充电窗口修复记录（2026-08-07）

## 结论

`FACT`：统一算例预查发现，同日出车前充电虽然标记为第 0 天，旧碳感知重排仍允许它在第 0 天的任意时刻开始，因而可能把充电排到车辆出发之后。成渝、京津冀、珠三角三个 50 客户真实算例都复现了这个问题。病因在 `solver/src/setp_solver/search/multitrip_schedule.py` 的首趟重排窗口，不是地区碳强度或算例本身。

`CORRECTION`：首趟充电现在必须同时满足代表日边界、证书中的实际出发时刻和共享检查器使用的自然出发时刻；三者取最早结束边界。第 -1 天的上一晚充电仍保留原来的完整一天窗口。实现见 `solver/src/setp_solver/search/multitrip_schedule.py:2313-2369`。

`FACT`：修复后，三个地区 50 客户算例的碳感知充电方案均为 0 条完整检查违规。单元反例见 `solver/tests/test_multitrip_schedule.py:400-447`；京津冀真实反例明确覆盖“证书出发时刻与检查器出发时刻不同”的情况，见 `baselines/algorithm_prototypes/duty_hgs_20260807/tests/test_dynamic_adapter.py:324-369`。相关测试共 83 项通过，Ruff 与 `git diff --check` 通过。

`ADVISORY`：Claude Opus 5 逐行复核后确认根因、日期换算和修复方向正确。它指出当前取较早时刻会略微压缩物理上可能存在的低碳窗口，但在受保护检查器不改的前提下，这是同时满足证书和检查器的唯一安全口径；补入真实反例后同意封存并继续统一算例探索。

`BOUNDARY`：同一文件的通用 `certified_depot_charge_window` 使用另一套完整路线出发时刻，Opus 将其登记为后续可能存在的口径张力。本轮没有扩线修改这个入口，因为当前统一算例扫描调用的已修函数已经通过三地真实复验；若后续实际调用另一个入口并出现冲突，再凭实测证据处理。
