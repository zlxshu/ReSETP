# 第二病灶：内核为什么不肯把任务从油车挪到电车

只读诊断。仓库根 `/Volumes/移动硬盘（512G）/ReSETP`，分支 `codex/reporting-pipeline`。
**没有改仓库任何文件，没有跑任何 GA / 求解器搜索。** 只读源码与已落盘产物；六份只读脚本写在会话临时目录
（`q1_struct.py`、`kernel_eval.py`、`kernel_eval2.py`、`gap_sweep.py`、`slack.py`、`pen.py`），未进仓库。
所有数字用工作树 `kernel_proposals.py` 的建图函数 `_build_unique_asset_problem` 实算，
把已落盘解投影进**同一个** `data`（`engine.project()`），再读内核自己的
`distance_cost() / fixed_vehicle_cost() / time_warp() / is_feasible()`。

自检：内核代理总额与精确总额的差在 `cost_plus_carbon` 臂上是一个几乎恒定的正偏移
（33 份解里 29 份落在 +4.15 ~ +5.51 元），说明我建的图和求解器建的是同一张图。

## 零、三句话结论

1. **问题不是钱。** 内核代理**同意** ③warm 更便宜，而且幅度和精确账几乎一样
   （run_02：代理 −51.98 元 / 精确 −47.12 元）。**"内核代理认为 ③warm 更贵"被证伪。**
2. **问题是时间，而且是内核自己造出来的时间。** `ev_reload_gap_seconds` 给每条
   「客户 → reload 副本」的电动车弧加一段固定的趟间充电预留。**第 1 轮就是 2031.7 秒**，
   而 101 次真实趟间充电的中位数只有 **1348 秒**（p75 = 1875 秒）。
   **在第 1 轮这个值下，全批第二好的那份解（精确 2577.40 元，3 辆电车、6 次趟间回场）就已经带 920 秒 time warp**，
   它在**任何一轮、任何一次跑**里都当不上内核的 `best`。
   第 2 轮起 `runner.py:710-712` 改用上一轮精确最优解的**最长**一次充电回填（实测 2380–2642 秒），
   在 2614.1 秒下 **33 份已知精确可行的解有 25 份在内核里不可行**（gap=0 或 1348 秒时是 0/33）——
   这解释的是**第 2 轮为什么白跑**（冷启动 9/10 次第 2 轮零改进），不是第 1 轮为什么停在 2588–2618。
3. **后果正是「电车不肯多带活」。** 30 份解里电动车任务最多只有 3 趟（4 趟只出现 1 次），
   而油车常见 4 趟、出现过 5 趟。第 4 趟要再买一份 34–44 分钟的预留。
   `GeneticAlgorithm.py:126/212-222` 的 `_best` 取自 `cost_evaluator.cost()`，
   不可行解代价为无穷 → **带 time warp 的电车密集解永远当不上内核的 `best`，也不进停机判据**。

**并且：派工单里「冷启动搜不到这些解」这句本身不准确**——见 §五「被证伪的前提」。

## 三、必答 4：电车在内核里的隐性成本 —— **病灶在这里**

### 3.1 先排除一个自然假设：每弧充电时长**本批没开**

`run_ideal_construction_one.sh:29` 的 `COMMON` 里有 `--no-ev-charge-time-proxy`
→ `run_problem_hgs_private_technical.py:1898-1900` 置 `ev_charge_time_proxy_enabled=False`
→ `kernel_proposals.py:1112-1131` 整块跳过 → `ev_charge_time_proxy` 字典里**没有 `seconds_per_kwh` 键**
→ `:1216-1218` 的每弧 `arc_energy × seconds_per_kwh` **不生效**。
落盘 `route_engine_wiring.ev_charge_time_proxy` 实测就是
`{"reload_gap_seconds":2031.6707, "reload_gap_reference_kwh":33.7619, "reload_copy_depots":2}`——
只有 reload 三个键。`ev_departure_gap_proxy` 也没开（无 `departure_gap_seconds` 键）。
**"每弧充电时间 + reload 预留 双重计费"这个假设：证伪。**

### 3.2 真正的隐性成本：`reload_gap_seconds`，而且逐轮加码

记账点：`kernel_proposals.py:1229-1243`，加在「客户 → reload 副本」的电车弧 `duration` 上，
即**每一次趟间回场**各加一份。取值链条：

- 第 1 轮：`reference_trip_energy_kwh(..., reference="max")` = 见证解**最大**一趟 33.76 kWh
  → 曲线换算 **2031.67 秒（33.9 分钟）**（`:1168-1195`，实测复现）。
- 第 2 轮起：`runner.py:710-712` 调 `max_inter_trip_reload_seconds(best[0])`
  （`kernel_proposals.py:800-820`），取上一轮精确最优解**所有趟间充电里最长的那一次**，
  经 `runner.py:574-577` 的 `ev_reload_gap_seconds` 回填。
  落盘 `accounting.reload_gap_seconds_by_round` 实测：
  冷启动 10 次的第 2 轮值 = **2380.0 / 2614.1 / 2641.9**（6 次是 2614.1）。

**过度预留有多大**（101 次真实趟间充电，冷+热 20 份解）：

| 分位 | min | p25 | **p50** | p75 | p90 | max |
|---|---:|---:|---:|---:|---:|---:|
| 秒 | 631 | 1109 | **1348** | 1875 | 2614 | 2642 |

- 第 1 轮预留 2031.7 秒 = 真实**中位数的 1.51 倍**，每次回场多占 **11.4 分钟**。
- 第 2 轮预留 2614.1 秒 = 真实**中位数的 1.94 倍**，每次回场多占 **21.1 分钟**。
- 一辆跑 3 趟的电车有 2 次回场 → 第 2 轮凭空多背 **42.2 分钟**。

### 3.3 这笔时间**不进目标、只进可行性**——所以是硬墙不是软价

`unit_duration_cost` 默认 0 且从未传（`kernel_proposals.py:1310-1332` 的 `add_vehicle_type`
只传 `unit_distance_cost=1`）。车辆时间窗 `tw_early=21600 / tw_late=79200`（16 小时），
实测最长路线才 37 131 秒，**班次总时长根本不紧**。
真正被顶穿的是**客户时间窗 + 班次 release_time**（AM 窗 28800–39600、PM 窗 46800–68400）。

**预留时长扫描（同一 33 份精确可行解，只改 `ev_reload_gap_seconds`，`gap_sweep.py`）：**

| 预留值 | 0 s | 1348 s(真实中位) | 2031.7 s(第1轮) | 2380 s | **2614.1 s(第2轮实际)** |
|---|---:|---:|---:|---:|---:|
| **内核判不可行的份数** | **0/33** | **0/33** | 4/33 | 16/33 | **25/33** |

逐份的**最大可承受预留**（二分，`slack.py`）：中位约 **2400 秒**，
最差的两份（`init2 run_04` = `warm run_04`，精确 **2577.40 元**，全批第二好）只有 **1561 秒**——
**它在第 1 轮的 2031.7 秒下就已经是内核不可行解**（warp 920 秒），第 2 轮下 warp 2429 秒。

### 3.4 不可行 = 当不上 `best`，也进不了停机判据

`GeneticAlgorithm.py:126` `self._best = min(initial_solutions, key=self._cost_evaluator.cost)`，
`:212-222` `is_new_best` 同样走 `cost_evaluator.cost()`，PyVRP 语义下**不可行解代价为无穷**。
`runner.py:594` 的停机是 `NoImprovement(patience)`，喂进去的也是 `cost(self._best)`。
所以：**任何带哪怕 8 秒 time warp 的解，都当不上 `kernel_result.best`，也不会重置停机计数器。**
（缓解项：`runner.py:614` 的 `natives = [kernel_result.best, *population]`，
而 `Population.__iter__`（`Population.py:35-43`）先吐可行子群再吐不可行子群，
所以不可行成员**仍会**被解码送精确评价。所以这是**偏置**，不是**封闭**——但偏置足够解释现象。）

**惩罚量级**（`PenaltyManager.init_from:193-232` 实算）：
`init_tw = avg_cost / avg_duration = 2130.6 单位/秒 = 0.0213 元/秒`。
初始惩罚下：344 秒 warp = **7.33 元**，`run_04` 那 2429 秒 warp = **51.75 元**——
已经是一辆油车固定成本（170 元）的 **30%**，而这还只是初值。
惩罚会自适应（`penalty_increase=1.34`、`penalty_decrease=0.32`、`target_feasible=0.43`、
`feas_tolerance=0.05`）：可行注册比例低于 38% 时上调、高于 48% 时下调。
**它最终稳在多少，落盘产物里没有记录，不能判定**——所以上面两个数按初值报，不外推。

## 四、必答 3：邻域能否到达

内核算子集实测（`kernel_proposals.py:249-274` + `search/__init__.py:24-37`）：
节点算子 `Exchange10 / Exchange20 / Exchange11 / Exchange21 / Exchange22 / SwapTails / RelocateWithDepot`，
路线算子 `SwapRoutes / SwapStar`，另加 `DepotSplit`。粒度邻域 `num_neighbours=40`，
但 `rebuilt_shift_neighbours_only=True`（`:433-456`）把邻居限制在**同班次**客户内。

**从 ② 到 ③warm 需要的原子动作量（§一实测）：** run_01 要移动 37/50 个客户的归属车，
run_02 要移动 **50/50**。**一步或两步到不了，这是明确的。** 但这不是「邻域缺失」：

1. **算子集本身够用。** `Exchange10`（relocate）+ `RelocateWithDepot`（带 reload 的整趟迁移）
   + `SwapRoutes` / `SwapStar` 足以在 20 个单车槽之间重排整盘；
   `integrated_private.py:200` 关掉的是 **Python 侧**的 `relocate/swap/open-trip` 枚举，
   内核侧同名能力**一直是开的**（这也是当时关它的理由，注释 `:196-201` 写得很清楚）。
2. **真正的障碍是「先变差、后收钱」的路线消减台阶。** run_02 内核账：
   Δdist **+18.02**、Δfixed **−70.00**。要收那 70 元，必须先一路承担 +18 元的里程恶化，
   而**每一步中间态都还要在 §3.3 的预留下保持可行**——两个方向的压力叠在同一批中间态上。
3. **类型互换通道（whole-duty type exchange）能到，但它在内核外面。**
   4/4 改进解的最后一步标签都是它（§一），说明这条通道确实在收尾；
   但它只换整条任务的车型，不能自己完成 §一那种整盘重排。
4. **`integrated_private.py:200` 关掉的三条里，`multi_trip` 是唯一相关的一条**——
   但内核的 `RelocateWithDepot` 已经覆盖同一动作族，重开它是重复造轮子，
   而且 2026-09-02 关它的理由是速度（596k 次精确评价换 16% 改进）。**不建议重开。**

**判定：邻域可达性——不能判定为「缺失」，判定为「被可行性罚封住」。**
证据是 §3.3 的扫描：把预留从 2614.1 降到 1348 秒，**25 份原本不可行的解一份不剩地变回可行**，
其中就包括 4 份 ③warm 解和全批第二好的 2577.40 元那份。

三次均值 1263.3，**在基线 1 个 sd 之内**。

**判定：不是「代理某项把电车弧算贵了」——证伪。**
改动前两臂共用一套代理（AM 0.95342 / PM 0.59621）。改动后：
MTC 臂 AM **0.95342 → 0.68203**、PM 不变 0.59621 → **电车弧整体变便宜**；
MT 臂 AM 0.95342 → 0.96510、PM 0.59621 → 1.18460 → 电车弧变贵。
两边方向都是设计想要的。
车队没动的原因是 **§三那堵时间墙没被碰过**：新代理改的是 `distance`（钱），
`unit_duration_cost=0` 决定了钱进目标、时间进可行性，**改价改不动可行性罚**。

**同时必须说的第二件事：第 2 轮起 `ev_unit_cost_override` 会把电车价再抬上去。**
`kernel_proposals.py:1057-1099`：标量 = 上一轮精确最优的 (cost_elec+E_ev×碳价)/kWh = 实测 **0.680**，
两窗未加权均值 = (0.68203+0.59621)/2 = **0.63912**，比例因子 = **1.0686**（<1.25，会被应用）
→ 第 2 轮 AM 变 0.7288、PM 变 0.6371。
**于是第 2 轮同时发生两件反电车的事：电车弧涨价 6.9%，趟间预留从 2031.7 涨到 2380–2642。**
冷启动 10 次里第 2 轮只有 1 次（run_04）找到更好解；热启动 10 次里有 5 次。**这是描述，不是检验。**

### 5.3 派工单里被证伪的前提

- **「冷启动全优化搜不到这些解」——证伪。** 冷启动 `MTC-HGS/run_04` 精确 **2579.91 元**，
  与热启动 `run_01` **逐位相同**；冷启动 10 次里 6 次拿到 `cost_fix=1150`（2 油 3 电），
  热启动 10 次里 7 次。**车队构成的分布几乎一样。**
- **「n_veh_ev 恒 3」——部分证伪。** 冷启动 `run_09` 是 4 电 2 油。
- **「少派 1–2 辆油车 = 把任务从油车挪到电车」——证伪。**
  电车服务的客户数：② 均值 **24.8**，冷启动 **27.5**，热启动 **27.9**，短跑 **27.3**。
  **冷启动和热启动的电动化程度没有差别（27.5 vs 27.9）。**
  热启动赚到的是**把剩下的油车活压进更少的油车**（路线数 6→5），不是电动化。
- **应当替换成的真实命题：** 内核不肯做的不是「把活给电车」，而是
  **「让同一批电车多跑一趟」**——电车任务 4 趟只出现 1/86 次，油车 4 趟出现 15/77 次。
  这正是 §3.2 那笔按「回场次数」收费的预留所惩罚的东西。

## 七、两个可施工设计

前置红线（写进派工信）：`third_party/setp_hgs_kernel/` 一个字节不许动；
`cost.py`、`check.py`、`search/**`、`evaluation.py` 不许动；
`run_problem_hgs_public_technical.py` 只 import 内核，公开 28 题与表 7 不受影响。
两个设计互不冲突，建议 **D1 与 D2 同批出、分别验收**（D2 是 D1 的观测仪）。

**明确不做的一件事：** 曾考虑给电车车型传非零 `unit_duration_cost`，把预留从「可行性硬墙」
改成「目标里的软价」。**放弃。** 理由是机制性的：`unit_duration_cost` 乘的是**整条路线的时长**，
不是只有 reload 那几条弧，一开就等于给电车的每一秒行驶时间都加价，方向反了；
而且它同时会改 `PenaltyManager.init_from`（`:200-211` 读这个字段），连回归基线一起动。
**要软化这笔预留，正确做法就是 D1：把预留本身缩到站得住的分位数。**

### D1：预留取真实分位数，不再取「最大」

**改哪里：** `solver/src/setp_solver/algorithms/problem_hgs/kernel_proposals.py`
两处同源取值——
(a) 第 1 轮：`_build_unique_asset_problem` 里 `reference_trip_energy_kwh(..., reference="max")`
（`:1176-1186`），以及 `run_problem_hgs_private_technical.py:1899-1916` 传进来的
`ev_reload_gap_reference_kwh`；
(b) 第 2 轮起：`max_inter_trip_reload_seconds`（`:800-820`），调用点 `runner.py:710-712`。

```
def inter_trip_reload_seconds(individual, *, quantile: float = 0.75) -> float | None:
    # 2026-09-05: the max over all sessions (median 1348 s, max 2642 s in the
    # P=0.2 midday-valley batch) put 25 of 33 exactly-feasible solutions into
    # the kernel's infeasible subpopulation, where GeneticAlgorithm._best can
    # never reach them (cost() is infinite for infeasible).  A high quantile
    # stays sufficient for the bulk and leaves the EV-dense structures feasible.
    seconds = sorted(
        float(s.occupancy_minutes) * 60.0
        for duty in individual.duties
        for s in duty.charging_sessions
        if int(s.trip_index) >= 2
    )
    if not seconds:
        return None
    index = ceil(quantile * len(seconds)) - 1
    return seconds[max(0, min(len(seconds) - 1, index))]

max_inter_trip_reload_seconds = partial(inter_trip_reload_seconds, quantile=1.0)
```

`reference_trip_energy_kwh` 那一侧同样加 `reference="p75"` 选项，
第 1 轮的 `ev_reload_gap_reference_kwh` 改由见证解趟能量的 p75 换算
（本批见证解 max = 33.76 kWh → 2031.6707 s；p75 待派工时复算并落盘）。
**分位数 0.75 的依据是本批 101 次实测（p50 = 1348 s、p75 = 1875 s、p90 = 2614 s），
这是本算例本机器的内部标定，不是文献值，派工信里必须写明。**

**秒级验证（三条全要，不跑搜索）：**
1. **生效**：把 33 份已落盘解投影进 `ev_reload_gap_seconds = 1875` 的图，
   要求 **0/33 不可行**（现值 2031.7 s 下 4/33、2614.1 s 下 25/33）。差一份即停工回报。
   对照口径就是本报告 §3.3 的扫描表。
2. **回归**：`quantile=1.0` 时 `inter_trip_reload_seconds` 与现行 `max_inter_trip_reload_seconds`
   在 20 份解上**逐位相同**；`reference="max"` 时第 1 轮 gap 仍是 **2031.6707043430688**。
3. **不越界**：新取值必须 ≥ 本批 p50（1348 s）。低于 p50 即回滚——
   `max_inter_trip_reload_seconds` 的注释（`:806-817`）记录过 2026-09-03 用**均值**预留时
   「某一轮整个自由车队没有一个可修的电车成员、最优解 8 辆油车」的翻车，那条教训要守住。

**验收中间量（这才是 D1 会动的东西）：**
- D2 落盘的 `kernel_seed_infeasible_by_round`，第 2 轮应从「多数种子不可行」降到 **0**；
- 电车任务趟数分布里 4 趟的占比，从现在的 **1/86** 上升（基线见 §3.6）。
**不要用「第 2 轮出现改进的比例」当判据**——热启动第 2 轮改进多，是因为它的起手解本来就好，
与 gap 取值混淆，不能当 D1 的效果证据。**总成本落点不承诺**，要跑才知道。

### D2：把内核可行性落盘（诊断加固，零风险）

**改哪里：** `solver/src/setp_solver/algorithms/problem_hgs/runner.py`

```
# 2026-09-05: the round-N reservation can put the previous round's own exact
# best into the kernel's infeasible subpopulation, where GeneticAlgorithm's
```

## 八、给用户的一句话（不含编号）

**电车不肯多带活，不是因为算法觉得电车贵——它算的钱和真实账几乎一模一样，也同意那些好解更便宜。
真正卡住的是：算法给电车每一次回场都预留一段固定的充电时间。第一轮就预留 34 分钟，
而真实充电的中位数只有 22 分钟；从第二轮起它改拿"上一次最长的那笔充电"来预留，涨到 40–44 分钟。
多预留出来的那段时间在算法的成本里一分钱不值，却会让方案被判成"来不及、不可行"，
而算法只肯把可行的方案当作最好方案。全批第二好的那份方案（成本 2577.40 元），
在第一轮的预留下就已经超时 15 分钟，所以它在任何一次跑里都当不上最优。
第二轮更狠，33 个已经验证可行的方案里有 25 个被算法自己判死，所以第二轮十次里九次白跑。
结果就是电车最多只敢排三趟，油车能排四五趟。
改法很简单：预留不要取"最长的那一笔"，取一个站得住的高分位（比如四分之三位，31 分钟），
这件事改完能不能真省钱，要跑了才知道，我不承诺数字。**
