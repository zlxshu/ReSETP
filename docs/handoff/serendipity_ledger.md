# 意外价值台账（Serendipity Ledger）

**用途**：实验设计、调整、准备过程中出现的"意外"，很多本身就是有价值的发现——可以包装成论文贡献点、故事线支点、方法论卖点或防坑教训。本文档长期维护，是这类意外的唯一集中登记处。

**维护规则**（Claude 与 Codex 都要遵守）：
1. 每当一次任务/审计/实验里出现"预期之外的事实"，无论好坏，先问一句：这能不能变成论文里的一句话、一张图、一个实验轴或一条方法论声明？能就登记。
2. 每条目五要素：日期、意外是什么、怎么发现的、价值定位（贡献点/故事/教训/待定）、当前状态与证据位置。
3. 状态只有四种：**已包装**（已进论文/设计文档）、**处理中**（已立项待执行）、**待拍板**（需用户决策）、**纯教训**（不进论文但防再犯）。
4. 新条目追加在对应分类末尾；状态变化就地更新，不删除历史条目。
5. 与 `HANDOFF.md` 变更日志的分工：变更日志记"发生了什么"，本台账只记"这件意外值多少"。

## 三、已关闭的重大拍板

### 11. M0 搜索无上限 + 协同臂锚死 + 旧路线无法补丁式变成真实14车多趟
- **日期**：2026-07-12（封存前最后审查发现；同日 D1/D2 获批后复核）
- **意外**：E3 地基 M0 的子算例搜索阶段车队无上限（子包漏传 num_cv/num_ev）；打包=纯改标签（无跨趟时间检查，HALT_M0_PACKING 是死代码）；协同臂从 M0 热启动且开新 EV 路由的门被趟数堵死；实证 5 种子里 4 个 M1 路由结构与 M0 逐位相同——旧收口"协同 4 胜 1 平"的 4 胜是化妆差异。用户批准正式多趟后，固定路线精确趟链覆盖又发现旧 M0 每 seed 需 50--55 EV（原始全局仅14），seed1的59条EV路线有52条跨两个或三个班次；所以不能靠给旧#T补一个排程器就救回正式E3。
- **价值**：这把一个“检查器盲区”升级成很有价值的研究设计洞察：真正的多趟不是事后分配车号，而是从客户分组时就要让趟能回场、能衔接。若重建成功，可成为方法严谨性的强故事；若不做，必须老实降级，不可包装。
- **状态**：**已包装并关闭拍板**。用户批准正式重建；E3 v11最终100次在22千瓦按需补电、原始14油+14电上全部合法。合作严格胜出6/10、平均省0.353%，但实体车数没有下降；论文故事因此是“真实客户换场与成本重组”，不是“合作省车”。证据：`docs/handoff/e3_m0_search_asymmetry_audit_20260712.md`、`docs/handoff/e3_formal_multitrip_feasibility_audit_20260712.md`、`baselines/e3_ablation/e3_v11_clean_20260713/final100/`。
