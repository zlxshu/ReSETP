### 原因（Why）——是调度定义缺陷，不是算例饥饿

现有路线池程序把 `route_pool_candidate_or_parent` 固定钉在**倒数第二次**评价、
`final_independent_certificate` 钉在**最后一次**。因此最终重组**恒处 `S−1`**。
对"最后一次严格改进恰由最终重组产生"的单元（160/240 档的 50c-01 种子 1–8、10，
**两臂皆是**）：

```
L = S − 1   ⟹   L/S = (S−1)/S  →  1   （恒 > 0.5）
```

**所以把 S 提到 320、480、4000 都永远过不了。这不是"再花点机时就能过"，
是一个结构上不可能通过的调度。** runner 识别出这点主动停了，没有闷头烧机时——
处理正确。

> ⚠️ 上一会话 Claude 曾误判为"算例比预想饿得多、需 320/480、机时爆炸"，
> **该推断错误**，已被 runner 报告推翻。不要重犯。

### 备选决策（用户二选一，执行代理不得自行决定）

**方案 A — 改调度**：批准一种能在最终重组**之后**仍提供确定性完整候选评价的调度，

- 代价：动到路线池程序的**执行顺序**，属实质方法变更；**须重跑全部五档**

## 5. 监控与看门狗

### 5.1 ⚠️ 当前无任何监控在运行

上一会话的两个哨兵已随会话终止。**接手方必须自建监控**，不要假设有人在看。

### 5.2 已验证的架构

一任务一独立哨兵，挂在**需要被通知的那个会话的进程树**内，只读轮询，不进仓库、
不干预实验。

终止条件应至少覆盖：该任务**当前阶段**的 `completion_files` + 最终产物 +
monitor 离开 `RUNNING`/`paused=true` + runner 死亡超宽限期。

### 5.3 四个已证实的缺陷（全部实测踩过）

1. **共用看门狗天然叫不醒**：等多个产物全部出现才退出，中间只写日志；
   而后台任务**只在进程退出时通知**
2. **跨会话通知失效**：Codex 会话内启动的哨兵，其退出只通知 Codex；反之亦然。
   `ps` 里看到哨兵在跑 ≠ 你会被叫醒
3. **`pgrep -f "$PATTERN"` 匹配哨兵自身**：PATTERN 就在哨兵自己的 argv 里，
   不剔除则存活检查恒为真、死亡检测**永不触发**。须用
   `ps -o command= -p $pid | grep -q <哨兵名> && continue` 过滤
4. **重启循环可绕过存活检查**（07-29 实测）：E3/E6 每次重启都落在死亡宽限期内、
   把计时清零，于是"起来就死、零产出"的空转在"有无进程"维度上**与健康运行完全
   不可区分**，哨兵始终未响，直到重启停止满宽限期才报 `RUNNER_DEAD`，**延迟 45 分钟**。
   **必须补一条：checkpoint/产物计数在 N 分钟内无增长即告警。**

另：只盯最终产物会把**阶段性成功误报为死亡**——E3/E6 当前 monitor 的
`completion_files` 是 `pre_registration.json`，`result_files` 中**没有** `report.md`。

对应记忆节点：`watchdog-must-be-per-task-and-in-session`（用户全局 memory）。
