## 0. 结论一句话

`FACT` 路线搜索 100% 发生在 C++ 内核的代理问题上，而代理问题**看不见电车趟间充电时间**，
也**从不自适应罚系数**；Python 层只负责事后判死刑或收尸。因此 91% 的子代白生，每圈还要付
一次整解重评价（17–25 ms）。速度慢、改善稀、质量卡在 2520 附近，根子在这三处，
不在停止规则。

## 1. 架构事实（FACT，均有文件行号）

1. 每圈流程（`integrated_private.breed` → `IntegratedGeneticAlgorithm._improve_offspring`）：
   选两个父代（Python 种群）→ 投影到内核解 → SREX 交叉（C++）→ 内核局部搜索（C++）→
   解码回 Duty → 充电修复（Python）→ 完整评价（Python）→ 教育（Python，现只剩整车换型与
   跨场整趟交换）→ 入群；不可行且 80% 概率走修复（路线引擎＝再跑一次内核局部搜索）。
2. 代理问题（`kernel_proposals._build_unique_asset_problem`）：每辆实体车一个 vehicle type，
   多趟＝reload depot，弧成本＝非能耗每公里成本＋半载能耗×单价（电价＋碳），固定成本＝日固定费，
   **弧时长＝纯行驶时间**（第 793–800 行 `duration=max(0, round(duration_s))`），
   无电池、无充电时间。客户 release_time＝班次窗起点。
3. 内核罚系数（`kernel_proposals.py:180-185`）建一次后**从未 `register`**：全仓只有未接线的
   `patched_genetic_algorithm.py` 调用它；上游 HGS 每 50 个解按 43% 可行目标自适应。
4. 完整评价（`evaluation._evaluate_full` / `_evaluate_prepared`）：`prepare_multitrip_solution`
   全解证书＋`calculate_depot_profits`＋`check_solution`（受保护）＋成本。
   "增量评价"`evaluate_after_change` 只省了各车成本分项，证书、利润、检查器仍对**整解**重跑。
5. 种群 `ExternalPopulation.add` 每次对全体成员重算 broken-pairs（Python 重建字符串字典）。
6. 第四刀后 `repair()` 对 `REJECTED_CHARGING` 成员直接 return（只做父代，不修不教）。

## 3. 三目标各自的病灶归因（INFERENCE，依据上表）

- **消融明显**：M→MT 成本 −7%、排放 −45%；MT→MTC 成本 −1%、排放 −22%。第二步的成本效应是
  电价/碳价数据决定的，源码改不出来；排放效应明显。三臂重跑后效应应保持此量级。
- **速度**：(a) 每圈 30–85 ms 的地板＝整解重评价＋充电修复；(b) 九成子代白生 → 找到 7 次改善
  要三万圈；(c) 母版 1.3–2 分钟 vs 我们 19–61 分钟。停止规则的空等尾巴只占三到五成，
  且改善间隔最长 1.8 万圈，阈值下调会直接砍质量。
- **质量**：搜索在代理上跑，代理对电车的时间成本系统性乐观 → 内核把力气花在注定死的方向；
  第四刀把死子代放进种群但内核修不了它们 → 更差。

## 4. 改造设计（DECISION，代理方案，待用户选）

全部沿用原版 HGS 机制或纯删无用功，不新造算法。

### A. 让内核看见电车充电时间（同时救速度与质量）
`kernel_proposals._build_unique_asset_problem`：电车 profile 的弧时长
= 行驶时间 + 该弧半载电耗 ÷ 有效充电功率（59.8 kW，取自曲线实测）。
- 物理依据：初始电量 0、按需充电，每度电都要在车场用 60 kW 买回来；这是 EVRP 文献里
  "充电时间与电量成正比"的标准近似（Schneider et al. 2014 的线性充电时间），放到弧上分摊。
- 边界性质：趟 k 的内核回场时刻 = 真实回场 + E_k/P，即内核为下一趟预留了"上一趟的电量"的
  充电时间（真实需要的是下一趟的电量，相邻趟量级相近）；趟内客户到达时刻偏悲观
  （多算了尚未分摊的那部分），但内核 time warp 是软罚不是硬拒，只是略不偏好。
- 备选 A2：不按弧分摊，而是给电车"回场弧"加一个常数周转时间（＝算例平均趟长×电耗÷功率，
  本算例约 23 分钟）。趟内不悲观，但趟间用常数代替实际电量。
- 反面（辨证）：A 使首趟也被多算 E_1/P（首趟实际免费充电）；A2 对长短趟一视同仁。
  两者都由精确修复兜底，只影响内核偏好。推荐 A（全部由算例数据推出，无人造常数）。
- 电车单价代理（可选 F）：现全臂统一用"班次窗内最低碳半小时"价。asap 臂（MT）实际在回场后
  立刻充（白天均价 0.9994 元/kWh，碳价 0.075 时）而非最低价 0.848。可按臂取价：asap 用工作时段
  均价，cost_plus_carbon 用窗内最低价。**这会改变 MT 臂的搜索指引**，须用户点头；默认不动。

### B. 恢复内核罚系数自适应（原版行为，零风险）
`breed` 中局部搜索后 `engine.penalty_manager.register(native_child)`，booster 修复后再 register，
与上游 `GeneticAlgorithm._improve_offspring` 逐行对应。

### C. 充电不可行成员走原版修复路径（让第四刀有意义）
`repair()` 对 `REJECTED_CHARGING` 成员：投影 → 内核 booster 局部搜索（A 之后内核能看见时间病）
→ 解码 → 充电修复 → 完整评价；可行则入群。不进 Python 教育（无切片）。
备选 C2：整体撤回第四刀入群，回到三刀版。

### D. 每圈地板（纯提速，判决不变）
- D1 真增量评价：按车缓存"切片＝证书行＋成本分项＋该车单独跑 `check_solution` 的违规"，
  组合时只做跨车项（客户覆盖、车队数、车场容量、站点容量、time warp 汇总）。
  `check_solution` 仍是最终答案与任何完整评价的裁判；增量组合器须逐项复现其违规集与成本
  （新增测试：随机候选上二者逐位相同）。预期 17–25 ms → 3–5 ms/次。
- D2 预筛加充电时间下界：电车趟 k+1 的强制出发 ≥ 裸回场_k + E_{k+1}/P_max。
  这是必要条件（充电只会更慢），故拒绝即真死，把 3.5 万次 NO_FEASIBLE_WINDOW 修复在进门前拦掉。
- D3 种群 broken-pairs 签名按个体指纹缓存。
- D4 `breed` 的子代评价改走增量评价器（以父代播种）。

## 7. 2026-09-03 追加：有效时间／无效时间的账，与"内核搜路线、精确账只算候选"的分工

**用户令（09-02 深夜／09-03 凌晨）**：分清有效时间（找到最后一次改善之前）与无效时间（之后的两万圈空等）；
在保证质量的前提下用一切手段提速；眼光不局限，要辩证。提速改动须有开源代码或文献依据，只删改不扩容，不加门与防御代码。

**FACT（第一批 27 跑）**：每圈 31 ms；每跑平均 61% 时间是无效尾巴；即便每圈压到 3 ms，两万圈尾巴仍要 1 分钟，
而 Python 精确层给一个子代做充电修复＋评价的地板约 5–10 ms。结论：只要"每个子代都过精确账"，单跑就是分钟级起步。
**FACT（第二批，撤入群＋粒度教育）**：单跑 M 4–12 min、MT 10–18 min、MTC 14–19 min，约快一倍，质量持平略降。

**分工设计（已施工，`runner.run_kernel_native_problem_hgs`，脚本 `--search-mode kernel_native`）**：
1. 内核（PyVRP 0.12.2 `GeneticAlgorithm`，C++ 局部搜索）在路线代理上自己跑到"连续两万圈无改善"（`stop.NoImprovement`），
   不做停滞重启（`num_iters_no_improvement` 置极大）。初始种群＝参考解与上一轮候选的投影＋随机构造。
2. 精确阶段：内核终种群里每个可行成员（去重）→ 解码到实体车 → 锁检查 → 充电修复（含预筛）→ 完整评价 → 整车换型/跨场整趟教育。
3. 回填：把精确最优实际付的电价＋碳价（元/kWh）回填给代理的电车单价，重建内核问题，下一轮以本轮候选热启动；
   某一轮精确最优不再改善即停。每个报出的数都是完整评价。
**依据**：Montoya 等 2017（ILS 搜路线＋启发式集中解充电子问题）、Froger 等 2019（固定路线充电子问题只对候选路线求解）；
HGS 循环与停止规则直接取自内核开源实现。三个消融臂仍由内核锁维度（换型）与精确阶段充电策略（择时）区分。
**辨证**：代理看不见的东西（充电择时的真实收益）通过"回填单价 + 下一轮"进入搜索，而不是每圈过精确账；
风险是回填只有一个标量（全场统一电价），若不同车场/班次差异大则指引仍粗——先量再说。
**改动性质**：路线引擎加一个"电车单价覆盖"参数（改）；runner 加一段编排（约 200 行，调用现成零件）；脚本加一个模式开关。
未删旧循环（作对照与回退）。
