## 先回答用户那句判断

> "同类期刊的公开算例一题几十秒，我们私有 50 客户算例单次 5–12 分钟，这是代码和设计出了问题。"

**前半句不成立，后半句部分成立。**

- 公开那 28 题**根本不是"几十秒"级别的题**。它们是 Vidal 等 2013 的 MDVRPTW `pr11a–pr24b`，
  **360–960 个客户**。**原作者自己在原论文里报的平均耗时是 88.98 分钟**，最长 298.51 分钟，
  而且他为了省时间还把停止阈值降到了 2,500。不管怎么换算机器，"几十秒"都差着两个数量级。
- 公开这条路上**一行本项目代码都没有**：`run_problem_hgs_public_technical.py:103-105` 直接调
  未改动的 PyVRP 0.12.2 `solve()`。所以公开侧的耗时和"我们的代码"无关。
- 私有 50 客户单跑 5–12 分钟属实（38 个正式跑中位 464.9 s ＝ 7.75 分钟）。
  但它慢的原因不是"50 个客户的题应该几秒钟"——喂给内核的那道题在内核眼里不是 50 客户的题。

## 1. 公开算例我们到底多快

### 1.1 实测

产物：`solver/reports/public28_formal_20260830/<INST>/run_{01..10}/raw_runs.csv`（28 题 × 10 跑 ＝ 280 条）。

- 280 条单跑：**中位 2953.9 s（49.2 分钟）**，均值 4359.6 s，最小 204.1 s，最大 30872.6 s（8.6 小时）。
- 28 题的"每题中位"：最小 537.5 s（PR11B），最大 9175.0 s（PR24B），中位 2965.5 s。
- 停止规则：连续 20,000 次无改善，无时限、无重启（`run_problem_hgs_public_technical.py:19,105`）。

### 1.2 这 28 题是什么

`run_problem_hgs_public_technical.py:75-80` →
`baselines/algorithm_foundation/mdvrptw_v13_comparison_20260719/sources/normalised_instances/<INST>.vrp`，

Vidal 2013（CIRRELT-2011-61）**表 8，MDVRPTW 列 T(min)**，Xeon 2.93 GHz，5 次跑平均。
表 8 脚注写明：**为省计算时间，停止准则降到 ItNI ＝ 2,500 次无改善，并加 5 小时上限**。

**这一句就足以否掉"几十秒"**，不需要任何跨机换算：造出这批题、写出这套算法的作者本人，

## 2. 私有算例 5–12 分钟花在哪

38 个正式跑，算例 `cn-jjj-50c-01-DEPOTSEARCH-d996f755bd`，50 客户、2 车场。

- `run_wall_seconds`：**中位 464.9 s（7.75 分钟）**，范围 284.6–778.4 s。与用户说的 5–12 分钟一致。
- 内核圈数 `crossover_calls`：中位 76,451。

### 2.1 实测拆分

把 38 跑 `convergence.csv` 的 `cycle` / `wall_seconds` 逐行做差，得 **92 个轮次**，最小二乘：

```
round_wall = 5.823 ms × iterations + 4.92 s        R² = 0.923，92 个轮次
   斜率 95% CI [5.477, 6.169] ms
   截距 95% CI [-7.4, 17.2] s   ← 没被数据定住
```

| 大类 | 占整跑 | 依据 |
|---|---:|---|
| 内核 GA（PyVRP C++） | **≈ 91–95%** | 5.823 ms × 圈数 |
| Python 精确阶段（解码＋充电修复＋完整评价＋教育） | **≈ 5–9%** | 见下 |
| 初始化 | 0.7% | `initialization_wall_seconds` 均值 3.20 s |
| 落盘 / 日志 IO | 可忽略 | `convergence.csv` 每跑只有 2–4 行 |

**为什么给区间而不给点值**：按轮拟合的截距 95% 置信区间跨过 0（[-7.4, 17.2] s），
**这个方法定不住 Python 侧的绝对量**。所以取两端：

- **下界 5.4%** ＝ metadata `accounting.wall_seconds` 均值 25.4 s / 467.7 s。
  这是**下界**，因为它只在 `contracts.py:193`（`record_outcome` 里
  `self.wall_seconds += outcome.wall_seconds`）累加，**只计机制动作候选**，
  **不覆盖** `runner.py:625-690` 每轮那段精确阶段。
- **上界 ≈ 8.9%** ＝ 截距 CI 上端 17.2 s × 2.42 轮 / 467.7 s。

**口径更正**：`docs/handoff/route_effect_design_review_20260904.md:243` 的"Python 侧占 5–8%"
**结论方向正确，但它引的计数器（`wall_seconds`）并不度量它想度量的东西**。
以后引这个结论，要引区间和它的两个来源，不要引 `wall_seconds` 单个数。

## 3. 为什么私有比公开"每客户"慢

### 3(a) restarts 2–4 ＝ 20,000 无改善准则被执行了 2–4 遍 —— **成立**

私有走 `--search-mode kernel_native`（README §一），代码在
`solver/src/setp_solver/algorithms/problem_hgs/runner.py:572-720`：

```
while True:
    rounds += 1                                                        # :573
    ... 重建种群 ...
    kernel_result = algorithm.run(NoImprovement(patience), ...)        # :615
    ... 精确阶段：解码 + 充电修复 + 完整评价 + 教育 ...
    stop(state())                                                      # :695  ← 每轮只调一次
    if confirming_round:  if rounds > 1 and not improved: break        # :698-700
    elif rounds == 2: break                                            # :701
accounting.restarts = rounds                                           # :723
```

`patience = int(parameters.stagnation_patience)`（`runner.py:529`）＝ 20,000
（`run_problem_hgs_private_technical.py:107`）。README §一确认交付批带 `--confirming-round`。

**每一轮都从零开始重数 20,000 次无改善：**

- 38 跑共 **92 轮** → 92 × 20,000 ＝ **1,840,000 圈是确认尾巴**，占全部 2,995,542 圈的 **61.4%**。
- 折成墙钟：5.823 ms × 1,840,000 ＝ **10,714 s ＝ 全批墙钟的 59.9%**。
- 其中 **32 轮整轮恰好只跑 20,000 圈**（那一轮一次改善都没有），平均每轮 119.8 s，
  合计 3,834 s ＝ 全批的 **21.4%**。

这与 2026-09-02 诊断（`solver_redesign_three_goals_20260902.md:133`「每跑平均 61% 时间是无效尾巴」）
**数值吻合** —— 本轮是在新的 kernel_native 架构上独立复现了同一结论。

**但多出来的轮不是白跑。** 逐跑核 `convergence.csv` 的最好成本：
**38 个正式跑里 14 跑（36.8%）的最优解出现在第 2 轮或更后**。
所以"砍掉多轮 ＝ 白赚 2 倍"**不成立**，砍轮次属于改变搜索行为，须用户批。

**三个必须记进论文的口径问题：**

1. metadata 写 `"stop_semantics": "20,000 consecutive non-improving iterations; no restart"`，
   `pending_decisions.md` P135 也写"不重启"。但外层实跑 2–4 轮，每轮各一次 20,000。
   那句话描述的是**每轮内核**，不是**整跑**。
2. `runner.py:558` 的 `state()` 把 `iterations_without_improvement` 硬编码成 0，
   而 `run_problem_hgs_private_technical.py:1918` 的停止判据是 `>= NO_IMPROVEMENT_LIMIT`
   —— **这条路径上外层停止回调永远不可能返回 True**，整跑实际由轮数 `break` 结束。
3. `accounting.restarts` 写的是 `rounds`（`runner.py:723`），**不是 GA 重启**。谁读 metadata 都会读错。

### 3(b) 每圈耗时被"内核规模"撑大 —— **成立**

`git show HEAD:solver/src/setp_solver/algorithms/problem_hgs/kernel_proposals.py`，
函数 `_build_unique_asset_problem`（:619 起）：

| 项 | 值 | 出处 |
|---|---|---|
| 地点数 | 2 车场 + 50 客户 ＝ 52 | :716, :748 |
| **车辆类型数** | **20**（每个 duty 一个类型，`num_available=1`） | :874-875 |
| **profile 数（＝独立矩阵份数）** | **4**（每个 (车型, 车场) 一份） | :768 |
| **每车最大 reload 次数** | **49**（`max(0, len(customers)-1)`） | :842, :891 |
| 载重维数 | 基础 + 体积 + 锁定车场数 + 锁定车型数 | :731-746, :860-872 |

车队实测 20 辆（`fleet_caps_by_depot` 6+14；`best_solution.json` 20 个 duty，cv 10 / ev 10，两个车场）。

内核看到的不是"50 个客户 1 种车"，而是
**52 个点 × 20 种单车类型 × 4 份矩阵 × 每车 50 段行程槽位 × 多维载重**。
PyVRP 的局部搜索与路线拼接开销随车辆类型数与 reload 槽位数增长 —— 这是"50 客户却要 5.8 ms/圈"的来源。

**`max_reloads = 49` 明显过头**：38 个正式跑被接受的最终解里，单车最多趟数
3 趟 / 4 趟 / 5 趟，**从没超过 5**（48 跑口径同样：3 趟 29 跑、4 趟 17 跑、5 趟 2 跑）。
内核却被允许排到 50 趟。注意 `mechanism_closure.final_max_trips_per_duty` 只是**事后观测值**
（`run_problem_hgs_private_technical.py:2264-2271`），**不是约束**
—— 所以调小 `max_reloads` 会真的改变搜索可达空间，属于要用户批的改动。

**关于"相当于多大的题"**：去掉并行拥挤后每圈约 3.4 ms（见 3(e)），
对比 1.5 节我们自己 n＝360 的 10.8–12.7 ms，比值约 0.3。
但**公开集最小就是 360 客户，没有更小的题可以插值**，
所以"等价于多少客户的普通 MDVRPTW"**数据不足以判定**，只能说：
一道 50 客户的题，单圈成本达到我们自己 360 客户题的三分之一，这个比例是不正常的。

### 3(c) 精确评价单次多少 —— 从产物定界，未跑微基准

- 每跑完整评价 `full_evaluations` 63–221 次（均值 142），平均 2.42 轮 → 每轮约 59 次。
- Python 精确阶段整跑 25–42 s（见 2.1 的区间两端）→ **每次"解码＋充电修复＋完整评价＋教育"约 0.18–0.29 s**。
- 109–167 次完整评价合计约 **20–48 s**，即整跑的 5–9%。

不需要新跑微基准就能定界，所以**本轮没有运行任何求解器**。
这和 `solver_redesign_three_goals_20260902.md:17` 的"一次整解重评价 17–25 ms"不冲突：
那 17–25 ms 只是 `evaluate` 本身，0.18–0.29 s 是整条精确阶段
（含 `decode_replacements`、`repair_changed_duties_outcome`、`refine` 教育）。

### 3(d) 圈数里多少"有效"

`convergence.csv` 只在**每轮末**写一行（`stop()` 每轮只调一次，`runner.py:695`），
所以**轮内改善曲线看不到**。能确定的是：

- 由 `NoImprovement(20000)` 的定义，**每一轮的最后 20,000 圈必然全部无改善**。
- 38 跑 92 轮 → **61.4% 的圈、59.9% 的墙钟是确认尾巴**。
- 典型形态（`P=0.2/MTC-HGS/run_01`）：第 1 轮末 34,436 圈 / 196.9 s；
  第 2 轮末 54,436 圈 / 306.5 s，最好成本一位不变 —— 第 2 轮 20,000 圈、109.5 s（整跑 35.7%）零收益。

### 3(e) 并行拥挤：**n＝38 的回归，不是单点观察**

README §二 与 `launcher.log`：`run_ideal_construction_batch.sh 6`，`nice -n 5`。
机器 **Apple M1，8 核 ＝ 4 性能核 + 4 能效核**（`hw.perflevel0/1.logicalcpu` ＝ 4/4）。
6 个单线程求解进程压 4 个性能核，还被 `nice -n 5` 降权推向能效核。

从 `probe.log` + `launcher.log` + `launcher_confirm.log` 取出全部 38 个跑的起止时刻，
按 5 秒采样算出每个跑窗口内**实际平均并发数**，再回归：

```
ms_per_iter = 0.560 × concurrency + 2.800
   n = 38，R² = 0.675，Pearson r = 0.822
   预测 c=1 → 3.36 ms/圈 ；c=6 → 6.16 ms/圈 ；比值 1.83x
```

并发数不是只有两档：实测覆盖 1.00 / 4.16 / 4.39 / 4.62 / 4.86 / 5.18 / 5.43 / 5.45 /
5.66 / 5.91 / 5.99 / 6.00，对应 ms/圈 3.88 / 4.79 / 4.73 / 5.13 / 5.05 / 5.50 / 5.77 /
5.72 / 6.06 / 6.08 / 6.22 / 6.0–6.7 —— **单调上升**，不是靠那一个独占跑撑起来的。

独占跑 `P=0.2/MT-HGS/run_01`（`probe.log` 19:17:48–19:22:49）的配置已逐字段核对：
**与批内 `run_02` 的 metadata 除逐跑结果字段外完全一致**（同 patience 20,000、同机制开关、
同车队参数类、同碳价、同日历、同算例），不是配置不同造成的快。

**注意 2.1 那个 5.823 ms/圈的斜率本身就是在 6 路并行条件下拟合出来的**，
所以拥挤不是"另外一块时间"，而是**同一块墙钟的另一个视角**：
去掉拥挤后，同样的圈数只要约 3.4 ms/圈。

**判定：**

1. **是的，20,000 比同行保守将近一个数量级。** 造这批公开题的作者本人用 2,500，
   在更小的 MDVRPTW 上用 5,000。我们用 20,000 —— 是 Vidal 同题设定的 **8 倍**。
2. **但公开侧的量级本身没问题**：我们和原作者在同一档（几十分钟到两小时），
   题就是这么大，没人能几十秒解完。
3. **真正不合格的是私有侧对同刊母版的比值**：陈婉茹 2023 在 **71 客户 6 车场**上每跑
   1.33–2.07 分钟；我们在**更小的 50 客户 2 车场**上要 7.75 分钟中位 —— **慢 3.7–5.8 倍**。
   "速度合格（对比同类算法耗时）"这个目标指的就是这个比值。
   （同样跨机器，同样不能拿来声称谁的算法更优；但**同一台机器上我们自己能改的部分**见第 5 节。）

## 一句话回答

**不是代码写坏了。** 公开侧完全没问题（那批题原作者自己就要平均 88.98 分钟，
而且我们那条路上一行自己的代码都没有）；私有侧 7.75 分钟里的时间去向，
三个视角看同一块墙钟：

- **按用途分**：约 **60% 的墙钟**是"每轮 20,000 次无改善"被执行 2–4 遍留下的确认尾巴；
- **按机器分**：同一批圈数，独占跑只要 3.4 ms/圈，6 路并行要 6.2 ms/圈 —— **1.83 倍**是机器超订；
- **按题目分**：剩下的是内核被喂了一道"52 个点 × 20 种单车类型 × 4 份矩阵 × 每车 50 段行程槽"的题。

（这三个是**同一块时间的三个切面，不能相加**。）

**改哪里能从 7.75 分钟到多少：**

- 只做第 1 条（交付批降并行度，不改代码、零质量风险）：**7.75 → 约 4.2 分钟**。
- 再做第 4、5 条（须用户批；第 4 条还要和正在改 `kernel_proposals.py` 的代理协调）：
  第 5 条把 patience 减半可再砍 30.7% 的圈数，第 4 条省多少**数据不足以判定**。
  **两条都必须先做第 2 条**（把轮内改善轨迹记下来），否则无法判断会不会砍掉质量。
- 目标参照系：同刊母版陈婉茹 2023 在 71 客户 6 车场上是 1.33–2.07 分钟。
