## 三、现在的四个实际问题

### 3.1 算法方向已定，但实现身份没有闭合

`FACT`：HGS 内核与“问题特化组件”已经由用户确定；当前论文基础稿仍写 `MV-HGS-SP`，与最新决定不一致。

`FACT`：SP 是成熟的混合求解组件，不构成独立新颖性。Subramanian、Uchoa 与 Ochi（2013）在作者版 pp.4–7 给出路线池—SP—启发式交互；Hiermann 等（2019）在能源异构车辆路径问题中采用分层路线评价并把搜索历史路线送入 SP，见作者版 §4 pp.4–7、§5 pp.8–9、§6.3 p.13。取证见 `mv_multiview_evidence_audit_20260806/C2_multiview_literature.md`。

`FACT`：当前 SP 主问题只有客户精确覆盖约束，选列后再交完整评价器。旧的“路线条数不超过实体车数”约束在严格多趟下语义错误；恢复它会等价地禁止一辆实体车执行第二趟。

`FACT`：约束仍在时，T25 的 90 个单元中 SP 候选被拒 76 个；最近 70 个单元中，65 个重组解被完整模型拒绝、4 个无解、1 个限时有 incumbent，接受数为 0。最终结果退回合法 HGS 父方案，所以这说明 SP 组件未发挥作用，不等于父方案不合法。

`INFERENCE`：病灶不是简单“少一条车队约束”，而是当前 SP 的列是单趟路线，完整模型的资源是可串联多趟的实体车辆；列定义和主问题资源层级不一致。

`HALT`：C3b 文献补查尚未闭合，不能声称“经典 SP 主问题只写覆盖约束就足以证明当前写法正确”。经典做法通常以“列本身已资源可行”为前提，而本项目的整体实体车可行性在列选择之后才知道。
